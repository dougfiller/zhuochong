# 步骤 17：实现源 lineage、不可变消息版本和导入代际

> 文档状态：实施前技术方案（仅方案设计）<br>

> LOOF run：`20260806-task-17-source-lineage-immutable-message-generations`<br>
> 前置基线：步骤 15 已冻结 `wechat_archive_v1` 的只读 allow-list、流式 JSON 解析与脱敏 fixture；步骤 16 已建立唯一 `KnowledgeStore`、`knowledge.sqlite` 的 schema v1、`staging → ready_candidate → active` 边界，以及预留的 `knowledge_source_lineage`、`knowledge_message_versions` 和 `knowledge_import_generations` 表。本步骤只把这些已存在的边界接成可证明的 lineage、不可变消息版本和确定性合并，不改变微信采集、OCR、模型、Tauri command、桌宠或自动发送行为。

## 0. 方案设计原则

- **候选绝不越界**：任何新导入只写其 `staging/ready_candidate` generation；在完整版本、provenance、索引映射和计数均已就绪前，`knowledge_catalog_state`、`knowledge_conversations.active_import_generation_id` 与现有 active index 均不得改变。
- **来源与正文分离**：导出包路径、显示名、媒体路径不进入普通日志或 DTO。派生库只保存受控内容、匿名 source/generation/message ID、manifest 已声明 hash、相对成员 token 与必要的 lineage 证据摘要。
- **版本只追加**：`knowledge_message_versions` 没有更新或覆盖路径。相同逻辑消息的正文变化创建新 version；相同 canonical content 复用已存在的 version（但仍为本 generation 写 member 选择记录）。
- **不猜增量语义**：现有 `wechat_archive_v1` 仅接受 `full/selected`，而 `full + filters` 已归类为 filtered。要接收“incremental”，必须有 v1 白名单中的明确 `scope.kind="incremental"` 和覆盖声明；不能由目录大小、时间、消息数或“看起来只多了一些消息”推断。
- **同一输入同一结果**：合并顺序只由持久化的 source 事实决定，绝不使用随机 opaque ID、SQLite 返回顺序、文件遍历顺序或本机当前时间作为 tie-breaker。

## 1. 目标、边界与验收

### 1.1 目标

1. 将每个成功导入源与其 predecessor/overlap/supersedes 证据写入 `knowledge_source_lineage`，可追溯某 active generation 使用了哪些导出源。
2. 对每条可用文本消息写入 immutable `knowledge_message_versions` 与 `knowledge_message_sources`；同一消息在不同导出中正文不同时，历史版本仍可审计且不被覆盖。
3. 让 full、filtered/selected 和显式 incremental 包可在同一会话上形成确定性的 candidate generation；仅 candidate 全部 ready 且 index 已就绪后，单事务替换 active 视图。
4. 验证任意候选正文、失败导入和未激活 index 均不可被 `read_active_snapshot` 或后续检索读取；旧 active 视图在失败时保持可用。

### 1.2 非目标

- 不增加导出源扫描、媒体读取、重算导出 hash、微信协议/数据库访问、上传、MCP/Bot、输入自动化或自动发送。
- 不将 `selected`/`filtered` 升格为完整快照，不把未明确声明的 v1 资料猜成增量，也不以 filtered 导出删除其范围外的历史消息。
- 不实现 embedding、chunk 算法或真实 `knowledge_retrieve()`；本步骤只提供下一步骤可安全消费的 active generation / immutable membership 边界。
- 不改步骤 15 的路径 guard、`manifest/report/meta/messages` 白名单，且不改 Work Review 数据库。

## 2. 输入分类、source lineage 与确定性优先级

### 2.1 Source facts

导入器在已完成步骤 15 的 manifest/report 一致性、前后 member audit 与流式解析之后，构造 `SourceDescriptor` 并一次性交给 Store：

```rust
struct SourceDescriptor {
    account_stable_id: String,
    export_id: String,
    schema_version: String,
    manifest_content_hash: String, // 只取源声明值
    coverage_signature: String,
    exported_at_ms: i64,           // 严格 RFC3339 解析，不能解析则拒绝
    coverage_kind: CoverageKind,   // Full | Filtered | Selected | Incremental
}

enum SourceRelation { SameSnapshot, Extends, Overlaps, Supersedes }
```

`archive_schema.rs` 仅将明确白名单的 `scope.kind` 映射为上述 coverage：`full` 无 filters 为 `Full`，`full` 带 filters 为 `Filtered`，`selected` 为 `Selected`；只有 schema 明定的 `incremental` 及其 base/coverage 声明齐全时才为 `Incremental`。缺失/未知声明继续返回 `KB_SOURCE_UNSUPPORTED`，不能悄悄当作 filtered。

Store 为相同 account 的既有 source 比较稳定的五元组、coverage signature、manifest 统计和本次流式实际 membership：完全相同为 `SameSnapshot`；明确 incremental base 与前驱匹配为 `Extends`；两个 source 有相同 message identity 为 `Overlaps`；覆盖声明可证明同会话范围被后续 source 完整取代时为 `Supersedes`。证据不足时只允许 `Overlaps`（或不写关系），不得写 `Supersedes`。`evidence_hash` 是规范化的无正文事实（source fingerprints、coverage、计数、成员 identity hash）之 hash，绝不含原路径/正文。

### 2.2 合并排序与冲突规则

每个会话的 candidate source set 先以以下持久化 key 升序排序，最后一个胜出；这也是 `source_set_hash` 的规范化输入：

1. `(account_stable_id, conversation_stable_id)`；
2. `exported_at_ms`；
3. coverage strength（`Full`、`Incremental`、`Filtered`、`Selected` 的固定枚举值，仅作**同一时间**的稳定 tie-breaker，不表示可删除范围）；
4. `manifest_content_hash`；
5. `coverage_signature`；
6. `export_id`。

对同一 message identity：

- 同一 `content_hash`：不产生重复 version，candidate member 指向已有 immutable version，并为每个贡献 source 追加 provenance。
- content 不同：追加一个 version；上述排序最高的 source 的 version 成为该 candidate 的 member，较低优先级 version 仍保留、可经 lineage 审计。
- 无合法 stable ID 的 message 仍沿用 schema 的 `fallback_key` 分支；其 key 必须由 conversation、规范化 sender/time/type/content hash 的固定编码产生，并设置 `low_confidence=1`。stable ID 与 fallback key 永不互相匹配。
- full 只对其**明确覆盖的会话**构建 replacement candidate；filtered/selected/incremental 只合并所声明覆盖内的 members，不从 active generation 剔除范围外 members。

这样可避免按 import 到达先后产生不同结果，也避免 candidate 正文因 source 优先级尚未确定而污染 active view。

| `knowledge_import_generation_members` | 保持一个 generation/message 一条选择记录，并以复合外键保证 version 属于该 message。`selection_reason` 限定为 `new`, `unchanged`, `newer_source`, `retained_outside_coverage`。 |

## 4. Store 与导入流程

### 4.1 最小 API 调整

`archive_importer.rs` 继续只负责 read guard、schema 解析和单条流式转换；它把每条受支持消息转换成私有 `IncomingMessage`（identity、规范化正文、content hash、source member token），不保留整包 `Vec`。`store.rs` 增加下列私有 typed API，仍为唯一 SQL owner：

```rust
fn begin_generation(&self, source: SourceDescriptor, conversation: ConversationDescriptor)
  -> Result<StagingImport, ContractError>;
fn append_message_versions(&self, staging: &StagingImport, batch: &[IncomingMessage])
  -> Result<(), ContractError>;
fn finalize_candidate(&self, staging: StagingImport, checks: CandidateChecks)
  -> Result<CandidateImport, ContractError>;
fn build_ready_index(&self, candidate: &CandidateImport) -> Result<ReadyIndex, ContractError>;
fn activate_candidates(&self, candidates: Vec<(CandidateImport, ReadyIndex)>)
  -> Result<CatalogGeneration, ContractError>;
```

`append_message_versions` 每 256 条沿用步骤 15 的批事务：resolve/create message identity → insert-or-reuse immutable version → insert source provenance → upsert staging membership，任何约束/计数失败将该 generation 标记 `failed` 或回滚当前批；绝不修改 active generation。每个来源完整解析、前后 audit 相等、关系/计数/coverage 通过后才 `ready_candidate`。

### 4.2 原子候选激活

1. 读取当前 active generation 作为每个会话 candidate 的 parent；基于归一化 source set 与选中的 immutable version 计算 snapshot hash。
2. 仅为 `ready_candidate` 建立对应 ready index；building/failed index 不得可读。
3. `activate_candidates` 在一次 `BEGIN IMMEDIATE` 中校验所有 candidate/index/source-set/parent 仍匹配：先写 source lineage，再将每个新 generation 设为 active、仅把同会话旧 active 设为 superseded、更新每个 conversation pointer、最后一次性更新 catalog snapshot/index 与 generation sequence。
4. 任一会话或 index 不 ready、parent 已变化、lineage 约束失败或写入出错，则整笔回滚：旧 catalog、旧 active pointers、旧 index 和正文完全不变；返回 `KB_NOT_READY`/已存在的 fail-closed 错误。

快速核验命中仍只复用完全相同 source fingerprint + member audit；它可返回同一 source 的既有 lineage/membership，不能把“相似导出”误作相同 source，更不能跳过 candidate 关系校验。

## 6. 测试、隐私与通过条件

必须新增的定向测试：

- 同一 full source 重复导入走 fast verify，不产生 duplicate source、version 或 lineage；同 account/export 但 manifest/coverage 任一改变则重新走 candidate。
- full → selected、selected → incremental、两个交叠 filtered 以不同到达顺序导入，最终 source-set hash、选中 version、lineage 边和 active snapshot 完全一致。
- 同 stable message ID、同正文只保留一个 immutable content version；同 ID、不同正文产生两个 version，旧 generation 仍指向旧 version；稳定 ID 与 fallback identity 永不合并。
- 仅 filtered/selected/incremental 覆盖内的 message 被替换，未覆盖的 active member 以 `retained_outside_coverage` 留在 candidate；没有明确 coverage 不发生删除。
- candidate 解析失败、batch 约束失败、index fail、并发 parent 更新、lineage self-loop/跨 account、v2 migration/外键/完整性失败，均不改变旧 active catalog，且 active read 从不返回 candidate 正文。
- incremental 声明缺 base、未知 coverage、非法 RFC3339、未知 manifest 字段、路径逸出、媒体访问和包含真实样本的 fixture 均 fail-closed。
- 运行本步骤 Rust 定向单测、`cargo fmt --check`（限相关文件）和 `git diff --check`；macOS 单元测试不是 Windows OCR/UAT 证明，后者不属于本步骤。

通过仅表示：合成多导出可确定性合并、source lineage 可审计、message versions 不可变、候选对 active view 零泄漏，并由上述测试证明。未完成实际检索、embedding、Windows 实机、模型回复或自动发送。

## 7. 回滚与风险

- SQLite v2 migration 出错、来源不完整或关系证据不足时保持 Store unavailable/旧 active，不自动覆盖数据库或源包；发布后按该步骤独立提交 `git revert`，不删除用户 `data_dir`。
- 最大风险是导出器没有足够事实声明 incremental/base 或 coverage。此时只拒绝该包，不通过推断扩大导入权限。
- 所有诊断只使用错误码、匿名 ID、计数和截短 hash；禁止正文、真实 source 路径、账户/会话/消息 ID、媒体名称进入日志、断言失败文本或本计划后续的测试夹具。
