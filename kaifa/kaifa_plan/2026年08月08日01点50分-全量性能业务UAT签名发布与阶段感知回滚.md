# 全量性能、业务 UAT、签名发布与阶段感知回滚技术方案

## 0. 方案设计原则（自检清单）

- **阶段与 run 边界**：本文件只设计步骤 27，run_id 为 `20260808-task-27-final-performance-uat-release-rollback`，dispatch_id 为 `aich8-zhuochong-desktop-pet-rag-27-steps-20260805-task-27`。本阶段只新增本方案文档，不修改产品代码、不执行性能/UAT/打包、不启用发布或 updater、不写任何真实 Windows/签名/授权通过结论。
- **前置门禁的准确解释**：`main@d15b7c9` 与步骤 26 的 LOOF phase-5 已发布，允许步骤 27 开始；但正式 `work-review-m2-after-gate.json` 仍诚实为 `blocked`。步骤 27 必须重新收集真实同批证据，不能把步骤 26 的 synthetic fixture、macOS 回归或历史 M1/步骤 22 的 default-pass 政策当作正式发布证据。
- **最小改动**：复用 `KnowledgeStore` maintenance registry、候选库/manifest 成对发布、`Database::backup_to()`、`AppConfig::load_with_recovery()`、M2 audit/strict gate、现有 Tauri NSIS/单实例/自启动边界和禁用 updater 骨架。只补最终 release manifest/gate、Windows 采集脚本、私有 rebuild manifest、恢复备份 seam 与 runbook；不引入部署平台、通用遥测、远程 Agent、自动操作或第二套知识库。
- **外部参数 fail-closed**：正式产品名/identifier/binary、图标及素材授权、Windows Authenticode 证书与时间戳、Tauri updater 公钥/私钥引用和唯一受控 endpoint、内容保留期限、回复模型、loopback embedding、目标 Windows/微信 profile、冻结数据集与性能上限，任一未由用户/发行负责人确认时，正式发布 verdict 必须为 `blocked`。不得用占位值、旧上游参数或自签名替代。
- **发布物必须是 M2**：正式构建必须显式启用且只启用 `wechat-m2`；默认无微信 feature 的 Work Review 构建、`wechat-m1` 构建或双 feature 构建都不是候选。候选清单必须记录 feature 集与强制 RAG contract hash。
- **安全边界不变**：产品只处理用户当前明确选择的前台微信单聊可见区，只能手动触发、审阅、复制，由用户自行粘贴和发送。禁止微信注入、协议/数据库读取、UIA 输入、键鼠模拟、自动粘贴/发送、逐条新消息监控、未选聊天处理，以及从微信/RAG 链路调用 MCP、Bot、Localhost API、search、upload、Agent/tool/action。
- **RAG 不可降级**：同一 requestId 必须先 `knowledge_retrieve()` 再获得模型 permit。retrieval、scope、binding、context 或 audit 失败直接终止当前请求；运行时不存在切换 M1、换 scope、换 provider、云 embedding 或工具调用的补偿。
- **源数据与派生层分离**：用户明确选择的原始 JSON/JSONL 导出始终只读且不进入隔离/删除集合；`knowledge.sqlite`、`-wal`、`-shm`、内部非正文 rebuild manifest 和知识审计 JSONL 是独立可重建派生层。路径和 manifest 仅留在本机私有恢复文件，不进入 UI DTO、上传、仓库或发布证据。
- **证据与正文分离**：发布证据只保存候选/环境/场景 ID、计数、版本、耗时和 SHA-256/HMAC，不保存真实问题、聊天/OCR/命中/回复正文、API key、Authorization/Cookie、源路径或内部 conversation/message/chunk/source ID。
- **回滚不等于降级**：回滚目标只能是签名 release index 中最近一个 `m2Contract=forced-rag` 且最终 gate 真实通过的 M2 构建。禁止回滚到 M1、默认无 feature 包或仅因版本号较旧就任选安装包。

## 1. 背景与目标

### 1.1 当前可复用基线与真实缺口

当前 `main@d15b7c9` 已提供以下基础：

1. M2 命令编排在 Windows 路径调用 `generate_m2_wechat_reply()`；`finish_captured_m2_reply()` 固定 binding revalidate → `knowledge_retrieve()` → context → model permit → frozen transport，同请求检索失败不会调用模型。
2. 步骤 26 已把 retrieval、loopback embedding、OCR、physical model attempt、terminal、upload/capability 计数关联到 metadata-only M2 audit，并提供严格 evidence manifest 验证器。
3. `KnowledgeStore` 是唯一 `knowledge.sqlite`/SQL/migration owner；当前 `SCHEMA_HEAD=5`，chunk/token/FTS 版本分别为 `chunk-v1`、`v1`、`fts-pretoken-v1`，候选数据库与 manifest 可校验后成对发布并在失败时恢复旧对。
4. knowledge source maintenance 已有立即 receipt、后台 worker、单 maintenance lease 与终态查询；`start_rebuild(roots)` 仍要求显式 roots，但当前 manifest 只描述已建数据库，不能独立恢复 root 选择、priority/deny 决策，也没有完整隔离 WAL/SHM 的恢复演练。
5. Work Review 配置已使用原子 pending file、`.bak` 和 `load_with_recovery()`；核心 `workreview.db` 已有 `Database::backup_to()`（WAL checkpoint + `VACUUM INTO`），但尚无步骤 27 的同批回滚备份 receipt。
6. 单实例插件与 Windows `auto-launch` 已接入，普通用户重复启动会唤起现有窗口，自启动重复实例保持静默；这些只有代码/单测事实，尚无签名 candidate 的 Windows 安装/升级/卸载实测。
7. 正式 updater 目前正确地被禁用：`createUpdaterArtifacts=false`，无 updater plugin/pubkey/endpoints，release workflow 手动触发后固定失败。当前 `productName=Work Review`、`identifier=com.workreview.app`、证书 thumbprint 为 null、timestamp URL 为空。
8. `knowledge-performance-gate-v1.json` 当前没有目标 Windows、冻结数据集、批准阈值或实际观测，且保留历史 `default_pass_user_authorized`。本步骤不得沿用该事实豁免。
9. production `windows-wechat-v1.json` 的 `profiles=[]`，`third-party-assets.md` 仍有 BongoCat、图标/供应商标识、文档截图的 `pending-verification`。因此此刻无法生成合法正式候选，更不能发布。
10. 默认 `tauri build` 不选择 `wechat-m2`，所以发布工作流若只照搬上游命令会产出不含 M2 的普通 Work Review 包；步骤 27 必须显式冻结 feature identity。

### 1.2 业务目标

- 在同一冻结 Windows 主机、微信 profile、原始导出、模型/embedding 和候选批次上，完成性能、业务题集、真实微信端到端、升级/恢复、签名包与运行时隔离验收。
- 让发行负责人可从单一 strict gate 判断 `pass|fail|blocked`；缺外部输入或缺任一同批 evidence 时只能 blocked，而不是靠文档声明或人工修改 JSON 变 pass。
- 发生候选故障时，先生成可验证的配置和 Work Review 核心库备份，再只回滚到最后一个强制 RAG M2；知识派生层隔离后可从用户确认的只读导出确定性重建。
- 发布说明准确描述能力边界，不把“可见区手动生成回复”宣传成逐条消息识别、自动回复或自动发送。

### 1.3 可量化技术目标

## 2. 核心业务流程与边界

### 2.1 发布组件关系

```text
release-freeze-v1.json（用户确认的非秘密输入）
  -> Windows evidence collector（只写脱敏原始证据 + SHA-256）
       -> 性能 runner / 业务题集 runner / 微信 M2 audit
       -> rebuild + migration + recovery drill
       -> NSIS/updater/install/runtime/package observers
  -> final-release-manifest.json（同 releaseBatchId）
  -> verify_final_m2_release_gate.py
       -> blocked：缺输入/未运行/待授权，保持 release/updater disabled
       -> fail：证据矛盾、阈值超限、安全能力非 0、签名/数据恢复失败
       -> pass：才允许受保护 workflow 发布并写入 signed LKG index
```

### 2.2 候选冻结与构建顺序

1. 发行负责人先填写不含秘密的 freeze 文档：目标 Windows、微信 profile digest、数据集 manifest digest、性能 limits、产品 identity、已授权素材 ledger digest、回复模型 profile/digest、loopback embedding fingerprint/dimension、保留期限、签名证书 subject/thumbprint、timestamp host、唯一 updater endpoint host/pubkey digest、发布渠道。
2. freeze verifier 检查所有 required 字段已确认，时间早于测试，且 profile/dataset/assets 与仓库中的受控文件 hash 对应。API key、签名私钥、证书私钥只作为 CI secret/Windows certificate store 引用，绝不写文档。
3. 固定 `main` commit 与 clean source tree，生成 `candidate-identity.json`：commit、tree SHA-256、Cargo.lock/package-lock hash、Rust/Node/Tauri 版本、`features=[custom-protocol,wechat-m2]`、M2 contract hash、schema/prompt/profile freeze hash。
4. Windows 构建命令必须显式传 `--features wechat-m2`；构建前后 gate 分别证明 M1 symbols/feature 不可达、M2 command 可达。默认无 feature 产物即使成功打包也丢弃。
5. 先产出未发布的 signed candidate，计算 NSIS、updater archive、`.sig`、可执行文件和依赖 manifest hash；在这个不可变 candidate 上做所有后续测试，不在 UAT 后重编。

### 2.3 性能复验流程

1. collector 校验 Windows 硬件/OS/电源模式/磁盘空闲、微信 profile、embedding 服务和冻结 export manifest；任何漂移新建 batch，不能复用旧结果。
2. 在全新 data root 执行首次导入/索引，原始导出只读；采集 wall-clock、process working set、`knowledge.sqlite` 与 `-wal/-shm` 峰值/稳定大小、派生 index 大小。
3. 用固定查询集预热规则后运行足够次数；保存每次 query 的耗时与 outcome，只在 freeze 已固定的采样数量上计算 p50/p95，不删除慢样本。
4. 与此同时运行 Work Review 记录调度和前端输入探针，记录 drift/input latency；性能 runner 不模拟微信键鼠输入，UI latency 使用专用测试页面/受控内部事件。
5. gate 从原始样本重新计算聚合，不信任摘要 JSON。任一指标缺失、样本数不足、环境漂移、超限或沿用 `defaultPassRequirements` 均 blocked/fail。

### 2.4 业务题集与真实微信 UAT

1. `m2-business-question-set-v1` 只在受控 Windows evidence 根保存真实题目；仓库只保存 schema/template 与 question set hash。每题字段固定为 opaque `questionId`、category、scope kind、expected outcome、expected source rule、reviewer decision，不在 release manifest 复制正文。
2. 8 类至少各有一题且所有题在执行前冻结；noHit 预期是成功检索结果且可以生成谨慎回复，检索错误不是 noHit。
3. 真实微信流程必须由用户显式选择前台单聊和点击触发：隐藏 overlay/截图 → Windows OCR → binding 复核 → retrieval → model → 气泡 → 用户复制；UAT 停在复制确认，不由工具粘贴或发送。最终“自行发送”由用户人工确认，collector 只记布尔签字，不操作输入。
4. 每次运行从步骤 26 audit 收集 requestId HMAC、stageSeq、retrieval mode/count、permit、physical attempt、terminal、capability counts。来源复核通过现有显式 source fetch UI 人工验证，证据只记 source receipt hash/可用性，不复制 excerpt。
5. 前台切换、未选聊天、群聊实时回复、scope 失效、KB busy/corrupt、context 超限必须 fail-closed；模型调用 0 且没有旧建议覆盖新 generation。

### 2.5 deterministic rebuild 与缺 manifest 分流

本步骤把“数据库配对 manifest”和“私有 rebuild manifest”分开：

- `knowledge.sqlite.manifest.json` 继续只校验当前数据库/schema/catalog/source set，不承担定位原始导出。
- 新的私有 `rebuild-manifest.v1.json` 位于应用受管 data root、权限仅当前用户可读。它可含 canonical source root、root identity、原始 manifest/coverage hash、明确选择顺序、priority、retired/deny policy receipt 和 frozen index/embedding 配置；不含消息正文、excerpt、向量、API key。路径不得进入 UI DTO、日志、release evidence 或上传。

正常恢复顺序：

1. 用户通过 native directory picker 明确选择/确认 roots；Store 重新读取只读 manifest/report 并计算 facts，禁止调用者传 source IDs 或路径字符串绕过 picker。
2. 在单一 maintenance lease 下拒绝新 import/rebuild/retrieval/M2；取消并等待 in-flight request 与 reader drain，写入并 fsync 私有 rebuild manifest。
3. 关闭 Store writer/readers，对 app-managed `knowledge.sqlite`、`-wal`、`-shm`、数据库 manifest 和可选知识 audit JSONL 做同目录 rename 隔离，写 quarantine inventory/hash。**用户原始 JSON/JSONL root 永不在隔离/删除 allowlist 中。**
4. 从 rebuild manifest 顺序重读各原始 export，校验 root/manifest/coverage hash，重建 source lineage/import generations；再按冻结 receipt 恢复 priority/deny/retire，构建并验证 index candidate。
5. 验证 integrity/foreign key/schema/source set/lineage/priority/denial/message/chunk/FTS/vector/catalog 和 manifest pair 后一次发布并 reopen；生成不含路径/正文的 recovery receipt。
6. 为确定性证明，以同一只读原始数据在新的临时 data root 再跑一次，比较上述逻辑摘要；SQLite 文件字节不要求相同，业务/代际/索引摘要必须相同。
7. 任一步失败恢复被隔离的旧完整派生集合并 reopen，保持 `KB_NOT_READY` 或旧 active；不删除 quarantine，不触碰原始导出。

缺 manifest 或 hash 漂移时：保持 maintenance 安全结束、知识状态 not-ready，UI 只显示“需要重新选择知识导出目录”，必须再次 native picker + 用户确认；不得扫描常用目录、猜路径、静默采用 recent path 或从 `knowledge.sqlite` 反推正文来源。

### 2.6 旧配置、核心数据库升级与恢复

1. 从受控、脱敏的最后支持版本 fixture 和用户批准的克隆生成升级矩阵；原件只读，所有演练使用复制品。
2. 启动 candidate 前调用窄范围 recovery builder：`config.json`、现有 `.bak` 和 `Database::backup_to(recovery/workreview.db)`；写 owner-only 权限、SHA-256、SQLite integrity/row-count 摘要。knowledge 派生层单列 inventory，不塞入核心 DB backup。
3. candidate 读取旧 config 后验证 `AppConfig::normalize/migrate_legacy_config`、字段默认值、网络/截图安全配置和 `.bak` 语义；主文件损坏时从备份载入且不自动覆盖现场，主备均损坏时使用 fail-safe。
4. `Database::new()` 完成核心 schema 初始化/迁移后，验证活动、设置、报告、实体缓存、FTS 和已有 Work Review 功能；升级失败使用 recovery bundle 恢复，不拿 knowledge.sqlite 替代核心库。
5. rollback 前再创建一次独立 `pre-rollback` bundle，禁止复用升级前旧备份。backup receipt 必须与当前 installed version/releaseBatchId 绑定并实际 reopen 校验后才允许卸载/覆盖安装。

### 2.7 安装、升级、updater 与卸载

正式输入未齐时保持当前 disabled workflow/后端，不进行以下启用。输入齐全后最小启用顺序：

1. `tauri.conf.json` 替换为获批 product identity/icons/copyright；Windows certificate thumbprint/timestamp URL 绑定受控证书；`createUpdaterArtifacts=true`，只配置一个 HTTPS allowlisted endpoint 与获批 pubkey，禁止继承上游 GitHub/gh-proxy。
2. `Cargo.toml/main.rs/capabilities` 只恢复官方 Tauri updater plugin 所需最小依赖/权限；`commands/updater.rs` 参考上游版本比较/进度结构，但删除多源 fallback、GitHub API fallback 和任意 endpoint builder，所有下载由签名 updater 验证。
3. protected release workflow 只接受已经 final gate pass 的 candidate manifest，不能在 workflow 内重新构建另一个候选。Authenticode 校验、Tauri signature 校验和 timestamp 链均通过后才上传到暂存渠道。
4. Windows 生命周期矩阵：clean install；从最后已发布 M2 升级；updater 升级；重复启动；自启动 visible/silent；普通退出/重启；卸载；重装并读取保留核心数据。卸载不得静默删除用户 data root；如未来要提供清除数据，必须另有明确确认且保留期限已获批。
5. 暂存 endpoint 先验证 manifest 版本/hash/signature/candidate batch；错误签名、降级、endpoint 漂移、MITM/404/timeout 均安全失败且旧版本继续运行。

### 2.8 发行物、运行时和授权审计

- 依赖：从 Cargo.lock、package-lock、PE imports、安装目录生成 SBOM/allowlist；`uiautomation` 只能用于现有只读窗口识别边界，不得出现输入 API 调用；不允许 VPet、Open-LLM-VTuber、.NET/WPF sidecar、Steam/Workshop、MOD loader、Live2D。
- 进程/模块：在安装、启动、M2 UAT、updater、rollback 各阶段采集 process tree、window owner、loaded modules、child process、network endpoints 和 synthetic input counters。允许进程按 owner/frozen hash 列出；未知项 fail。
- 文件：解包 NSIS/updater 后扫描真实聊天/secret canary、`参考/`、`kaifa/`、测试 fixture、source roots、knowledge.sqlite、WAL/SHM、evidence、私有 rebuild manifest、debug symbols 与未授权素材。
- 授权：`third-party-assets.md` 中任何 `pending-verification` 都是 blocker；不能只扫描文件名。每个实际打包素材必须绑定 ledger row、来源、许可证/商业授权、版权声明和 SHA-256。

### 2.9 阶段感知回滚

```text
检测 release incident
  -> 停止新 M2 request / 进入 maintenance
  -> 创建并验证 pre-rollback recovery bundle
  -> 校验 signed LKG index
       -> 无 forced-rag M2 LKG：停止，人工处置（绝不装 M1）
       -> 有 LKG：安装签名旧 M2
  -> 启动并验证 config + workreview.db
  -> 隔离不兼容 knowledge 派生层
  -> 用户确认的 rebuild manifest 重建
  -> 运行强制 RAG smoke：retrieval error model=0，success 先检索后模型
  -> 恢复服务 / 保留 incident 与 quarantine
```

`release-index.json` 每条 LKG 至少包含 version、candidate commit/tree、NSIS/updater hash、signer、releaseBatchId、final gate hash、`m2Contract=forced-rag`、schema compatibility、publishedAt。index 本身必须签名/受保护，不能由本机脚本随意手填。

回滚不会修改 request 级错误策略：一次检索故障只结束该 request，不触发安装降级；只有发布级 incident 经过人工确认才进入 runbook。

### 2.10 明确不做的事项

- 不新增自动微信发送、粘贴、键鼠/UIA 输入、消息监听、群聊实时回复或未选聊天扫描。
- 不新增云 embedding、模型自动切换、MCP/Bot/search/upload/Agent 工具。
- 不把原始导出写入/删除/打包/上传，不把 Work Review 核心 DB 与 `knowledge.sqlite` 合并。
- 不重构 `KnowledgeStore`/Tauri updater/配置系统，不建立通用部署平台或后台遥测。
- 不发布 M1、默认无 feature、unsigned/self-signed、上游 identity/updater endpoint 或包含 pending asset 的包。
- 不在本步骤启用 Live2D、VPet/Open-LLM-VTuber、PNG 增强、ASR/TTS 或附件理解。

## 4. 接口定义（内部契约）

### 4.1 rebuild 接口

保留现有 `start_rebuild(roots)` command 语义，Store 内部增加窄接口而非第二套 owner：

```text
prepare_rebuild_manifest(explicit_picker_roots, current_policy) -> PrivateRebuildManifest
start_rebuild_from_manifest(manifest, expected_manifest_hash) -> operationId
get_knowledge_maintenance_status(operationId) -> running|succeeded|failed
```

- 只有 native picker receipt 能创建/替换 root 路径；frontend 不能构造路径。
- manifest 缺失/不匹配返回稳定 `KB_REBUILD_SELECTION_REQUIRED`（若不新增错误码也可复用 `KB_NOT_READY` 并由安全 reason enum 映射 UI，但不得透出路径）。
- 整个 isolation/rebuild/publish 使用同一 maintenance lease；读请求 closed 时 fail-closed。

### 4.2 recovery builder

在 `commands/config.rs` 复用 `Database::backup_to()`，抽出不暴露数据库连接的内部函数：

```text
create_recovery_bundle(selected_directory, reason=pre_upgrade|pre_rollback)
  -> { bundleId, createdAt, verified, fileDigests }
```

目录必须由 native picker 明确选择、不是 data root 内部/父子目录、不是 symlink；先写临时 bundle，校验 reopen/integrity/hash 后 rename 提交。错误时删除本次未提交临时文件，保留原 config/DB。

### 4.3 final gate CLI

## 5. 核心逻辑详解

### 5.1 同批证据 join

1. candidate identity 是 batch root；每个 evidence file 声明同 `releaseBatchId` 与 candidate SHA-256。
2. verifier 打开文件并重算 hash，再从 raw event 计算 summary；摘要字段与 raw 不同即 fail。
3. 真实 M2 request 同时满足：Windows attestation/profile、question/scenario、trace/audit、retrieval/model counts、candidate batch；任何一边缺失 blocked。
4. package/install/runtime/rollback evidence 必须指向相同 NSIS hash。安装后 executable hash 与包内 hash不一致 fail。
5. approval 只能批准既有 manifest hash；证据或候选变化后 approval 自动失效。

### 5.2 性能统计

- percentile 使用 verifier 中固定算法（排序后 nearest-rank），raw samples 只增不删。
- 首次索引从空派生根开始到 candidate active/reopen 完成；不把下载 embedding 模型或人工选择时间混入，环境前置时间单列。
- DB 大小同时记录 stable main、WAL/SHM peak、derived total，防止只报主文件。
- query latency 按 scope/category分层并给全量 p50/p95；错误请求不删除，错误率必须为 0 或由 freeze 明确上限。
- 调度 drift/UI latency 与索引/查询同时压测，证明知识工作不破坏 Work Review 核心体验。

### 5.3 rebuild policy 重放

- source identity 来自原始 manifest/coverage/account/export facts，不由 path 或导入顺序单独决定。
- manifest 记录选择顺序与 priority，但重建通过确定性排序固定相同事实；deny/retire 通过不可正文 policy receipt 重放。
- 两次重建比较 source facts、lineage edges、message version/membership hashes、active source mapping、deny set、chunk/index/catalog snapshot；不比较随机 UUID 或 SQLite 页面布局。
- 原始导出变化即旧 manifest 无效，要求重新确认；不做猜测性 incremental merge。

### 5.4 签名与更新信任链

- Authenticode：`signtool verify /pa /all /v` 成功，证书 thumbprint/subject 与 freeze 相同，timestamp 可验证且在证书有效期内。
- Tauri updater：artifact `.sig` 使用 freeze pubkey验证，manifest version/URL/hash 指向同 candidate；错误 key/hash 必须拒绝。
- 发布 endpoint 只允许 HTTPS exact host/path prefix；redirect 到其他 host、代理或 HTTP 失败。
- private keys 只在 protected environment 使用，不写日志；证据保存公钥 digest、证书公有信息和验证输出摘要。

### 5.5 阶段兼容判断

rollback verifier 使用矩阵：

| 当前/目标 | 核心 config/DB | knowledge 派生层 | 允许 |
| --- | --- | --- | --- |
| M2 newer → M2 LKG，schema兼容 | 先 backup 后原地验证 | 可继续使用，仍复验 RAG | 是 |
| M2 newer → M2 LKG，knowledge schema不兼容 | 先 backup 后恢复/迁移验证 | 隔离并从 manifest 重建 | 是 |
| 任意 M2 → M1/无 feature | 不执行 | 不执行 | 否 |
| 无签名/无 gate/LKG index缺失 | 不执行 | 不执行 | 否 |

### 5.6 当前缺输入时的行为

实现阶段可以完成 schema、verifier、Windows runner、rebuild/recovery seam、runbook 与 blocked manifest；但以下保持不变：release workflow 固定失败、updater disabled、`createUpdaterArtifacts=false`、production profile 空、现有产品 identity 不当作已确认。只有用户给齐并确认所有外部参数，另由同 run 的实施按 gate 顺序启用；否则最终 formal release 证据必须持续 exit 2。

## 6. 非功能性设计

### 6.1 性能与资源

- release collector 为短期测试工具，不常驻生产；metadata audit 仍有有界事件和单行限制。
- rebuild 先候选后切换，长耗时导入不持 AppState 锁；maintenance closed 明确阻断新知识任务，reader drain 有限超时。
- backup 使用 SQLite 自带 checkpoint/VACUUM INTO，不直接复制打开中的单个 DB 文件。

### 6.2 高可用与失败补偿

- build/UAT/gate 任一失败不改远端 release channel。
- rebuild/publish 任一步失败恢复旧 DB+manifest+WAL/SHM inventory，quarantine 保留；无法完整恢复则 KB_NOT_READY，不影响 Work Review/M1-less核心启动。
- updater 失败继续运行旧签名版本；rollback 失败保留 pre-rollback bundle并停止，不尝试 M1。
- config 主备损坏使用现有 fail-safe，不启动自动网络、截图或消息能力。

### 6.3 安全与隐私

- Windows runner 仅在用户批准的测试根工作，拒绝 home/data root broad glob 与 symlink；删除仅限本 batch 创建的 temp/quarantine。
- 真问题、原始导出、recovery bundle、private rebuild manifest不提交、不上传；release manifest只引用摘要。
- 包扫描用虚构 canary；若发现疑似真实聊天/secret只报告规则和文件摘要，不回显内容。
- 不启动 Chrome/网络搜索/MCP/Bot/Agent 做 UAT；模型仅走现有 no-tools single-turn reply transport，embedding仅 loopback。

### 6.4 可维护性与版本冻结

新增 `m2-contract-freeze-v1.json` 从代码常量/配置生成并验证：knowledge schema head、migration file hashes、chunk/token/FTS版本、RRF/retrieval config、embedding fingerprint/dimension、微信 system prompt SHA-256、context schema/token budget、compatibility catalog hash、M2 audit schema、release note hash。任何漂移必须新 candidate/batch。

### 6.5 回滚安全

- runbook 所有目标以 signed manifest 的精确绝对 artifact hash解析，不用 latest glob。
- 不执行 `git reset --hard`、递归删除 data root 或覆盖原始导出。
- material quarantine/backup 删除不属于自动回滚；保留期限未获批时不自动清理。
