# 完善可观测性、能力隔离和 M2 综合故障测试技术方案

## 0. 方案设计原则（自检清单）

- **阶段与 run 边界**：本文件只设计步骤 26，run_id 为 `20260808-0027-步骤-26完善可观测性能力隔离和-m2-综合故障测试dispatch_idaich8-zhuoc`，dispatch_id 为 `aich8-zhuochong-desktop-pet-rag-27-steps-20260805-task-26`。本阶段只新增本方案文档，不修改产品代码、不执行测试、不写步骤 27 的性能、UAT、打包或发布结论。
- **最小改动**：复用步骤 8 的 `WechatReplyRuntime`/`ReplyTraceStore`、步骤 21 的 `EmbeddingAuditSink`、步骤 23 的 `knowledge_retrieve()`、步骤 25 的 `M2ReplyTailPort`/`FrozenRagTransportEnvelope`/`RagTransportAttempt` 和现有 Work Review 测试骨架。只补一个元数据证据汇聚边界、必要 spy seam、严格门禁和缺失的故障用例；不引入通用 telemetry 平台、消息队列、数据库迁移或新的网络依赖。
- **事实与门禁分离**：自动化通过只证明对应 fake/合成场景；Windows、真实微信、真实模型、安装包、真实性能和素材商业授权没有证据时必须为 `not-run`/`blocked`。步骤 14 的 `default_pass_requirements` 只保留为历史调度事实，步骤 26 的 M2 门禁不得接受 default-pass、用户豁免或空 evidence 代替事实通过。
- **证据不带正文**：汇聚记录只允许 requestId、stageSeq、事件枚举、计数、attempt、结果码、耗时、版本和 SHA-256/HMAC；禁止记录 OCR/聊天/命中/建议正文、API key、Authorization、Cookie、模型完整 endpoint、源路径、内部 chunk/message/conversation ID 或上传对象 ID。
- **安全边界不变**：仍只允许用户在前台明确选择的微信单聊中手动触发、审阅、复制、粘贴和发送。禁止微信注入、协议/数据库读取、UIA 输入、键鼠模拟、自动粘贴/发送、切换未选聊天，以及从微信/RAG 链路调用 MCP、Bot、Localhost API、remote upload、web search、Agent/tool/action。
- **谁来做都不走样**：下文固定事件模型、能力枚举、join 规则、故障矩阵、证据 schema、严格 verdict 和文件修改顺序；实现者不得把“扫描到字符串”当作动态零调用证据，也不得把时间戳先后替代 stageSeq/permit/真实 transport attempt。

## 1. 背景与目标

### 1.1 现状基线

当前 `main@e25e6c3` 已具备以下可复用事实：

1. `desktop/src-tauri/src/wechat/runtime.rs` 维护单请求 lease、合法状态迁移、严格单调 `stage_seq`、`logical_model_requests` 和 metadata-only trace；M2 只有 `Retrieving -> Generating -> ReplyReady/Failed/Cancelled` 合法路径。
2. `desktop/src-tauri/src/wechat/reply_flow.rs` 已抽出平台无关的 `finish_captured_m2_reply` 与私有 `M2ReplyTailPort`，可在 macOS/Linux 用 fake revalidate/retrieve/transport 覆盖 Windows 前半段之后的真实编排顺序。
3. `desktop/src-tauri/src/wechat/model_client.rs` 已用 `FrozenRagTransportEnvelope` 把 requestId、binding generation、stageSeq、context hash、model request id、精确 request bytes 和 physical attempt 绑定；有限重试只复用同一 envelope。
4. `desktop/src-tauri/src/knowledge/embedding.rs` 已有 `EmbeddingAuditSink`，loopback endpoint 经过解析、pin、禁止 redirect 和维度/fingerprint 校验；检索层已有 FTS fallback、reader busy、BLOB/FTS 损坏、代际切换测试。
5. `desktop/src-tauri/src/wechat/content.rs` 已实现默认关闭、1—30 天留存、按请求删除、到期清理和 symlink fail-closed；来源查看从当前 active Store 重取，来源失效不返回旧正文。
6. `desktop/src-tauri/src/knowledge/store.rs` 与 `archive_importer.rs` 已覆盖候选不可见、失败导入清理/重放、source lineage/priority/deny、候选计数/向量一致性验证和原子 catalog 切换。
7. `desktop/docs/baselines/work-review-m1-after-gate.json` 的历史 M1 verdict 使用了 `default_pass_requirements`；`desktop/docs/baselines/third-party-assets.md` 仍含 `pending-verification`。二者均不能作为步骤 26 的事实通过证据。

当前缺口不是再造功能，而是把分散证据按同 requestId 串联、明确 allowed/forbidden capability 语义、补齐物理 attempt 与综合故障/并发矩阵，并产出不能伪通过的 M2 after-gate。

### 1.2 业务目标

- 用户每次明确触发 M2 后，都能用一份脱敏证据回答：哪一个 request 先完成了何种检索、何时获准开始真实模型 transport、调用了哪些允许能力、哪些禁止能力保持 0、最终是否发布了当前建议。
- 任一检索、scope、context、binding 或数据库错误都 fail-closed，不回退 M1、不调用回复模型、不上传、不执行工具。
- Work Review 原能力、桌宠与设置仍可用；全局开启原有上传/MCP/Bot/Localhost API/搜索并不赋予微信/RAG 请求使用这些能力的权限。

### 1.3 可量化技术目标

| 目标 | 可量化验收 |
| --- | --- |
| 请求串联 | 每个受测 M2 request 的 reply trace、retrieval receipt、embedding spy、model transport spy、upload queue spy、capability snapshot 均由同一 `requestId` 或不可逆 requestId HMAC 关联；无孤儿 transport attempt |
| 先检索后模型 | 所有 physical model attempt 均引用已落盘的 `retrieval_completed(success|no_hit)` 对应 `stageSeq=5` permit；模型 attempt 出现前 trace 已成功 append；检索错误分支 physical attempt=0、logical request=0 |
| 重试冻结 | retryable 首次失败最多再试 1 次；两次 attempt 的 requestId、bindingGeneration、stageSeq、contextHash、modelRequestId、provider request bytes SHA-256、selectedHitCount/集合摘要完全一致；retrieval_calls 恒为 1 |
| 能力隔离 | request-scoped `replyModelNonLoopback` 为 0—2、`knowledgeEmbeddingLoopback` 按场景计数、`ocrBackendLocalProcess` 仅条件适用；MCP/Bot/Localhost API/upload/search/action/cloudEmbedding/petResourceProcess 均为 0 |
| 上传隔离 | 开启所有相关全局开关后，微信/RAG request 对应 upload enqueue/attempt 为 0；Work Review pending upload 集合中不存在虚构微信 canary、`wechat_reply/**`、`knowledge.sqlite*`、源目录、内部 ID 或派生文件 |
| 隐私 | evidence/trace/fixture/package scan 对真实聊天 canary、常见凭据形状和受控敏感字段 0 命中；聚合 JSON 单记录上限固定且拒绝额外字段 |
| 留存 | 默认关闭不创建 content 根；开启只写专用 request 目录；到期与手动删除有效；来源重取失效时不返回旧正文；内容文件不进入 knowledge Store 或上传集合 |
| 综合故障 | 第 7 节所有 required 行有自动化 `pass` 或真实环境 `pass`；任一缺项、`not-run`、counter 非法、证据 hash 不匹配或素材授权缺口令 M2 verdict 为 `blocked`/`fail` |

## 2. 核心业务流程与边界

### 2.1 组件关系

```text
用户显式触发
  -> 现有 Windows 微信 capture/OCR 编排器
  -> WechatReplyRuntime + ReplyTraceStore
  -> finish_captured_m2_reply(M2ReplyTailPort)
       -> binding revalidate(BeforeRetrieval)
       -> KnowledgeStore::knowledge_retrieve
            -> embedding loopback spy / FTS fallback
       -> build_model_context
       -> runtime.complete_retrieval (trace 先持久化 stageSeq=5)
       -> binding revalidate(BeforeModelTransport)
       -> runtime.authorize_model_call
       -> WechatReplyModelClient
            -> RagTransportAttempt spy -> 真实 no-tools text transport
       -> runtime 终态 -> 桌宠有限 payload
  -> M2EvidenceCollector（只汇聚元数据快照，不接触正文）
       -> strict M2 after-gate JSON/MD
```

`M2EvidenceCollector` 不是新的运行时业务总线。生产路径只在已经存在的 trace、embedding、transport 和 OCR audit sink 上补统一的只写元数据 sink；上传队列、禁止 capability 与桌宠哨兵主要通过 request-scoped integration spy、静态调用边界和 Windows 外部观察三类证据交叉证明。

### 2.2 正常 success/no_hit 流程

1. `begin_reply` 写 `validating(stageSeq=1)`，后续 capture/OCR 仍沿用现有迁移。
2. OCR 成功后进入 `retrieving(stageSeq=4)`；证据 sink 只收 requestId、stageSeq、backend class，不收 OCR 文本。
3. `BeforeRetrieval` binding gate 成功；`knowledge_retrieve()` 最多执行一次。embedding spy 记录 endpoint class、operation、call count、batch size、outcome，不记录 query、model endpoint 或向量。
4. 检索结果为 `success`、`no_hit` 或合法 `fts_fallback`；`build_model_context` 冻结实际 provider bytes、context hash 和 selected hit 数量。
5. `runtime.complete_retrieval` 先 append 现有 `Generating(stageSeq=5,m2=...)` trace。证据归一化时将这一事实命名为 `retrieval_completed`，保留 `success|no_hit|fts_fallback`，不新增可绕过状态机的状态。
6. 第二次 binding gate 成功后，runtime 只在当前 request/binding/context/stageSeq=5 发 `ModelCallPermit`。
7. `RagSingleTurnTransport::complete` 在调用真实 `SingleTurnTextTransport` 之前记录 `model_transport_started`。事件复用 envelope 的 requestId/stageSeq/contextHash/modelRequestId，并只记录 provider bytes SHA-256 与 attempt；provider body 不复制进 evidence。
8. 成功后 runtime 写唯一 `reply_ready` 终态并发布有界桌宠 payload；上传/Agent/MCP/Bot/输入能力无入口。
9. 测试/门禁从各 sink 生成 immutable snapshot，一次性 join 并校验；collector 不读取真实正文目录。

### 2.3 先检索后模型的主证据规则

不能只比较 wall-clock 时间戳。严格 join 规则如下：

```text
trace(requestId, stageSeq=4, stage=retrieving)
  -> trace(requestId, stageSeq=5, stage=generating, m2.retrievalMode=success|no_hit|fts_fallback)
  -> permit(requestId, bindingGeneration, stageSeq=5, contextHash, modelRequestId)
  -> transport_started(same envelope, attempt=1[,2])
  -> trace(requestId, stageSeq=6, terminal=reply_ready|failed|cancelled)
```

- `retrieval_completed` 是现有 `Generating(stageSeq=5,m2 metadata)` 已成功持久化的归一化名称；不为了日志名字引入新业务状态或把 reply-ready 整体改号。
- transport spy 必须由拿到 `RagTransportAttempt` 的最后一层记录，不能由调用方“预计将调用”代写。
- collector 验证 trace 文件中 stageSeq 严格递增、迁移合法、stage 5 行在读取快照时已存在，且 attempt envelope 精确等于 permit。时间戳只用于诊断同一证据批次，不决定 pass。
- `success/no_hit/fts_fallback` 才能有 attempt；`KB_NOT_READY`、`KB_SCOPE_UNRESOLVED`、`KB_RETRIEVAL_FAILED`、context/binding 失败均必须出现唯一失败终态且 attempt=0。

### 2.4 异常与补偿流程

| 故障位置 | 必须行为 | 补偿/恢复 |
| --- | --- | --- |
| scope/binding 在检索前失效 | 当前精确阶段写 `Failed/Cancelled`，retrieval=0，model=0 | 释放 lease；用户重新显式选择/绑定后新 request 重试 |
| KB 未就绪/SQLite busy/损坏 | 映射稳定 KB 错误，context 不构造，model=0 | 保持旧 active generation；不自动清库、不回退 M1 |
| embedding 不可用 | 仅按现有契约走同 generation 的 FTS fallback；若 FTS/payload 失败则 model=0 | 不云回退、不更换 embedding provider |
| context 超限/组装失败 | 检索 receipt 可留存，模型 permit 不发 | 用户可调整问题/配置；不发送裁减失败的半成品 |
| binding 在 transport 前晚失效 | 已完成检索但 model=0，唯一失败终态 | 释放 lease；旧 context 不复用到新 request |
| 模型 timeout/429/5xx | 同 envelope 最多 attempt=2 | 第二次仍失败则 `LLM_FAILED`；不重检索、不换 provider |
| 空输出/tool call/provider 非可重试错误 | 立即失败，attempt 按真实调用计数 | 不发布建议、不调用工具 |
| 模型晚到/取消/代际变化 | runtime 拒绝 result，不能覆盖新建议 | 记录 stale/cancelled；下一 request 可正常开始 |
| 导入/索引崩溃 | building/candidate 保持不可见 | 清理或从会话头重放；旧 active pair 继续服务 |
| 候选校验/维度/source conflict 失败 | 原子激活前拒绝 | catalog sequence 与旧 active pair 不变 |

### 2.5 功能边界

本步骤不做：检索排序/embedding 模型重选、schema migration、性能阈值重定、Windows 真机最终 UAT、正式 NSIS/更新包发布、通用观测后台、云 telemetry、日志上传、桌宠引擎重构、VPet/Live2D/PNG 增强、OCR 新引擎、Agent/tool API 改造。

无真实凭据的 Work Review S3/WebDAV、Bot、Localhost API、MCP、联网搜索仍保留现有 schema/mock/队列/错误路径测试；“微信请求禁止调用”不能通过删除原有功能来满足。

## 3. 数据模型设计

### 3.1 不新增业务数据库

- 不修改 `knowledge.sqlite`、Work Review SQLite 或 migration。
- 不把 audit/capability 写入知识库，不让 `KnowledgeStore` 以外模块拥有 SQL。
- 生产 evidence 继续使用专用 metadata-only JSONL；测试汇总 JSON 写入受控证据目录。正文留存仍由现有 `WechatContentStore` 独立管理。

### 3.2 元数据事件模型

在 `wechat/observability.rs`（名称可按现有风格最终定为 `audit.rs`，二选一，不同时创建）定义私有、封闭枚举：

```rust
enum M2AuditKind {
    RetrievalCompleted,
    ModelTransportStarted,
    EmbeddingTransport,
    OcrLocalProcessStarted,
    UploadQueueObserved,
    CapabilityObserved,
    TerminalObserved,
}

enum CapabilityKind {
    ReplyModelNonLoopback,
    KnowledgeEmbeddingLoopback,
    OcrBackendLocalProcess,
    Mcp,
    Bot,
    LocalhostApi,
    RemoteUpload,
    Search,
    Action,
    CloudEmbedding,
    PetResourceExternalProcess,
    PetResourceNetwork,
    PetResourceModuleLoad,
    PetResourceSyntheticInput,
}
```

事件字段固定为：`schemaVersion`、`eventId`、`occurredAt`、`requestId`、`kind`、`stageSeq?`、`attempt?`、`capability?`、`origin`、`outcomeCode`、`count`、`elapsedMs?`、`contextHash?`、`modelRequestId?`、`requestBytesSha256?`、`selectedHitCount?`。所有字符串使用枚举或已验证的 32/64 位十六进制摘要；JSON 使用 `deny_unknown_fields`，单行继续受 16 KiB 上限。

明确禁止字段和调试输出：`text/body/prompt/excerpt/query/apiKey/authorization/cookie/path/sourcePath/chunkId/messageId/conversationId/objectKey/vector/endpoint`。静态 verifier 和 serde round-trip 测试同时约束。

### 3.3 request 级能力快照

`CapabilitySnapshot` 使用固定 key，不接受任意 map 名称：

```json
{
  "requestId": "opaque-uuid",
  "counts": {
    "replyModelNonLoopback": 1,
    "knowledgeEmbeddingLoopback": 2,
    "ocrBackendLocalProcess": 0,
    "mcp": 0,
    "bot": 0,
    "localhostApi": 0,
    "remoteUpload": 0,
    "search": 0,
    "action": 0,
    "cloudEmbedding": 0
  }
}
```

- `replyModelNonLoopback` 计 physical attempts，不等同于 runtime 的 `logicalModelRequests`；正常成功通常为 1，有限重试为 2，检索失败为 0。
- `knowledgeEmbeddingLoopback` 计真实 metadata/query HTTP attempts；纯 FTS 或 preflight 失败可为 0，不要求为了计数而发请求。
- `ocrBackendLocalProcess` 只有经 `WechatOcrDispatcher` 且 frozen fallback audit 批准时可大于 0；origin 必须是 `wechat_ocr_orchestrator`，上限为本次单次 fallback。桌宠/资源/设置 origin 永远为 0。
- forbidden key 只要非 0 即 `fail`，缺 key、负值、字符串值或无法关联 requestId 同样 `fail`。

### 3.4 严格 M2 after-gate 文档

新增 `desktop/docs/baselines/work-review-m2-after-gate.json` 与同名 `.md`。JSON 至少包含：

- `schema_version`、`gate_id`、`generated_at`；
- candidate：`git_commit`、`source_tree_sha256`、`nsis_sha256`、`batch_id`，未知项为 `null`，不能填占位字符串；
- environment：OS/build、Windows host、微信 profile fingerprint、是否真实 model/embedding、证据类型；
- request evidence：只放 requestId/HMAC、事件/计数/证据文件 SHA-256，不放正文；
- fault matrix：第 7 节稳定 ID、`pass|fail|blocked|not-run`、evidence IDs；
- AC matrix：完整 AC-BASE-01..10、AC-WX-01..10、AC-PET-01..05、AC-KB-01..08、AC-RAG-01..11 逐项状态和证据；条件项只能使用 `conditional-not-applicable` 且必须有适用性理由；
- credentials mock matrix、privacy scan、sentinel counters、reference/assets review；
- `verdict` 和 `blockers`。

本 schema **不提供** `default_pass_requirements`、waiver 或 authorized-defaults 字段。存在这些字段必须 schema fail。`pass` 仅在所有 required/当前适用项均有真实可复核 evidence 且 blockers 为空时允许；无 Windows/安装包/授权时只能 `blocked`，不因自动化代码完成而改为 pass。

## 4. 接口定义（内部契约）

### 4.1 Audit sink

```rust
trait M2AuditSink: Send + Sync {
    fn record(&self, event: M2AuditEvent) -> Result<(), ContractError>;
}
```

- 生产默认 sink 只写现有 `dataDir/wechat_reply/audit/YYYY-MM-DD.jsonl`，写失败 fail-closed：在模型 transport 前写失败则不发模型；transport 已发后的终态证据失败则按现有 trace failure 策略终止且不得把缺证据 request 判通过。
- 测试 `SpyAuditSink` 用 `Mutex<Vec<M2AuditEvent>>`，按 requestId snapshot；不向业务层暴露可伪造的 public constructor。
- 不把 sink 放入前端 command，不提供正文/路径查询 API。设置页继续使用现有安全 trace summary/source explicit fetch。

### 4.2 Model transport spy

保留现有 `RagSingleTurnTransport`，只把 audit sink 注入到 `SingleTurnRagTransport` 与测试 `SequenceTransport`：

```text
record(model_transport_started from RagTransportAttempt)
-> inner.complete(model, exact frozen request)
-> record(outcome code / elapsed only)
```

记录前先验证 request bytes SHA-256 等于 envelope 的冻结 bytes；attempt 只能 1 或 2。API key、provider body、endpoint 不进入 event。真实 provider parser 的 tool-call response继续由 `single_turn_text()` 拒绝，不为工具执行建立任何入口。

### 4.3 Embedding/OCR spy 适配

- 给 `EmbeddingCallAudit` 增加可选 request correlation（query path 为 requestId；index build 使用无 request 的 batch correlation），或用薄适配器在 `knowledge_retrieve` 调用边界把当前 requestId 与 sink 组合；不能用 thread-local 隐式串联并发 request。
- `WechatOcrAuditSink` 映射 `ocrBackendLocalProcess`；只有现有 `fallback_is_approved` 成功后的 local fallback start 可加 1。Windows Memory OCR 不计外部进程。
- 生产 `DiscardOcrAudit` 改为受控 sink 适配，但不记录 OCR result/body。

### 4.4 Upload queue spy

不把 WeChat 数据送进 `remote_upload.rs` 再观察失败。采用两层证据：

1. request-scoped `UploadQueueSpy` 作为测试能力 sink，M2 tail 没有 enqueue 方法；任何未来新增调用都让计数非 0 并失败。
2. 使用完全虚构 canary 运行内容留存/知识导入/M2 流程后，读取临时 Work Review DB 的既有 pending-upload 查询，并检查参数捕获：不存在 `wechat_reply/`、`knowledge.sqlite`、`-wal/-shm`、源目录、请求 UUID、hit/source opaque token、OCR/命中/建议 canary 或派生文件。全局 upload/MCP/Bot/Localhost/search 开关设为 true 仍保持此结果。

测试只读临时数据库和 fake queue，不读取用户 dataDir。

### 4.5 Error code 与前端显示

复用现有 `ContractError` 和 `errorDisplay.js`；仅在现有枚举无法区分证据写失败时增加一个稳定、非详细错误码。不得把 SQLite error text、模型 provider body、路径或配置秘密透传前端。Settings/Avatar 测试只验证安全文案、显式操作和旧功能不退化。

## 5. 核心逻辑详解

### 5.1 证据汇聚算法

1. 按 requestId 读取/接收 reply trace，拒绝 JSONL 中段损坏、重复 eventId、stageSeq 逆序和多终态。
2. 找唯一 `retrieving(stageSeq=4)` 与唯一 `generating(stageSeq=5,m2)`；将后者归一化为 `retrieval_completed`。
3. 对每个 transport attempt 校验：同 requestId、binding generation、stageSeq=5、context hash、model request id、bytes hash；attempt 序列必须为 `[1]` 或 `[1,2]`。
4. join embedding/OCR/capability/upload snapshots；缺少 required sink 不是 0，而是 `blocked`。只有显式存在的零值才是零调用证据。
5. 对检索错误 request 断言：无 generating m2 success event、无 permit/attempt、logical model request=0、唯一 failed/cancelled terminal、lease 可被下一 request 获取。
6. 对成功/no_hit request 断言：retrieval_calls=1、context_build_calls=1、logical model request=1；physical attempt 由实际结果决定。
7. 输出只含摘要的 evidence batch，计算 SHA-256；gate 引用路径和 hash，不复制原 trace 内容。

### 5.2 能力隔离策略

- 微信 M2 只注入 `revalidate/retrieve/model transport/audit` 四类能力；`M2ReplyTailPort` 不增加通用 AppState、HTTP client、Agent、upload、shell 或 Tauri command handle。
- 模型 transport 继续使用 `SingleTurnTextRequest`：一个 system + 一个 user，无 history/tools/tool_choice/function/action；tool-call response 只作为错误。
- embedding client 继续只接受已 pin 的 HTTP loopback；DNS 混合地址、redirect、非 loopback、云地址、endpoint 漂移均失败或按契约 FTS fallback，不可云回退。
- OCR 外部进程能力留在 `WechatOcrDispatcher` 私有 fallback；Avatar/Settings/资源解析模块没有获得该对象。
- 静态 verifier 检查 `wechat/**` 与 `knowledge/**` 的生产依赖中不新增 `remote_upload`、Bot、localhost_api、agent::tools、shell/process/input API；静态检查只作为调用图边界，不替代动态 counter。

### 5.3 并发与晚到结果

- 复用 runtime single-flight；并发第二个触发返回 `WX_BUSY` 且不创建 trace/model attempt。
- fault hooks 不使用进程全局 FIFO。步骤 24 已记录并行 hook 会交叉消费；本步骤把注入器绑定到单个 fake Store/port/request，或测试固定 `--test-threads=1` 仅用于无法移除的现有全局 hook，并在证据中标注。
- 模型 future 在 timeout/cancel 后必须被等待/隔离，晚到 reply 经 request/suggestion/binding generation 校验拒绝；不能发布、复制或覆盖新 request。
- 导入/索引 crash 使用子进程 checkpoint 测试，避免在同进程伪造 panic 后继续使用污染连接。

### 5.4 内容留存与来源重取

覆盖以下独立事实：

1. default config：retention off/days=0，不创建 `wechat_reply/content`；trace/audit 仍无正文。
2. enabled：只允许 Capture/OcrText/RetrievalExcerpt/Suggestion 固定文件名写入 UUID request dir；不接受调用者路径。
3. expiry：只删到期 UUID 目录，symlink/异常条目 fail-closed 并计 failed，不越界。
4. manual delete：全部删除与当前 request 删除分别验证；关闭留存时清除当前 request 既有正文。
5. source refetch failure：source retire/deny/delete/generation change 后明确 unavailable，不从 trace 快照返回旧正文。
6. no knowledge ingestion：运行内容留存后 knowledge catalog/message/chunk/count 不变；导入入口没有指向 content root 的能力。
7. no upload：上述文件及其相对路径不进入 pending upload 或 fake uploader。

### 5.5 桌宠/资源无害哨兵

哨兵由测试运行时在隔离临时目录生成，不加入生产资源、不进安装包：

- `sentinel.dll`：无效、不可执行的测试字节，不含第三方代码；任何模块加载尝试即失败并计数。
- `sentinel.cmd`/`sentinel.ps1`：仅在临时目录写一个 marker；无网络、注册表、系统目录或输入操作。
- `commands.json`：声明唯一 canary 命令名，产品 schema 不认识该字段。
- `urls.json`：声明不可路由的 `.invalid` URL canary，产品不得解析/访问。

自动化侧先验证 Avatar/资源 parser 忽略未知旁置文件、不枚举执行；Windows candidate 侧用受控观察器记录：canary 文件 open、加载模块、子进程、TCP/UDP、低级键鼠 hook 中带 injected flag 的事件。桌宠/资源 origin 五类计数均必须为 0。回复模型、loopback embedding、获准 OCR 以独立 origin/白名单计数，不能被归入桌宠零调用中抵消。

没有原生 Windows、候选安装包、观察工具版本和原始脱敏日志 hash 时，AC-PET 动态项为 `not-run/blocked`。

## 6. 非功能性设计

### 6.1 性能

- 每个 audit event 为小型固定结构，单 request 上限按阶段/attempt 固定；禁止正文确保不会随聊天长度增长。
- JSONL append 沿用现有单行上限和按日文件；collector 只读取当前证据批次，不常驻扫描全部历史。
- spy/audit 不改变检索 topK、FTS/vector 算法或性能 gate。本步骤只做正确性/隔离回归；真实规模 p50/p95/峰值内存仍由步骤 27 在冻结 Windows 环境复验。

### 6.2 高可用与降级

- audit/trace 在模型前写失败则 fail-closed，不能“无证据继续发模型”。
- embedding 只允许既有 FTS fallback；SQLite/context/binding/model 错误均不降级 M1。
- candidate 导入/索引失败保持旧 active pair；原子切换失败不改变 catalog。
- 原 Work Review 网络能力无凭据时运行 schema/mock/queue/error tests，不删入口、不假连通。

### 6.3 安全与隐私

- 所有 fixture 使用明显虚构 canary，不复制、读取、哈希真实聊天目录。
- secret scanner 至少覆盖 OpenAI/Anthropic/Gemini/AWS 常见 key 形状、Bearer/Authorization、Cookie、私钥头和项目约定 canary；命中时只报告文件/规则/摘要，不回显秘密。
- package scan 覆盖源码夹具、trace/evidence、截图目录、NSIS/zip/update payload 文件列表和解包内容；没有 candidate 包时记录 `not-run`，不能声称“安装包无数据”。
- 测试 URL 只使用 loopback 或 `.invalid`；不访问外网。

### 6.4 兼容性

- 保持 `wechat-m1`/`wechat-m2` feature 互斥与 compile-fail probes；普通 Work Review 默认构建不强制启用微信 feature。
- 前端 trace DTO 仍只暴露安全 summary；本步骤不把 capability 内部细节、API key、路径或 IDs 发给 Avatar/Settings。
- Windows-only observer 与 UAT 证据独立；macOS/Linux 继续运行平台无关 M2 tail/fake transport 测试。

### 6.5 回滚

- 新 audit sink/spy 通过私有构造接入，回滚可按第 9 节文件清单定向 revert；不得 `git reset --hard`，不得清理其他 run 的 dirty 文件。
- 回滚后必须复跑 M1/M2 feature 编译、现有 WeChat/knowledge tests、AC baseline verifier 和内容留存测试；不能以删除 strict gate 换取 pass。

## 9. 代码实施修改顺序

1. **冻结证据 schema 与 strict gate fixture**：先写 `verify_m2_observability_gate.py` 的 pass/fail/blocked 脱敏 fixture，固定必需 AC、能力 key、禁止 default-pass、缺 evidence 不能算 0。验证：删除任一 AC、counter 或 evidence hash 必须 fail/blocked。
2. **实现私有 metadata audit sink**：新增单一 observability/audit 模块，serde deny-unknown、字段/行长限制和 forbidden-field 测试。验证：正文/API key/path/内部 ID 无法进入 schema。
3. **接 model physical attempt**：在现有 `RagTransportAttempt` 最后一层记录 start/outcome，区分 logical request 与 physical attempts。验证：attempt 1/2、bytes hash、request/stage/context/model id 全匹配。
