## 1. 背景、目标和边界

步骤 15--18 已有只读 `wechat_archive_v1` 输入边界、独立 `knowledge.sqlite`、唯一 `KnowledgeStore`、源 lineage/导入 generation，以及流式 messages 导入。当前 `SettingsKnowledge.svelte` 仅显示配置里的 source 摘要，`get_knowledge_settings_status` 也没有读取 Store 事实；用户不能显式选择导出目录、看到本次导入状态、停止使用来源，或在不冒险覆盖现库的前提下重建派生库。

本步骤在既有“知识库”设置页补齐一个本地知识源管理区：用户显式选择一个导出目录，查看无正文/无路径的 source 清单和进度，退役/拒绝来源，并通过确认后的候选库安全重建。所有导入仍走同一个 `KnowledgeStore::import_wechat_json_archive` 门面和既有 `WechatJsonArchiveReadGuard`；不新增第二个 SQLite 所有者、目录扫描器、网络、上传、模型调用、检索实现、微信数据库/协议访问、OCR、输入自动化或自动发送。

本步骤不做：

- 不改变 `wechat_archive_v1` allow-list、no-follow、64 KiB 限制、`includeMedia=false` 或只读导出约束；目录选择不是“扫描微信目录”。
- 不把导出路径、导出名称、正文、联系人、消息 ID、媒体名或原始 manifest 放入配置、UI DTO、Toast、日志、测试断言或新 manifest。
- 不实现 embedding/chunk/retrieval，也不把未 ready 的候选暴露给 M2；M1 手动截图--建议--人工复制粘贴发送链路不变。
- 不做增量“猜测”、自动重导、后台定时导入、自动恢复未完成重建，或全局架构重构。

## 3. UI、状态和交互

### 3.1 设置页

在 `SettingsKnowledge.svelte` 的 scope/embedding 区块后增加“本地知识源”区域：

1. 初始加载和每次操作结束调用 `list_knowledge_sources`，与既有 `get_knowledge_settings_status` 一起刷新；加载中使用现有卡片内 loading 文案。
2. “选择导出目录并导入”按钮在非维护状态时调用 `openDialog({ directory: true, multiple: false })`。只把返回值立即作为本次 `start_knowledge_source_import` 参数；取消、空值或正在操作时直接返回。
3. 每行只显示 Store 返回的匿名 `sourceId` 短显示值、覆盖类型、`active/retired/missing/denied` 状态、导入阶段、匿名 lineage 数量、消息/会话计数和可安全显示的时间；绝不显示路径、导出 ID、account/conversation/message ID、hash 原值或正文。
4. 在本次导入/rebuild 期间，显示由 `get_knowledge_maintenance_status` 返回的阶段和已完成/总数计数；禁用选择、退役、拒绝和重建按钮，禁止重复提交。采用轮询（例如 500 ms--1 s）且组件销毁时停止；不为此新增全局事件总线或后台任务。
5. “退役来源”使用 warning 确认框，说明它只会排除后续派生候选，既有 active snapshot 不会被静默替换；成功后 Toast 显示泛化成功文案并刷新。
6. “停止使用并拒绝”使用 error 确认框，明确会立即让受影响 active 视图 fail-closed，直到用户显式完成安全重建；调用前端不得传自由文本 reason，后端使用固定 reason 枚举。成功后刷新，页面显示 `KB_NOT_READY`，不显示旧内容。
7. “安全重建派生库”仅在没有维护任务且至少有可用、未 retired/denied/missing 的 source manifest 时可点；确认框说明必须重新用用户本次选择的导出目录建立完整候选，期间知识检索不可用、失败保留旧库。实际选择采用一次 `openDialog({ directory: true, multiple: true })`；用户取消不改变任何状态。

重建操作不自动使用历史源路径：本地存储中不保存路径，用户必须重新选择目录。每一个选择仍经过 importer 的 manifest 身份匹配和只读 guard；不匹配、重复、不足或任何一个导入失败，整体候选失败，旧 `knowledge.sqlite` 保持不变。

### 3.2 状态模型

前端只消费以下 DTO 枚举，不自行根据文案推断状态：

| 层级 | 值 | 含义 |
| --- | --- | --- |
| source state | `active` | 允许参与下一次候选合并。 |
|  | `retired` | 用户已停止未来派生使用；保留 lineage/immutable 审计，当前 active 不因该操作被偷偷改写。 |
|  | `missing` | 仅当用户本次显式选择并核验该已知 source 时不可读/manifest 不匹配；不在后台探测历史路径。 |
|  | `denied` | 用户已确认禁止使用；任何关联 active snapshot 必须不可读。 |
| operation | `idle/importing/rebuilding/failed` | 单一 Store 维护槽的摘要，不携带路径和错误原文。 |
| maintenance | `open/closed` | `closed` 时只允许清单/状态读取；写入、激活和 active read 均 fail-closed 为现有 `KB_NOT_READY` 或新增稳定 `KB_MAINTENANCE`。 |

`missing` 不等于自动删除，也不修改旧 snapshot；`retired` 不等于 denial；`denied` 的安全优先级最高。对 `denied` source 的 read 必须被拒绝，即使旧 index 仍可在磁盘上找到；不得以“其他 source 仍可用”为由返回混合旧快照。

## 4. 后端门面、维护屏障与数据规则

### 4.1 最小 command/DTO

在 `knowledge/commands.rs` 添加最小命令，注册在现有 `main.rs` invoke handler：

```text
list_knowledge_sources() -> KnowledgeSourcesStatus
start_knowledge_source_import({ selectedRoot }) -> KnowledgeOperationReceipt
get_knowledge_maintenance_status({ operationId }) -> KnowledgeOperationStatus
retire_knowledge_source({ sourceId }) -> KnowledgeMutationReceipt
deny_knowledge_source({ sourceId }) -> KnowledgeMutationReceipt
start_knowledge_rebuild({ selectedRoots }) -> KnowledgeOperationReceipt
```

- `selectedRoot(s)` 是 plugin dialog 当次返回的内部参数，只在 command 调用栈和 worker 中存活；command 先做数量/非空/重复值检查，随后把所有文件访问交给现有 Store/Importer，绝不记录、回传或写入 `AppConfig`。
- `sourceId` 必须是 Store 先前发出的 opaque ID；Store 在同一事务验证其存在及可转换状态。未知、已 denied、并发维护、重复 operation 或 malformed input 统一返回受控错误码。
- `KnowledgeSourcesStatus`/`KnowledgeOperationStatus` 只含固定枚举、opaque operation/source ID、计数、schema/version、时间和受控错误码；错误摘要没有 OS 路径、`rusqlite` 原文、manifest 文本或消息正文。
- 同时把 `get_knowledge_settings_status` 改为组合 Store 可用性、维护状态和红acted source 统计，而不是以 config 数组判断 ready；scope/loopback embedding 校验仍复用现有函数。

长操作在 command 内用 Tauri 的 blocking worker 启动，立即返回 operation receipt；worker 只持有 Store 的内部维护 lease。UI 只能查询状态，不能伪造完成或触发 activation。Store 不在 writer mutex 内解析 archive 文件；仅每批 SQL/状态切换时短事务持锁，沿用现有流式 256 批写入策略。

### 4.2 同一 Store 的维护屏障

`KnowledgeStore` 增加私有的 operation/maintenance state（一个进程内互斥 lease）；对任何导入、retire、deny、rebuild 先取得该 lease。保持 reader factory 和现有 writer 为 Store 内部实现，不向 command 暴露连接或数据库路径。

1. 导入：lease 为 `importing`，解析/写 staging 时不允许第二个写操作；只有 importer 的完整 audit、candidate/index/activation 既有检查均通过才更新清单。失败调用既有 `discard_stagings`/`discard_source_candidates`，并标记受控失败码。
2. 退役/拒绝：lease 内完成单个短事务。退役仅改变该 source 的 future eligibility；拒绝写 denial、使受影响 catalog/index 不可读，并在同一事务写入 manifest 状态。读取 API 在 maintenance `closed` 或存在相关 denial 时必须 fail-closed。
3. 重建：先关闭 maintenance 并停接新 writer/reader；尚未完成的 reader 在有限 timeout 后失败，而不是强行杀线程。任何 timeout/busy/完整性失败取消本次候选，旧库继续作为未交换文件存在；前端只能看到失败码。重建期间 `read_active_snapshot` 不返回内容。
4. 进程异常：内存 lease 丢失后，启动时不会接续、激活或删除遗留重建目录；只把主库按既有 migration/integrity 规则打开。遗留候选没有受验证 manifest 时不可读，需用户重新触发。

### 4.3 安全重建和 manifest

重建不原地清空 `knowledge.sqlite`：

1. 在同一 `wechat_knowledge/` 根内创建受 Store 私有 UUID 命名的候选目录和候选 SQLite；它使用同一 migration runner/Store 门面，只接收本次 dialog 选择且通过 `WechatArchiveReadGuard` 的目录。
2. 按已有 deterministic source-set/lineage/generation 规则导入全部选中来源，构建 ready index，执行 `foreign_key_check`、`integrity_check`、schema head、catalog/index/member 计数和 source-set snapshot 校验。任何 source 为 missing/denied/retired 或任一检查失败都不得形成可交换候选。
3. 为候选写临时 `knowledge.sqlite.manifest.json`，内容只包括 manifest format/schema head、candidate catalog sequence/snapshot hash、匿名 source ID/状态、coverage、计数、受控的 lineage digest 和时间；不含源路径、绝对路径、正文、真实导出 ID、媒体路径或原始 hash。写后 reopen 校验其与候选 SQLite 一致。
4. 仅在所有连接关闭、候选 SQLite 和 manifest 均再次校验成功后，Store 用同目录原子 rename 交换为主库，并保留一个受限权限的前一主库备份及对应 manifest，供受控 rollback；先完成新主库/manifest 成对落盘，再允许打开 reader。不能保证原子交换的平台直接失败，绝不 copy-overwrite 原库。
5. 交换后 reopen 新主库，重复完整性/manifest 匹配检查；失败则切回保留的旧对并保持 `KB_NOT_READY`，不宣称重建成功。旧备份的保留/清理策略不在本步骤自动执行，避免无授权删除用户派生数据。

普通单源导入后也由 Store 原子更新同一受限 manifest；manifest 是派生库一致性摘要，不是导出包副本，不能被 UI 用来恢复路径或绕过重新选择。

## 6. 验收与测试

所有测试使用手写、脱敏 `wechat_archive_v1` fixture 和临时数据目录：

- Given 用户取消目录对话框，When 点击导入或重建，Then 不调用导入/rebuild command、不改变 config/Store、没有成功 Toast。
- Given 一个合法 synthetic 导出，When 用户显式选择并导入，Then 全程经过 `KnowledgeStore` + 现有 read guard，UI 只显示 redacted DTO，且无路径/正文进入 status、配置、Toast 或日志。
- Given 正在导入或重建，When 再次点击任意写操作或请求 active snapshot，Then 写操作被禁用/后端拒绝，active read fail-closed；正常完成后状态恢复 `idle`。
- Given active source，When 退役，Then 它不参与下一 candidate，现有 lineage/version 仍审计可见，当前 active snapshot 未被静默交换。
- Given active source，When 用户确认拒绝，Then Store 写受控 denial、相关 active read 立即为 `KB_NOT_READY`/`KB_MAINTENANCE`，而不是返回旧 index 内容；未知/已 denied source 不能重复改变状态。
- Given 用户重新选择全部有效来源，When rebuild 任一 source 失败、DB busy、migration/integrity/foreign-key/manifest 校验失败或进程中断，Then 原 `knowledge.sqlite` 与旧 manifest 字节/内容保持可验证不变，候选绝不可读且不自动恢复。
- Given 完整候选，When rebuild 成功，Then 新 SQLite 与 manifest 成对匹配、source set/hash/计数一致、旧对作为备份保留，且恢复 reader 后只能读取新 ready catalog。
- Given historical source path 已不存在，When 用户未重新选择目录，Then 不进行任何探测；When 用户显式选择但校验失败，Then 仅标为 `missing` 并返回泛化码，不保存该路径。
- 定向检查包括相关 Rust unit tests、Svelte/Node settings test、`python3 -B kaifa/kaifa_test/verify_knowledge_source_management.py`、相关文件 `rustfmt --check` 与 `git diff --check`。测试通过不构成真实微信导出、Windows UAT、模型/检索或自动发送的证明。

## 7. 回滚、风险和待确认项

- 本步骤的发布回滚仅撤销其独立代码提交；不得删除用户 `wechat_knowledge/`、候选或备份文件。运行时异常、迁移失败、manifest 不一致及锁冲突一律关闭知识读取并保留可恢复旧对。
- 最大风险是“重建”被误解成可从数据库恢复原始导出。设计明确要求每次重建重新显式选择源目录；数据库/manifest 都不保存路径，因此不会扩大本地文件访问能力。
- 若 Windows 文件系统不能为 SQLite+manifest 提供同目录安全交换语义，功能返回 `KB_REBUILD_UNSUPPORTED`，保留旧库；不得以删除后复制替代。
- 需在 phase 2 实作前确认：单个 `sourceId` 的 denial 是否应精确失活关联会话还是按当前既有 `knowledge_denials` 全局 fail-closed。默认按更安全的全局 fail-closed 落地，待后续有完整 target-aware active-snapshot 查询和回归测试时再收窄，不能在本步骤猜测性放宽。
