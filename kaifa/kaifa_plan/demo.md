

# 代码开发技术方案模板



## 0. 方案设计原则（自检清单）
- **谁来做都不走样**：依赖关系、边界清晰。
- **代码怎么写**：接口、模型、关键算法都已明确。
- **出了问题怎么办**：异常、补偿、降级、回滚都设计好。
- **如何验证成功**：测试方案、监控指标、上线标准明确。

## 1. 背景与目标
> *拒绝空泛，必须定出可量化、可验收的目标。*

- **业务背景**：为什么要做这个模块？
- **业务目标**：（例）“用户下单到支付转化率提升2%”
- **技术目标（必须可量化）**：
  - 性能：接口P99延迟 < 200ms，支持 5000 QPS
  - 一致性：订单状态不能出现中间态
  - 可用性：模块需独立部署，不影响核心交易链路

## 2. 核心业务流程与边界
> *用“图+文字”清晰定义模块职责，明确输入、输出和异常分流。*

- **系统上下文图/架构图**：标注模块与上下游（上游依赖谁，下游提供给谁）。
- **核心业务流程图/时序图**：至少包含以下三种流程，每一步需标注**调用的接口名**、**关键参数**、**异常处理**：
  - **正常流程**
  - **核心异常流程**（如库存不足、支付超时）
  - **补偿流程**（如何回滚、如何重试）
- **功能边界**：明确本模块不做什么。

## 3. 数据模型设计
> *直接给出可执行的 DDL 与缓存结构，并说明理由。*

- **数据库设计（给出完整 DDL）**
  ```sql
  CREATE TABLE order (
    id bigint PRIMARY KEY,
    user_id bigint NOT NULL,
    status tinyint NOT NULL DEFAULT 0,
    created_at datetime NOT NULL,
    INDEX idx_user_create (user_id, created_at) -- 说明索引用途：用户订单列表分页
  );
  ```
  - **分库分表策略**：分片键、分片算法、数据量预估及归档方案。
  
- **缓存设计**
  - **缓存结构**：`order:detail:{orderId} → JSON`
  - **策略**：过期策略（TTL / 主动失效）、更新策略（Cache Aside / Write Through）。
  - **高可用**：热点数据防击穿/雪崩方案（如互斥锁、逻辑过期）。

## 4. 接口定义（API 契约）
> *准生产级别定义，附完整错误码，下游/前端可据此并行开发。*

- **接口规范格式**：OpenAPI 3.0 / Protobuf（gRPC）
- **接口示例**：
  ```yaml
  POST /api/v1/orders
  Request:
  {
    "user_id": 12345,
    "items": [{"sku_id": "A001", "quantity": 2}],
    "coupon_id": "C100"
  }
  Response 200:
  {
    "code": 0,
    "message": "success",
    "data": {"order_id": 98765, "status": "PENDING"}
  }
  Error Codes:
  - 1001: 库存不足
  - 1002: 优惠券已失效
  ```
- **安全策略**：身份认证、权限控制、数据加密、输入校验（如JSR303）。

## 5. 核心逻辑详解
> *方案的灵魂。把技术难点拆解到“伪代码级”实现步骤。*

- **复杂逻辑实现方式**：
  - **选型与原理**：如使用 RocketMQ 事务消息 + 本地消息表保证最终一致性。
  - **详细执行步骤**：
    1. 发送半消息到MQ。
    2. 执行本地事务（创建订单、扣减库存）。
    3. 事务结果提交/回查MQ。
    4. 消费方执行并回调。
  - **补偿与异常处理**：消费失败重试策略、订单超时取消解冻库存（延迟队列/定时任务）的全流程。

## 6. 非功能性设计
> *禁止只写“高性能”，要给出具体实施方案。*

- **性能**：哪些走缓存、缓存穿透处理（布隆过滤器）、线程池与队列配置、批量SQL合并。
- **高可用与降级**：依赖中间件挂掉的表现与降级方案；通过配置中心（如Apollo）动态下发的降级开关配置示例。
- **可扩展性**：业务流程中使用策略/责任链模式的点，并给定接口定义。
- **安全**：SQL注入防护（MyBatis `#{}`）、敏感字段AES-256加密及脱敏。
