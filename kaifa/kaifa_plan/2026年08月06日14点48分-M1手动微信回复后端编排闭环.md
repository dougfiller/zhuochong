# 步骤 11：M1 手动微信回复后端编排闭环

> 文档状态：实施前技术方案（仅方案设计）  
> dispatch：`aich8-zhuochong-desktop-pet-rag-27-steps-20260805-task-11`  
> LOOF run：`20260806-步骤-11-m1-手动微信回复后端编排闭环-dispatch_idaich8-task-11`

## 0. 方案设计原则

- **只接线，不重造组件**：复用步骤 6—10 已有的 `WechatReplyRuntime`、`CaptureCoordinator`、临时隐藏/截图、`WechatOcrDispatcher`、`M1ReplyInput` 和私有 `WechatReplyModelClient`；新代码只负责将它们按 M1 状态机串联。
- **M1 与 M2 严格隔离**：本步只在 `wechat-m1` 下编译；不调用 `knowledge`、`RetrievedReply`、`ModelKnowledgeContext` 或任何 `KB_*` 流程，也不写入 M2 trace metadata。
- **无微信操作**：只读前台窗口证据、内存截图和 OCR 文本；不激活/聚焦/点击/滚动微信，不输入、复制、粘贴或发送消息，不读取微信数据库、协议或导出文件。
- **先释放锁，再 await**：从 `AppState` 仅复制配置、profile、`ScreenshotService` 和 `data_dir`；整个截图、OCR、模型调用期间都不持有 `AppState` 或 runtime mutex。
- **不越过步骤 12**：本步产出受限的内部 `GeneratedReply`，供后续 `AvatarPresenter` 边界消费；不新增 Tauri command、Svelte UI、气泡展示、复制/关闭按钮或持久建议。

## 1. 背景、目标与边界

### 1.1 当前事实

1. `runtime.rs` 已有 single-flight lease、严格 `stageSeq`、metadata-only trace、`record_model_transport_call()`、`complete_generated_reply()` 与模型失败终态；步骤 10 已将 M1 客户端接到 runtime 的私有生成方法。
2. `capture_foreground_wechat()` 已做前台复核、窗口隐藏恢复、内存截图、ROI 裁剪、超时/取消等待；`ocr.rs` 只接受裁剪后的 `chat_rgba` 并在 `Text` 时构造 `OcrReadyReply`。
3. 现有 capture 返回时自行创建 `RequestId`，而 runtime 的 `begin_reply()` 也创建 lease `RequestId`；两者不能在正式编排中并存，否则 OCR 输入与 active lease 失配。这是本步必须消除的唯一接线缺口。
4. 项目现有 `avatar_engine::AvatarBubblePayload` 是 Work Review 气泡设施，但尚不存在 `AvatarPresenter`；按总计划，持久气泡、复制/关闭和代际显示属于步骤 12，不在此提前接入。

### 1.2 可验收目标

在一次未来显式调用可进入的**内部** M1 门面中，完成下列闭环：

`Validating → Capturing → Ocr → Generating → ReplyReady`

- 所有成功阶段属于同一个 `ReplyLease.request_id`；成功截图得到的 `capture_version` 从 `Ocr` 阶段起写入既有 trace。
- 仅当单聊 OCR 返回 `Text` 时才构造 `M1ReplyInput`，随后最多发生一次模型 transport；成功仅经 `complete_generated_reply()` 进入 `ReplyReady`。
- 前台/布局、截图、OCR、过期/cancel、模型配置和模型失败均为终态；这些路径模型调用数为 0（模型 transport 本身失败例外：恰为 1）。
- 返回的只是 `GeneratedReply`（文本和 request/suggestion generation）；不含截图、OCR 正文、窗口身份、路径、profile、密钥或检索信息。

### 1.3 非目标

- 不做倒计时、Tauri command 注册、自动触发/监听、UI 或用户可操作的纵向闭环；显式触发入口和展示交互留给后续授权步骤。
- 不修改 `desktop/src/`、`main.rs` 的 invoke handler、普通 Work Review 截图循环、Agent/orchestrator、模型 provider、配置结构、数据库、知识库、导入/检索或 `AvatarBubblePayload`。
- 不新增模型 fallback、重试、排队、流式输出、历史上下文、OCR 文件落盘、trace 正文、网络/上传能力。

## 3. 内部接口与流程

### 3.1 门面接口

新增 crate-private 函数（命名可随现有风格微调，契约不变）：

```rust
#[cfg(feature = "wechat-m1")]
pub(crate) async fn generate_wechat_reply(
    app: tauri::AppHandle,
    state: Arc<Mutex<AppState>>,
    runtime: &WechatReplyRuntime,
    coordinator: &CaptureCoordinator,
) -> Result<GeneratedReply, ContractError>;
```

- 它不是 `#[tauri::command]`，不接收前端 DTO，也不 emit 气泡。
- 先在一次短锁内复制 `WechatConfig`、`text_model_profiles`、`screenshot_service` 和 `data_dir`；`ReplyTraceStore::new(data_dir)` 随后可在锁外创建。
- 使用固定 M1 `BeginReplySnapshot`（`ReplyMode::M1`、零值/既有约定的 binding 与 observation、有限超时、初始 `capture_version: None`）。函数无外部裸文本参数。

### 3.2 正常时序

```mermaid
sequenceDiagram
  participant F as reply_flow private facade
  participant R as WechatReplyRuntime
  participant C as CaptureCoordinator/capture
  participant O as WechatOcrDispatcher
  participant M as WechatReplyModelClient
  participant A as future AvatarPresenter

  F->>R: begin_reply(M1, trace) => ReplyLease
  F->>R: validate foreground; transition Validating->Capturing
  F->>C: guarded capture(lease.request_id, cancellation)
  C-->>F: verified slices + captureVersion
  F->>R: bind version; transition Capturing->Ocr
  F->>O: recognize(chat RGBA only) => OcrReadyReply
  F->>R: transition Ocr->Generating
  F->>R: generate_m1_reply(config snapshot, M1ReplyInput, lease)
  R->>M: exactly one no-tools transport
  M-->>R: GeneratedReply
  R-->>F: ReplyReady
  F-->>A: bounded GeneratedReply only
```

实施必须按以下顺序处理：

1. `begin_reply()` 先创建唯一 lease，并取得 cancellation receiver；busy 直接返回 `WX_BUSY`，不创建第二个请求或排队。
2. `validate_foreground_wechat()` 成功后才写 `Validating → Capturing`；任何前台、profile、平台或取消/超时错误写合法终态并 `finish_reply()`。
3. capture API 改为接收 `lease.request_id().clone()`，且在 guard 恢复、二次窗口复核和 ROI 成功后才分配 `capture_version`；返回的 slices/request id 必须与 lease 相等。不得保留当前 capture 自建 request id 的路径。
4. runtime 用受限 helper 在 active 为 `Capturing` 时写入该 `capture_version` 并提交 `Ocr` trace；这一步既校验版本，又禁止在捕获失败后伪造 OCR stage。
5. 用 `CapturedWechat { request_id, capture_version, is_single_chat: true, .. }` 调用既有 dispatcher。header 仅用于 capture 身份复核，不进入 OCR；OCR audit sink 只接受现有无正文 metadata。`Text` 以外结果先将 `Ocr → Failed(error)` 写 trace，再释放 slot，绝不构造 `M1ReplyInput`。
6. OCR 成功后检查 `CaptureCoordinator::is_current_capture(capture_version)` 和 lease 未取消，再写 `Ocr → Generating`；然后将 `OcrReadyReply` 唯一转换为 `M1ReplyInput`。
7. 调用已有 `runtime.generate_m1_reply(config, profiles, input, lease)`。它已负责：无效 profile 零 transport、记录一次调用、await 时不锁 runtime、成功提交 `ReplyReady`、失败写稳定 `LLM_FAILED` 并释放 slot。门面不得再次计数、调用 client 或伪造 `GeneratedReply`。
8. 成功后只返回 `GeneratedReply`；调用者/后续步骤负责消费并最终 `finish_reply()`。本步的内部门面在没有 presenter 的情况下不得调用 `emit_avatar_bubble()`。

### 3.3 终态与补偿

| 阶段/条件 | 处理 | 模型调用数 |
| --- | --- | --- |
| busy、非 Windows、非微信/不支持布局、取消、capture timeout/失败 | 写 `Cancelled` 或 `Failed` 的稳定错误，guard 已恢复后释放 lease | 0 |
| OCR empty/unavailable/failed、群聊、capture version 过期 | `Ocr → Failed`，不创建 `M1ReplyInput` | 0 |
| profile 无效 | 进入 `Generating` 后由 runtime 写 `WX_TEXT_MODEL_UNAVAILABLE` 并释放 | 0 |
| transport/空白/超限回复失败 | runtime 写 `LLM_FAILED` 并释放 | 1 |
| client 成功但 lease/cancel/capture/generation 已失效 | `complete_generated_reply()` 拒绝或记录 stale，不返回可展示结果 | 1 |
| 成功 `ReplyReady` | 返回 `GeneratedReply`，由下一步 presenter 完成显示、copy/dismiss 再结束请求 | 1 |

不做重试、补偿性再次截图或模型 fallback；用户之后重新显式触发才是新的 request/lease。

## 4. 数据、隐私与安全

- 不新增数据库、DDL、配置项、持久化正文或前端 API。既有 trace 保持只存 request/stage/generation/call count/error/capture version 等 metadata。
- 截图帧、ROI RGBA、窗口身份和 OCR 文本均为函数内存对象；唯一可能的留存仍受既有 runtime content API 与配置控制，本步不调用其 OCR/建议正文写入路径。
- 返回 `GeneratedReply` 前不附加 profile、endpoint、原始 provider error、OCR、图片或 `WechatWindowIdentity`；错误面只使用 `ContractError` 稳定码。
- 静态审计应确认没有新增 `#[tauri::command]`、`emit_avatar_bubble`、clipboard、input automation、UI Automation、Win32 激活、微信协议/数据库、HTTP upload、MCP/Bot/Agent 调用。

## 5. 实施顺序

1. 先写 reply-flow fake ports 的失败/成功测试，明确期望 stage 顺序、request id 一致性和 call count。
2. 最小调整 capture/runtime 的 request-id 与 capture-version hand-off；保留现有 guard、worker join、二次 foreground revalidate 和 state-machine 规则。
3. 新增 `reply_flow.rs`，只用现有 `WechatOcrDispatcher`、`M1ReplyInput` 与 `generate_m1_reply`。
4. 将 module 限定在 `wechat-m1`，不修改 command 注册和前端。
5. 跑定向 fake 测试、M1 feature 编译和静态范围门禁；如格式工具不可用，按事实记录而不触碰范围外历史格式。

## 6. 测试与验收

| 场景 | 验证点 |
| --- | --- |
| 正常 M1 fake 流程 | trace 顺序严格为 Validating/Capturing/Ocr/Generating/ReplyReady；lease、slices、OCR 输入 request id 相同；模型恰 1 次；返回仅为 current `GeneratedReply`。 |
| 前台/布局/capture 失败 | 写失败或取消终态；窗口 guard 恢复；OCR/model 均为 0。 |
| OCR Empty/Unavailable/Failed、群聊 | 无 `M1ReplyInput`，模型 0，trace 含稳定 OCR/群聊错误。 |
| 无效 profile | runtime 记录 `WX_TEXT_MODEL_UNAVAILABLE` 后释放；fake model 0。 |
| transport 失败、空白/超限 | fake model 1；`LLM_FAILED` 终态；后续可取得新 lease。 |
| 取消、超时、版本/lease 不匹配 | 晚到结果不进入 `ReplyReady`，不泄露文本，不覆盖新请求。 |
| feature/范围 | `wechat-m1` 可编译；M2 build 不引用 reply flow；无 command/UI/微信自动操作/知识库依赖。 |

## 7. 风险、回滚与后续

| 风险 | 控制 |
| --- | --- |
| capture 与 runtime 分别创建 request id | capture 改为使用 lease id，并在单测中断言一致；不匹配即 fail closed。 |
| OCR helper 绕开 runtime trace | reply flow 只能通过 runtime transition 推进/终止；不让调用方持有独立 `StateMachine`。 |
| 提前把生成结果显示或复制 | 本步只返回内部 `GeneratedReply`，展示和交互留给步骤 12。 |
| 旧回调覆盖新请求 | 继续由 lease、suggestion generation、capture version、cancel/timeout 和 `complete_generated_reply()` 拒绝。 |
| scope 扩大为 M2/RAG 或微信控制 | `reply_flow` 仅编译进 M1，不导入 knowledge，也不接触输入/发送 API。 |

回滚仅移除 `reply_flow.rs` 及本步针对 `wechat/mod.rs`、`runtime.rs`、必要 capture hand-off 和测试的差异；不得回退步骤 6—10 的 capture/OCR/model/runtime 契约、删除 trace/content 数据或修改其他 LOOF 产物。步骤 11 完成只代表私有 M1 后端编排可被后续显式入口消费，不代表用户可点击、复制、粘贴、发送、真实 Windows 兼容性或 M2 RAG 已完成。
