## 1. 改动目标

- 在 `wechat-m1` 内完成 `Validating → Capturing → Ocr → Generating → ReplyReady` 的私有后端接线。
- 让 capture、OCR 和模型生成共用同一 `ReplyLease.request_id`，且 capture version 在 OCR trace 前原子绑定。

## 2. 改动背景与基准

步骤 6—10 已提供受限 capture、OCR dispatcher、runtime 和 M1 model client，但 capture 会自行生成 request id，不能直接进入 runtime lease。此次只收敛该接线缺口，不新增用户触发入口或展示行为。

## 3. 改动范围

### 3.1 涉及范围

- 新增 `desktop/src-tauri/src/wechat/reply_flow.rs`：M1 私有门面、快照、失败终态释放和内存 OCR 编排。
- 修改 `desktop/src-tauri/src/wechat/runtime.rs`：capture 接收 lease request id；原子写入 capture version 并进入 OCR；新增定向 handoff 测试。
- 修改 `desktop/src-tauri/src/wechat/mod.rs`：仅在 `wechat-m1` 声明 reply flow。
- 新增 `kaifa/kaifa_test/verify_wechat_reply_flow.py` 及相应命令/测试补录。

### 3.2 不涉及范围

- 不修改 Tauri command、Svelte、main invoke handler、气泡展示、复制/关闭、持久建议、微信输入/发送、数据库、上传、M2/RAG 或知识库流程。

## 5. 处理流程或行为变化

`begin_reply` 建立唯一 lease 后，门面只在短锁内复制配置、模型 profile、截图服务和数据目录。前台校验成功才进入 capture；guarded capture 使用 lease id，成功后才分配 version。runtime 原子记录 version 并进入 OCR；仅 OCR `Text` 能转为 `M1ReplyInput`。过期、取消、capture 或 OCR 失败均终态并释放 slot；生成仅委托既有 runtime，最多一次 transport。

## 6. 输入、输出与接口变化

- 新增 crate-private `generate_wechat_reply(...) -> Result<GeneratedReply, ContractError>`，不是 Tauri command，未接收前端文本或 DTO。
- `capture_foreground_wechat` 仅供内部调用，改为接收 lease 的 `RequestId` 和已校验 identity；不持久化截图或 OCR 正文。

## 7. 文件与目录变更

见第 4 节；未创建数据库、配置、前端目录或业务数据文件。

## 8. 关键设计决策

### 8.1 capture request id 由 runtime lease 提供

避免 capture 自建 request 和 active lease 不一致，OCR input、trace 和生成都可由同一 capability 验证。

### 8.2 M1 门面只在 feature 内部存在

模块受 `wechat-m1` gate 保护，未注册 command；M2 构建不会引用该文件，保持 M1/M2 隔离。
