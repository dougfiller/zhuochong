## 1. 改动目标

- 在 chunk/FTS 写入前原子冻结完整 `conversation -> import generation` 映射、embedding 身份、token 预算和 schema 版本。
- 在单一会话内按稳定消息顺序生成确定性 chunk，并在同一事务写入 chunk、member version 与 FTS5 文档。
- 活动查询只允许 catalog 指向的 `ready` index generation，并在 SQL 内限制显式稳定会话 scope、时间和 topK。
- 本步骤不生成 embedding、不把 building 标为 ready、不激活 import generation，也不接入 UI/M2 最终检索链路。

## 2. 改动背景与基准

### 2.1 改动前状态

schema head 为 3；已有 import generation、规范化消息和预留 chunk/FTS 表，但缺少冻结 builder、member version/index、chunk 顺序/预算字段及活动代际隔离查询。

### 2.2 本次基于的版本或状态

基于 `main` 的 `a5aefcb`。工作区存在其他 LOOF run 的未提交改动，本阶段只修改步骤 20 明确列出的知识模块、测试和 kaifa 文档，未清理或覆盖其他改动。

### 2.3 改动原因

步骤 21 的本地向量生成和步骤 22 的原子激活需要一个可恢复、配置不可漂移、内容与 scope 可审计的 building index generation。

## 4. 详细改动清单

- `0004_candidate_index_chunks_fts.sql`：增加冻结字段、building 唯一索引、chunk 顺序/时间/token/count、direction 及 version-aware member 表。
- `migrations.rs`：schema head 升至 4；加入 v3 member preflight、v4 执行及 chunk/member/FTS/embedding 一致性校验。

## 5. 处理流程或行为变化

`ready_candidate/active imports` → 原子选择与 snapshot hash → `building index + complete mapping` → 稳定会话分页 → 纯分块/预分词 → chunk/member/FTS 同 batch 事务。查询从 catalog active pointer 开始，只有 `ready` 且位于显式 stable scope 的 chunk 可见。

## 6. 输入、输出与接口变化

- 新输入：`FrozenIndexBuildSpec`，固定 chunk/token 版本、256—4096 retrieval budget、loopback embedding provider/endpoint/model/fingerprint/dimension。
- 新输出：`FrozenIndexBuild`、`BuildMessagePage`、`ChunkDraft` 和 `FtsHit`。
- 错误保持现有契约：配置/映射/输入不可发布返回 `KB_NOT_READY`，scope 非法返回 `KB_SCOPE_UNRESOLVED`，查询参数/SQLite 查询失败返回 `KB_RETRIEVAL_FAILED`。

## 8. 关键设计决策

### 8.1 snapshot 只使用稳定事实

hash 输入为稳定账户/会话键、source-set hash、稳定 message identity 与 content hash；opaque UUID、当前时间和 SQLite 默认行序不参与。

### 8.2 预分词复用 bundled FTS5

连续 CJK 生成 2/3-gram，ASCII letter/digit 转小写并保留完整 term；索引和 query 使用同一函数，query term 被逐项 phrase 化并以 AND 组合，不执行用户提供的 FTS 语法。

### 8.3 building 与活动查询严格隔离

步骤 20 只写 building。活动查询必须经 catalog + ready join 和显式 scope CTE；不存在 `LIKE` 或全库后置过滤回退。
