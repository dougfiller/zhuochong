## 1. 改动目标

- 冻结后续微信 M1/M2 的请求、版本、OCR、知识范围、检索状态、模型输入和错误码契约。
- 以纯状态机和 feature 门禁消除旧建议、错误检索状态和 M1/M2 模型入口混用。
- 提供可查询验收矩阵和不含真实聊天内容的 fixture。

## 2. 改动背景与基准

### 2.1 改动前状态

`desktop/src-tauri/src/` 没有 `wechat/` 或 `knowledge/` 领域模块；默认 Work Review 产品构建不含微信/RAG 实现。

### 2.2 本次基于的版本或状态

基于 `main` 的变更前 HEAD `cf13654`。工作区原有其他 LOOF run 状态文件和调度文件未改动。

### 2.3 改动原因

在实施截图、OCR、知识库导入、检索、模型 transport 或 UI 前，先固定可编译且可测试的边界，避免 M2 绕过检索或旧代际结果被误用。

## 3. 改动范围

### 3.1 涉及范围

- 新增 `desktop/src-tauri/src/wechat/` 与 `knowledge/` 纯领域模块。
- 在 `main.rs` 声明模块，在 `Cargo.toml` 增加 M1/M2 release feature 和隔离的契约检查 feature。
- 新增验收矩阵、7 个虚构 JSON fixture，并补录命令与测试说明。

### 3.2 不涉及范围

- 不实现或注册 Tauri command、managed state、前端、托盘/桌宠入口。
- 不实现截图、OCR、剪贴板、UI Automation、模型 transport、网络、数据库、导入或检索。
- 不创建或访问 `knowledge.sqlite`，不读取、复制、哈希或提交真实聊天数据。

### 3.3 影响对象

后续 M1/M2 编排、检索和 Windows 实机步骤可复用这些类型与验收资产；当前用户可见产品行为不变。

## 5. 处理流程或行为变化

```text
OcrBackendResult::Text → OcrReadyReply → M1ReplyInput → generate_m1_reply（仅 wechat-m1）
OcrReadyReply → 后续 knowledge_retrieve → RetrievedReply（私有）
  → ModelKnowledgeContext（私有适配器） → generate_rag_reply（仅 wechat-m2）
```

M2 的状态只能经 `retrieving` 进入 `generating`；`no_hit` 是成功检索结果。任何 KB 错误不构造 `RetrievedReply`，因此没有 M2 模型调用资格。

## 6. 输入、输出与接口变化

- `KnowledgeScope` 的 JSON 固定为 `conversation`、`selected_conversations` 和 `global_user_selected` 三种判别形状。
- `WX_*`、`KB_*` 与 `LLM_FAILED` 使用显式 serde 枚举值，避免 Rust variant 改名影响 wire 协议。
- `wechat-m1` 与 `wechat-m2` 是互斥 release feature；`wechat-contract-check` 只用于验证“恰选一个”的发布契约，不改变默认产品构建。

## 8. 关键设计决策

### 8.1 用私有封装阻断 RAG 绕过

`RetrievedReply` 只能在 `knowledge` 模块内构造，`ModelKnowledgeContext` 只能由微信模型契约中的受信任适配器构造；模型输入没有完整命中、来源路径、内部 ID 或数据库句柄。

### 8.2 将发布契约从默认产品构建隔离

默认 Work Review 尚未发布微信功能，因此不强制选择 M1/M2。`wechat-contract-check` 仅在专项编译命令中启用，并对“零或双 feature”触发预期 `compile_error!`。

### 8.3 fixture 只表达契约

所有 fixture 采用虚构 UUID、稳定占位 ID 和通用文字；它们不模拟真实导入、不包含联系人/聊天记录/截图，也没有真实路径或来源哈希。
