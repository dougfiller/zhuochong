# 桌宠助手极简开发方案（v0.1）

> 初版日期：2026-08-03 20:35
> 简化修订：2026-08-04
> 对应需求基线：`最终需求文档.md` v0.1
> 本文只规定最快实现路线，不包含业务代码实现。

## 0. 结论

首个可运行产品直接以 `参考/Work-Review-main` 为代码底座，在同一套 Tauri 2 + Rust + Svelte 应用中增加微信回复功能，不开发临时壳，也不从零重建桌面应用。

本版本只交付一条链路：

```text
当前前台微信单聊
→ 用户手动触发
→ 现有截图能力截一次图
→ 固定坐标裁剪聊天区
→ Work Review 现有本地 OCR
→ Work Review 现有模型请求
→ 现有桌宠气泡显示一条建议
→ 用户点击复制并自行粘贴发送
```

除直接复用的 Work Review 代码外，新增部分只做最少胶水：一个 Rust 文件、一个 Tauri 命令、一个触发入口、一个复制按钮和一份 JSONL 记录。禁止为了后续功能预建通用层。

预计开发时间为 **3～6 个工作日**。该估算以 Work Review 能在目标 Windows 机器正常构建和运行、现有 Windows OCR 可用为前提。

## 1. 本次交付范围

### 1.1 必须完成

- 在目标 Windows 11 x64 机器启动 Work Review 派生应用和现有桌宠。
- 用户手动触发一次微信回复生成。
- 真正截图时只处理当前处于前台的微信单聊窗口。
- 对一种固定微信版本、主题、DPI、窗口尺寸和布局使用固定聊天区坐标；微信必须完整位于主显示器。
- 在本机完成 OCR，并在目标机器最终固定使用一个 OCR 实现。
- 使用 Work Review 已配置的一个模型生成一条中文建议。
- 在现有桌宠气泡中显示建议。
- 用户点击后复制建议；用户自行粘贴、修改和发送。
- 保存裁剪图，并向一个 `events.jsonl` 文件追加一行记录。

### 1.2 Work Review 原有模块

Work Review 的工作记录、时间线、日报、普通截图、远程上传、设置和其他已有功能原样保留。本次不整理、不拆分、不重写这些模块，也不把它们列为微信功能的新增验收项。

## 2. 参考代码复用清单

| 所需能力 | 直接复用位置 | 本次只做什么 |
| --- | --- | --- |
| 桌面应用外壳与打包 | `参考/Work-Review-main` | 复制为实际产品代码底座，沿用工程结构 |
| 前台窗口信息 | `src-tauri/src/monitor.rs` 的 `get_active_window` | 直接比较归一化后的 `app_name == "WeChat"` |
| 截图 | `src-tauri/src/screenshot.rs` 的 `ScreenshotService::capture_for_window` | 读取原始 PNG，按窗口矩形和固定比例裁剪 |
| 本地 OCR | `src-tauri/src/ocr.rs` 的 `OcrService::extract_text` | 读取裁剪图并取得纯文本 |
| 模型配置与请求 | `src-tauri/src/commands/ask.rs`、`commands/ai.rs` | 复用现有配置和一次文本生成调用 |
| 桌宠状态与气泡 | `src-tauri/src/avatar_engine.rs`、`src/routes/avatar/AvatarWindow.svelte` | 显示处理中、结果或失败信息 |
| 剪贴板交互 | 现有 Svelte/Tauri 前端能力 | 用户点击“复制”时写入建议正文 |
| 安装包 | Work Review 现有 Tauri 构建配置 | 生成目标 Windows 安装包 |

复用原则：

- 参考仓库只作为源，不直接在 `参考/` 目录中开发。
- 开始实现时，把 Work Review 复制到正式产品目录，例如 `desktop/`，然后在这份代码上直接修改。
- 能调用现有函数就调用，不复制一份再重写。
- 现有模块即使较复杂也保持原样；本次不花时间给它们“瘦身”。
- 不为现有代码补统一接口、统一错误码、统一配置或统一数据模型。

### 2.1 唯一备用 OCR

只有在目标 Windows 机器确认 Work Review 现有 OCR 无法工作时，才从 `参考/Umi-OCR-main` 搬运现成的 RapidOCR 可执行文件、模型和最短调用封装。

一旦选定可用方案就固定使用，不实现双后端切换、优先级、健康检查、适配器或结果对比。

### 2.2 本版本不使用的参考代码

`参考/Open-LLM-VTuber` 本版本不接入。其 ASR/TTS 后端只能在以后明确需要语音时再搬运一个具体实现；当前不为 Live2D、语音、摄像头或屏幕感知预留接口。

## 3. 最小代码改动设计

### 3.1 后端只增加一个文件

建议只新增一个后端文件：

```text
src-tauri/src/wechat_reply.rs
```

仍需在现有 `main.rs` 中增加一行模块声明和一行 Tauri 命令注册；“只增加一个文件”指只新建一个文件，不是禁止修改现有文件。

该文件直接完成以下顺序操作：

1. 检查当前是否已有请求在处理。
2. 获取当前前台窗口。
3. 直接判断归一化后的 `app_name == "WeChat"`。
4. 临时隐藏桌宠窗口和气泡，调用现有截图代码截一次图；无论成功或失败都立即恢复桌宠。
5. 读取 `ocr_source_path` 原始 PNG；微信限定在主显示器，先按窗口矩形裁出窗口，再按相对窗口的 `[left, top, right, bottom]` 四个 ROI 比例裁出聊天区并保存 PNG。
6. 调用现有 OCR 取得纯文本。
7. 用固定提示词调用现有模型请求。
8. 追加一行 JSONL。
9. 返回建议正文或一条简单错误文本。

裁剪完成后删除本次手动流程产生的整屏归档图和 OCR 临时源图，只留下聊天区裁剪图。

不把这九步拆成服务层、领域层、仓储层、适配器层或工作流引擎。

### 3.2 只增加一个 Tauri 命令

建议命令名：

```text
generate_wechat_reply
```

成功只需返回：

```text
screenshot_path
ocr_text
suggestion
```

失败直接返回可显示的字符串。无需专用错误码、错误枚举、请求取消接口或进度事件协议。

### 3.3 前端只改现有桌宠入口

- 在现有桌宠界面增加一个“生成回复”入口。
- 开发和验收前直接打开 Work Review 已有桌宠开关。
- 如果点击入口导致微信失去前台，先显示 2 秒倒计时，提醒用户切回微信。
- 请求期间禁用该入口并显示“生成中”。
- 成功后在持续气泡中显示建议和“复制”按钮，直到用户复制或主动关闭。
- 失败后显示一条错误，恢复入口。
- 不新增微信专用页面、路由、设置中心、调试面板或历史记录页。

### 3.4 运行时状态

新增状态只需要一个 `busy` 布尔值，防止用户连续触发。

不实现窗口绑定状态、聊天对象状态、会话键、代次、五元组、消息队列、任务调度、自动重试或恢复状态机。

## 4. 单次请求流程

```text
用户点击“生成回复”
        ↓
2 秒倒计时并切回微信（若需要）
        ↓
busy = true
        ↓
取得当前前台窗口并检查归一化应用名
        ↓
临时隐藏桌宠窗口和气泡
        ↓
现有截图能力截一次图
        ↓
立即恢复桌宠，读取 ocr_source_path 原始 PNG
        ↓
按主显示器中的窗口矩形和相对窗口固定 ROI 裁剪
        ↓
保存裁剪图
        ↓
现有本地 OCR 输出纯文本
        ↓
固定提示词调用一次现有模型
        ↓
现有桌宠气泡显示一条建议
        ↓
追加 events.jsonl
        ↓
busy = false
        ↓
用户点击复制并自行在微信发送
```

任一步失败：显示失败原因、写入失败结果、把 `busy` 设回 `false`，流程结束。没有自动重试或补偿流程。

固定提示词与需求基线保持一致：

```text
你是微信回复助手。根据以下当前可见微信单聊 OCR 文本，生成一条简短、自然、可以直接发送的中文回复。
只输出回复正文，不解释。

{ocr_text}
```

## 5. 最简数据保存

只保存两类文件：

```text
%LOCALAPPDATA%/Zhuochong/data/wechat/YYYY-MM-DD/HHMMSS.png
%LOCALAPPDATA%/Zhuochong/data/wechat/events.jsonl
```

JSONL 每行直接写：

```json
{"time":"...","window_title":"...","screenshot":"...","ocr_text":"...","suggestion":"...","result":"success"}
```

实现方式就是创建目录、保存 PNG、以追加模式写一行 JSON。开发调试阶段可以先完成闭环再补这一步。

本版本不增加 SQLite 表，不实现内容寻址、引用计数、事务编排、配额、自动清理、到期任务、删除审计、孤儿文件修复或微信记录上传。

## 6. 实施顺序与工期

| 顺序 | 工作 | 预计时间 | 完成标志 |
| --- | --- | ---: | --- |
| 1 | 复制 Work Review，在目标 Windows 跑通，启用桌宠并配置可用模型 | 0.5～1 天 | 应用、桌宠和一次模型测试可用 |
| 2 | 增加手动入口、前台微信检查、截图与固定 ROI 裁剪 | 1～2 天 | 能得到正确聊天区 PNG |
| 3 | 接通现有 OCR、现有模型、气泡和复制 | 1～2 天 | 完整建议链路可操作 |
| 4 | 增加 JSONL，生成安装包并在一台机器手工验收 | 0.5～1 天 | AC-01～AC-06 通过 |

总计：**3～6 个工作日**。

若第 1 步发现 Work Review 本身无法在目标 Windows 构建，先只修到它能运行，再重新估时；不在未跑通底座前设计更多模块。

## 7. 最小验收

验收完全采用 `最终需求文档.md` 的 AC-01～AC-06：

- **AC-01**：派生应用在目标 Windows 11 机器启动，启用现有桌宠，并配置测试一个可用模型。
- **AC-02**：手动触发后完成截图、固定裁剪、本地 OCR、模型生成、气泡显示和点击复制。
- **AC-03**：前台非微信、截图失败、OCR 无文字或模型失败时显示错误，之后能再次触发。
- **AC-04**：断网时截图裁剪和本地 OCR 仍可完成；远程模型失败可直接报错。
- **AC-05**：能找到裁剪图及对应 JSONL 记录。
- **AC-06**：没有自动输入、粘贴、发送、切换联系人或滚动记录；未点击复制时不改剪贴板。

只在开发者实际使用的一个微信版本、一种布局和一台 Windows 机器上手工通过以上场景即可交付 v0.1。不先建设大样本库、兼容矩阵、性能压测或全量自动化测试。

## 8. 明确删除的过度设计

以下内容不再属于当前方案：

- Python `assistant_core` 和 Python sidecar。
- IPC schema、跨语言类型生成和共享 contracts 包。
- OCR/LLM/ASR/TTS 通用适配器体系。
- `session_generation`、`binding_generation`、会话五元组和复杂状态机。
- 精确 HWND WGC、窗口身份数据库、布局自动识别和可视化校准。
- 自动轮询、新消息识别、重复抑制、方向识别和群聊隔离。
- 13 项授权、权限依赖矩阵、策略引擎和数据域体系。
- 微信数据专用 SQLite、内容寻址、引用计数和五年自动到期。
- `PetRenderer`、`NullPetRenderer`、Live2D 抽象和渲染替换层。
- ASR、TTS、摄像头、屏幕感知、主动建议和多模态 OCR 替换。
- 专门的安全加固、IPC 鉴权、静态加密、DPAPI、日志脱敏和安全扫描。
- 安装签名、自动升级、回滚、SBOM、补丁台账和全量测试矩阵。

Work Review 已有代码中若包含其中部分能力，保持不动即可；本次既不扩建，也不花时间删除。

## 9. 明确后置的产品能力

v0.1 被真实使用后，只按实际遇到的问题逐项增加，建议顺序为：

1. 固定 ROI 不方便时，再加四个数值的简单配置。
2. 用户确实需要自动触发时，再加一个固定周期轮询。
3. 重复建议成为真实问题时，再比较前后两次 OCR 文本。
4. 回复经常弄反时，再做最简单的左右方向判断。
5. 用户确实使用多个聊天或群聊时，再处理聊天对象隔离。
6. Work Review OCR 实机不可用时，再搬运 Umi-OCR 的 RapidOCR。
7. 用户提供可用 Live2D 资产并确认需求后，再单独设计角色渲染。

每一步只解决当时出现的问题，不提前为下一步写接口、占位模块或兼容层。

## 10. 开发人员首批任务

1. 将 `参考/Work-Review-main` 复制为产品工作目录并在目标 Windows 启动。
2. 启用现有桌宠，在原设置中配置并测试一个可用模型，然后找到桌宠中最容易加按钮的位置。
3. 新增 `wechat_reply.rs` 和 `generate_wechat_reply` 命令。
4. 用固定进程名检查前台微信。
5. 隐藏桌宠后调用现有截图函数，使用 `ocr_source_path`，实机调出主屏上的一组可用 ROI 四元数。
6. 调用现有 OCR；确认无文字时直接失败。
7. 调用现有模型请求，把结果送入现有气泡。
8. 加入点击复制。
9. 追加裁剪图与 `events.jsonl`。
10. 在同一台 Windows 机器按 AC-01～AC-06 手工走一遍并打包。

做到第 10 项即结束 v0.1，不顺手开发后置功能。
