## 1. 设计与架构

### [P1] 私有 client 与运行时保护未接线，步骤 10 的微信生成路径不可达

- 证据：`desktop/src-tauri/src/wechat/model_client.rs:25-26` 定义了 `WechatReplyModelClient::new()`；`generate_m1` / `generate_m2` 分别位于 `:35-45`、`:48-61`。对 `desktop/src-tauri/src` 的交叉引用结果中，除模块本身与 compile-fail probe 外，没有这三个函数的生产调用。
- 证据：`desktop/src-tauri/src/wechat/runtime.rs:204-213` 的 `record_model_transport_call()`、`:218-258` 的 `complete_generated_reply()` 同样只有自身及测试调用；没有编排代码先记录一次调用、await client、再提交 `GeneratedReply` 或将 client/transport 失败转为 `LLM_FAILED` 终态。
- 影响：步骤 10 日志第 5、9、10 节所述“运行时提交受一次计数和代际绑定保护”在实际执行中没有路径可触发。更重要的是，调用失败时不能按方案第 3.3 节持久化 `LLM_FAILED` 并释放 slot。编译通过不等同于该契约已落地。
- 修改指南：在后续获授权的内部编排层（不新增 Tauri command/UI/监听/发送入口）集中完成以下顺序：复制配置和 profile 后释放 AppState 锁；校验 profile 后才调用 `record_model_transport_call(lease)`；await `WechatReplyModelClient::generate_m1/m2` 时不持有 runtime/AppState mutex；成功仅用 `complete_generated_reply` 提交；失败用已有合法终态记录稳定 `LLM_FAILED` 并释放 slot。为这条编排补可观察的 fake transport 测试，断言一条 lease 恰一次 transport、失败为 `LLM_FAILED`、取消/超时/过期结果不写入 `ReplyReady`。

## 3. 正确性与测试

### [P1] 通过的 `model_client` 测试没有覆盖 M1/M2 的生成入口或无效 profile 零调用

- 证据：`desktop/src-tauri/src/wechat/model_client.rs:124-137` 的唯一异步测试只直接调用私有 `complete()`；它不调用 `generate_m1` 或 `generate_m2`。这两个 API 受 `wechat-m1` / `wechat-m2` feature 控制，而现行测试命令使用 `--no-default-features`。
- 证据：`cargo check --features 'wechat-contract-check,wechat-m1'` 与 M2 变体均成功，只证明 feature 组合能编译，并不执行 profile resolver、M1/M2 `GeneratedReply` 构造、M2 prompt 组装或 transport 计数。
- 影响：日志宣称的“无效 profile 在 transport 前返回 `WX_TEXT_MODEL_UNAVAILABLE`”“M1/M2 可信输入产生 `GeneratedReply`”“M2 no-hit 可生成”均没有本步骤的执行性证据。当前两个零调用/feature 边界主要由静态文本检查和早期契约测试间接覆盖，不足以验证新增 client 的行为。
- 修改指南：在分别启用 `wechat-m1`、`wechat-m2` 的定向测试中，通过 fake transport 覆盖：(1) 精确 success profile 的一次调用与 `GeneratedReply` 代际；(2) 缺失、未知、untested/error、空 model 时 `WX_TEXT_MODEL_UNAVAILABLE` 且 calls=0；(3) M1 prompt 不含知识上下文；(4) M2 no-hit 和 excerpt context；(5) transport 错误、空白、标量超限、字节超限都返回 `LLM_FAILED`。将实际命令和逐项结果写回 `kaifa_test/test.md`。

## 4. 安全性

- 静态门禁通过，且源代码审查未发现新增 Tauri command、自动发送、输入注入、数据库/上传/协议访问或工具字段。`SingleTurnTextRequest` 的请求体测试验证四类 provider 的 body 不含 tools/function/history。

## 5. 性能、并发与事务

- 单轮 transport 复用 `chat_client()` 且直接发送，不经 `send_with_retry()`；这与“一次逻辑请求对应一次物理请求”的设计一致。
- 由于 P1 路径未接线，尚不能验证真实编排没有跨 `.await` 持有 AppState/runtime mutex，也不能验证取消、超时和晚到结果在 client 调用后的行为。
