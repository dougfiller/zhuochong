## 1. 设计与架构

### [P1] Windows 专属门面未被类型检查或执行，私有编排闭环没有可执行证据

- 证据：`desktop/src-tauri/src/wechat/reply_flow.rs:61-159` 的唯一完整实现以 `#[cfg(target_os = "windows")]` 包裹；macOS 构建实际选择的是 `:161-169` 的直接 `WX_WINDOW_UNSUPPORTED` 返回，因而不会类型检查或运行 capture、OCR、过期检查及模型调用的主路径。
- 证据：本次实际执行 `rustup target list --installed` 仅输出 `aarch64-apple-darwin`。随后执行 `cargo check --target x86_64-pc-windows-msvc --manifest-path desktop/src-tauri/Cargo.toml --no-default-features --features 'wechat-contract-check,wechat-m1'` 以 exit 101 失败，错误为找不到该 target 的 `core`/`std`。
- 影响：`reply_flow.rs:102-158` 是否能在 Windows 上编译，以及捕获成功、OCR error、取消/超时、过期 version、无效 profile、transport 失败的终态和 slot 释放，均不能由本机 M1 check 或静态文本门禁证明。日志也已将 Windows 真机闭环列为 `not-run`，不能把当前结果升级为运行时通过。
- 修改指南：在受控 Windows 11 x64 runner/环境安装 `x86_64-pc-windows-msvc` target 后，先执行该 target 的 M1 check；随后以启用的精确微信 profile 和虚构或受控模型执行 Windows 定向闭环测试。测试必须分别断言阶段顺序、同一 request id、capture version 写入 OCR trace、0/1 次 transport、失败终态和新 lease 可取得。未取得这些结果前，维持发布门禁关闭。

## 2. 正确性与测试

### [P1] 现有门面测试只检查快照，未覆盖日志与方案要求的编排分支

- 证据：`desktop/src-tauri/src/wechat/reply_flow.rs:171-183` 仅有 `m1_snapshot_starts_without_capture_or_m2_binding`；它只断言 mode、初始 capture version 和两个 generation 为零。
- 证据：门面在 `:102-158` 中直接构造 `WechatOcrDispatcher`、`WindowsMemoryPrimary`、`DisabledLocalFallback`，并直接调用 `generate_m1_reply`。现有测试没有 fake capture/OCR/model port，也没有调用 `generate_wechat_reply`，因此无法覆盖成功路径及任何错误分支。
- 证据：`runtime.rs:185-232` 的 `enter_ocr_after_capture` 已有单测，证明 capture version 在 OCR trace 前写入；但它只能验证 runtime helper，不能证明门面把 capture 结果、identity、OCR 和模型按 `reply_flow.rs` 的顺序串接。
- 影响：现有通过结果证明局部状态机和静态词法约束，不能证明步骤 11 定义的 `Validating → Capturing → Ocr → Generating → ReplyReady` 在可调用门面中正确完成，亦不能证明任何失败分支不调用模型。
- 修改指南：保持生产门面为最小适配层，在其内部或 test-only 辅助层注入现有组件的窄 fake capture/OCR/model port；不要新增 Tauri command、UI、微信输入/发送或 M2/RAG 依赖。补充 feature-gated 测试覆盖：
  1. 成功链路的严格 stage 顺序、request id 一致、capture version trace、一次 transport 和 `ReplyReady`；
  2. 前台/capture/OCR/群聊/过期/取消/超时错误均为合法终态，模型调用为 0；
  3. 无效 profile 为 `WX_TEXT_MODEL_UNAVAILABLE` 且调用为 0；
  4. transport、空白和超限结果为 `LLM_FAILED` 且调用恰为 1；
  5. 终态之后能够取得新的 lease，成功 reply 由后续 presenter 的明确关闭路径释放。
