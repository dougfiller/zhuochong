# 代码审查：品牌应用标识和发行安全下限适配
## 审查结论

**结论：不通过，不能合并或进入正式发行。**

本次实现已有效移除指定 updater 源码、Tauri 配置和 Release workflow 中的上游 endpoint，并使应用自身的更新命令返回 `disabled`。但是，仍加载 `tauri-plugin-updater`，且 capability 继续授予其检查、下载和安装权限；这与“彻底切断更新服务请求和安装路径”的安全下限不一致。另有 Rust updater 单元测试在当前工作区不能完成编译，变更记录将该项写为“通过”缺少当前可复现证据。

## 1. 设计与架构

### P1：原生 updater 插件与下载/安装权限仍被注册，安全边界没有彻底关闭

- 证据：`desktop/src-tauri/src/main.rs:4139` 仍执行 `.plugin(tauri_plugin_updater::Builder::new().build())`；`desktop/src-tauri/Cargo.toml:57` 仍依赖 `tauri-plugin-updater = "2.10.0"`；`desktop/src-tauri/capabilities/migrated.json` 仍包含 `updater:allow-check`、`updater:allow-download-and-install` 和 `updater:default`。
- 风险：虽然本次自定义命令 `check_github_update` 与 `download_and_install_github_update` 已走禁用分支，Tauri updater 原生插件仍在应用中加载，并向 WebView 暴露更新检查、下载和安装权限。移除 `tauri.conf.json` 的 endpoint 并不能证明这条已授权的原生路径不可被调用；因此不能宣称“安装路径已彻底切断”。
- 修改指南：在本阶段的安全下限中，同时移除 `Cargo.toml` 的 `tauri-plugin-updater` 依赖、`main.rs` 的插件初始化，以及 `migrated.json` 的全部 `updater:*` permission。保留自定义兼容命令时，应继续只返回明确的 disabled 结果。新增静态测试，断言这三处均不存在 updater 插件注册/权限；再执行一次 Tauri 编译验证。

## 2. 可读性与可维护性

- 禁用分支的命名和中英阿繁四语文案一致；`should_check_updates()` 返回 `false`，手动检查进入 `updater.disabled`，没有把禁用误报为“已是最新版本”。
- Release workflow 缩为手动触发且明确 `exit 1` 的门禁，避免沿用上游资产命名和发布动作；该设计与未冻结发行输入时的安全下限相符。
- `git diff --check` 报告的是两个较早 LOOF run 的 `state.md` 尾随空白，不在本 run 的功能文件或本审查报告范围内；未将其归为本次实现问题。

## 3. 正确性与测试

### P1：Rust updater 单元测试当前未能执行，变更记录的“通过”不可复现

- 实测命令：`cd desktop && cargo test --manifest-path src-tauri/Cargo.toml commands::updater::tests --quiet`
- 实际结果：失败于 `tauri::generate_context!()`，错误为 `frontendDist` 指向的 `../dist` 不存在，故没有编译或执行 updater 单测。
- 风险：本次变更删除了较大段 Rust updater 逻辑；没有可复现的 Rust 编译/单测结果，不能确认命令宏、配置生成和禁用响应在真实构建中仍正确。
- 修改指南：在不提交生成物的前提下，用已锁定依赖运行 `npm ci && npm run build`（或提供等价的受控 `dist` 构建工件），随后复跑上述 Rust 定向测试；将日志和 `kaifa/kaifa_test/test.md` 中的结果改为实际输出。若安装依赖未经授权，应把该项标为 `blocked`，不能标“通过”。

## 4. 安全性

- 上游更新 URL、公钥、CSP 域名和正式发布 workflow 已从本次目标文件移除；自定义 Rust 安装命令返回禁用错误，属于有效的纵深防御。
- 但 P1 所述 updater 原生插件与 capability 仍构成不必要的授权面。完成该移除并以编译测试证明前，正式 Release 必须保持阻断。

## 5. 性能、并发与可观测性

- 禁用后的自动检查在启动入口提前返回，不创建本次自定义更新 HTTP client；未发现新增循环、并发或资源释放问题。
- 本次没有新增需运行时采集的指标；发行阻断原因已在 workflow 与台账中写明。

## 6. 兼容性、依赖与范围

- `update_settings.json` 的读写命令被保留，数据目录与数据库名未改，符合本步骤不迁移旧数据的边界。
- 已核对 `git diff --name-only`：本功能代码改动与指定变更记录的文件清单一致；工作区另有先前 LOOF run 的 state 文件、`kaifa/定时任务.md` 和未跟踪文件，不属于本审查对象，也未被本审查修改。
- 本次审查只新增本报告；未修改任何产品代码、配置、测试或既有文档。

## 7. 合并/发行门禁

在以下条件同时满足前，不建议合并，更不能创建正式发行物：

1. 修复 P1：移除 updater 原生插件及其 capability 权限，并补充针对该边界的静态测试。
2. 提供可复现的 Rust 定向测试通过证据；如依赖安装尚未获授权，明确保持 `blocked`。
3. 保持全量 Node 测试、`rustfmt`、Windows 签名/时间戳和更新信任链验收为未通过或阻断状态，不把环境限制写成通过。
4. 后续正式品牌、identifier、图标授权、签名、时间戳、受控更新 endpoint 和公钥仍须按方案的 BRI-01 至 BRI-07 另行完整验收。
