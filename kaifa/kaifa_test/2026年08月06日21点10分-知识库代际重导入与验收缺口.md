## 2. 审查发现

### P1：同一会话无法创建第二个 import generation，代际切换主路径不可用

- 证据：`desktop/src-tauri/src/knowledge/store.rs:134-151` 在每次 `begin_staging_source` 都生成新的 `conversation_id`，随后于 `:141-144` 无条件插入 `(account_stable_id, conversation_stable_id)`；schema 在 `0001_initial.sql:20-23` 对该组合设置了 `UNIQUE`。
- 影响：同一账号/会话首次导入后，第二次导入会因唯一约束失败并被统一映射为 `KB_NOT_READY`。因此无法形成新的 candidate，也无法执行 `activate_candidate` 中承诺的旧 active → superseded 切换；这与方案要求的“旧 active 不动、候选成功后原子切换”不符。
- 修改指南：在 writer transaction 内按 `(account_stable_id, conversation_stable_id)` 查找并复用已有 conversation id；仅首次导入插入 conversation。为每次导入创建新的 source / import generation，并保持所有失败事务回滚。增加测试：激活 generation A 后为同一会话创建 generation B，验证 B 激活后 A 为 `superseded`、catalog 序号递增，且 B 激活失败时 A 仍是可读 active。

### P1：方案要求的故障与删除边界测试缺失，当前 18 个测试不能证明验收完成

- 证据：Store 自身仅有三个测试：新库/单次 candidate 激活（`store.rs:357-403`）、future `user_version`（`:405-423`）与重开（`:425` 起）。本轮 `cargo test ... knowledge::` 实测为 **18 passed, 0 failed**，但没有 busy 锁竞争、损坏库、非法既有 schema、外键级联或 `deny_or_delete` 的行为测试。静态脚本也只检查关键字，见 `verify_knowledge_store.py:35-43`。
- 影响：阶段 1 的验收明确要求 busy 在有界时间内 fail-closed、损坏/非法库不被覆盖、外键/级联正确，以及 denial 后 active 读取安全。这些不是格式或编译检查能够替代的数据库行为；阶段 2 日志也在第 123 行承认 busy 竞争尚待后续，和该步骤的完成条件冲突。
- 修改指南：以临时虚构 SQLite 文件补齐独立测试：第二连接持有 `BEGIN IMMEDIATE` 时 Store 在 timeout 内返回 `KB_NOT_READY`；非 SQLite / integrity failure / version=0 且已有 `knowledge_*` 表均保持原文件不变且 Store unavailable；验证外键限制与预期级联；验证 `deny_or_delete` 清除 active 后 `read_active_snapshot` fail-closed。测试须不访问用户 dataDir、真实导出或 Work Review 数据库。
