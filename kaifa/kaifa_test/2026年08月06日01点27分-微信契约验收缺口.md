**不通过，禁止进入合并或发布。** 本报告只审查 run `20260806-0110-步骤-4冻结微信知识库状态机和验收契约dispatch_idaich8-zhuochong-de` 的阶段 2 产物；没有修改产品代码。定向 Rust 测试和 feature 编译可复现通过，但两个 P1 验收契约没有被实现为可强制、可验证的行为；另有格式检查环境阻塞。应先完成下列修改与复验，再重新审查。

- M1/M2 feature 通过 `wechat-contract-check` 隔离，不破坏默认 Work Review 构建；本次实际复跑默认 `cargo check` 成功。
- 但是“RAG 不可绕过”和“实时回复只限单聊”是本步骤计划中的安全边界，当前没有被领域类型/状态机完整冻结，故架构验收不能通过。

## 2. 可读性与可维护性

- 模块文件较小，错误码和 scope wire 值显式声明，可读性基本满足本步骤的领域契约目标。

## 3. 正确性与测试

### P1：M1 单聊限制只被记录，未被代码强制

- 证据：验收矩阵明确写明“M1 仅支持单聊实时回复”（`desktop/docs/contracts/ac-applicability-matrix.md:3`）。但 `OcrReadyReply::from_backend` 仅检查 OCR 文本（`desktop/src-tauri/src/wechat/types.rs:61-70`），`M1ReplyInput::from` 无条件接收该值（同文件 `88-95`）；`CapturedWechat.is_single_chat` 为 `false` 时也能形成 M1 输入。
- 影响：后续编排器即使传入群聊采集元数据，也不会在这条“OCR -> M1 输入”契约链被拒绝，违反当前明确的实时回复范围。
- 修改指南：先在计划规定的稳定错误码中确定群聊拒绝所用 code（不可临时复用语义不匹配的 code）；随后在从 `CapturedWechat` 进入 `OcrReadyReply` 或 M1 输入的唯一入口强制 `is_single_chat`，并增加 `isSingleChat:false` fixture 与单元测试，断言不能得到 `M1ReplyInput`。同时将矩阵 AC 行的证据指向该测试。

### P1：M2 的检索失败门禁没有被状态机或测试表达

- 证据：`StateMachine` 对 M2 的唯一限制是 `Retrieving -> Generating`（`desktop/src-tauri/src/wechat/state_machine.rs:76-77`），迁移并不携带或校验检索结果。`knowledge_retrieve` 的输入模型也只列出 `Success`、`NoHit`、`FtsFallback` 三种成功结果（`desktop/src-tauri/src/knowledge/types.rs:47-55,93-101`），无法表示/返回 `KB_RETRIEVAL_FAILED`。`retrieval_failed.json` 只在“所有 fixture 可解析”的循环中被读取（`desktop/src-tauri/src/wechat/fixtures.rs:16-35`），没有断言其 `modelTransportCalls: 0`。
- 影响：矩阵把 AC-RAG-03 标为步骤 4 的 `required`（`desktop/docs/contracts/ac-applicability-matrix.md:22`），但当前不存在可执行证据证明检索失败终止请求、不会构造模型上下文且 transport 调用为零。文档中“已通过”的结论超出了测试覆盖。
- 修改指南：把检索成功（含 `no_hit`）与检索失败建模为可区分的结果；状态机仅接收成功的检索凭据后才允许 M2 进入 `Generating`，失败必须进入 `Failed`/`Cancelled` 并携带稳定 `KB_*` 错误。增加 fake transport spy 测试，以 `retrieval_failed.json` 驱动，断言错误码、终态、未构造 `ModelKnowledgeContext` 与零模型调用；`no_hit` 则断言是唯一允许继续生成的空命中路径。

### P2：token budget 未在模型上下文边界落实

- 证据：`KnowledgeRetrieveRequest` 定义了 `token_budget`（`desktop/src-tauri/src/knowledge/types.rs:36-45`），但 `RetrievedReply::excerpts` 返回全部摘要（`85-90`），`ModelKnowledgeContext::from_retrieved` 原样复制全部摘要（`desktop/src-tauri/src/wechat/model_contract.rs:20-27`）。计划要求模型上下文仅带 token 预算内摘录。
- 影响：未来实现如果按现有接口接入，不能由契约层阻止过长上下文或超预算的知识内容进入模型。
- 修改指南：把预算约束放在创建 `RetrievedReply` 或其到 `ModelKnowledgeContext` 的唯一适配器，并新增超预算命中测试；测试应验证截断/拒绝策略、`no_hit` 行为和不泄露内部 ID/来源路径。

### P2：私有构造与 feature 可达性缺少反向编译证据

- 代码检查可见 `RetrievedReply` 字段无公开构造器，`ModelKnowledgeContext::from_retrieved` 限于 `crate::wechat`，而 M1/M2 函数受 `cfg(feature)` 控制（`model_contract.rs:18-47`）。
- 但现有成功 `cargo check` 只证明四个 feature 组合可编译，未证明外部/非受信任模块“不能构造”上述类型，也未证明 M2 target 无法引用 M1 入口。
- 修改指南：加入独立 compile-fail 测试（例如 `trybuild` 或最小 UI test），覆盖非受信任模块构造两个私有封装、M2 引用 M1 入口和 M1 引用 RAG 入口三种失败；将矩阵 AC-RAG-04/05 的 `evidence_target` 指向实际测试名。

## 4. 安全性

- fixture 使用固定虚构 UUID、通用文字和相对占位值；人工检查未见聊天正文、联系人、截图、绝对真实路径、源目录哈希或凭据。
- P1 单聊限制未强制，因此现阶段不能将实时回复的处理范围视为安全闭合。
- P1 检索失败零调用只存在 JSON 声明，尚非执行证明；不能据此批准 M2 的“检索失败不调用模型”安全结论。
