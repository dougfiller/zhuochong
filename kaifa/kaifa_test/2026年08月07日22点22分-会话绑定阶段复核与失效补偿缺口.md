## 1. 设计与架构

### [P1] 阶段复核 gate 没有强制自行重读前台窗口和 header

**证据**

- 方案要求在检索前和模型 transport 前各调用一次 gate，两次都必须重新读取前台窗口并重新捕获 header，且不能缓存第一次结果（方案第 104、341—348 行）。
- `desktop/src-tauri/src/wechat/binding.rs:398-420` 的 `revalidate_for_stage` 却由调用方传入 `BindingWindowIdentity` 和 `HeaderIdentityClue`；`BindingStage` 参数被命名为 `_stage` 且完全未使用。
- 该方法不是负责捕获的异步边界，也没有持有/调用 `WechatReplyRuntime`、`CaptureCoordinator` 或 `capture_header_identity_observation`。调用方可以把第一次观察结果在两个阶段重复传入，类型和接口本身无法阻止缓存复用。
- 本次 `cargo check` 的 dead-code 警告确认 `begin_m2_request`、`revalidate_for_stage`、`update_m2_observation` 当前没有生产调用者；这符合步骤 25 尚未接完整 M2 编排的非目标，但不能证明步骤 24 所提供的 gate 契约正确。

**风险**

后续步骤 25 即使表面上在两个位置调用 `revalidate_for_stage`，也可能使用旧的 window/header 证据，使检索到模型传输之间发生的窗口、resize、profile 或 header 变化未被检测。该问题直接破坏“模型前必须重新核对”的安全边界。

**修改指南**

1. 将“重新读取前台窗口 + 共享协调器 header-only 捕获 + OCR + binding CAS + runtime observation 更新”封装为唯一的阶段 gate；不要让调用方传入已构造好的 window/header 证据。
2. gate 应显式消费 `BindingStage::BeforeRetrieval` / `BeforeModelTransport`，并对同一 request snapshot 记录两个独立、严格递增的 observation version。
3. 增加行为测试：第一次阶段通过后替换 HWND、bounds、profile 或 header，第二阶段必须拒绝；重复传入/缓存第一次证据应在 API 层无法表达或被测试拒绝。

### [P1] Store 解析失败和阶段复核变化丢弃 `BindingMutation`，没有执行统一补偿

**证据**

- `desktop/src-tauri/src/wechat/binding.rs:366-380` 在 active scope 解析失败或 catalog digest/count 变化时调用 `invalidate_if_current(...)`，但直接丢弃其返回的 `Option<BindingMutation>` 后返回错误。
- `desktop/src-tauri/src/wechat/binding.rs:405-413` 在阶段复核发现 window/header 变化时也只判断 `mutation.is_some()`，随后丢弃 mutation 并返回错误。
- 真正推进 capture generation、取消匹配 M2 lease、取出并清除旧建议的统一补偿只存在于 `desktop/src-tauri/src/wechat/commands.rs:184-200` 的 `apply_binding_mutation`。上述两个内部路径没有 `AppHandle`/runtime/coordinator，也没有把 mutation 返回给可以调用该补偿函数的所有者。
- 现有 5 个 binding 单测只直接验证 generation/state 变化，没有建立 active M2 lease、presented suggestion 和 capture version 来验证完整补偿链。

**风险**

binding generation 会递增且状态变为 unbound，但旧 capture 仍可能被认为 current，匹配旧 generation 的 M2 lease 未被取消，已展示建议也不会收到精确 clear 事件。之后若步骤 25 接入这些内部方法，晚到 OCR/retrieval/model 结果与旧 copy 操作不能获得方案承诺的统一失效保证。

**修改指南**

1. 让所有可产生 mutation 的 API 把 `BindingMutation` 明确返回到唯一编排层，或把统一补偿抽成 binding/command 都能调用的服务；禁止生成 mutation 后静默丢弃。
2. 保持锁顺序：binding mutex 内只计算 mutation，释放后依次推进 capture、取消 runtime M2 lease、精确清泡。
3. 增加端到端领域测试：scope resolution failure、catalog change、第二阶段 HWND/header 变化都必须同时断言 generation +1、capture 失效、active M2 lease 终止、旧建议不可复制并生成精确 clear payload；另断言 M1 不受影响。

### [P1] header 不可靠时，用户确认发生在新观察之前

**证据**

- 方案要求每次请求在气泡中展示当前 scope 摘要并由用户再次确认，确认只授权下一次请求（方案第 35、112、499 行）。
- `desktop/src/lib/components/KnowledgeScopePicker.svelte:143-163` 先弹出 `confirm(...)`，用户确认后才调用 `begin_knowledge_scope_observation`；得到新的 `nextObservation` 后没有再展示 `headerClue`，而是立即调用 `confirm_knowledge_scope_for_next_request` 写入 one-shot epoch。
- 后端 command `desktop/src-tauri/src/wechat/commands.rs:155-166` 只按前端提供的 observation version 写 receipt，不负责向用户展示或取得观察后的确认。

**风险**

用户确认的是捕获前的 scope 计数，而不是刚捕获的前台窗口/header 线索。只要观察结果仍被分类为同一 unreliable clue，后端就会发放一次性授权，用户没有机会看见本次请求实际观察到的线索。这不满足“每次请求再次展示并确认”的显式授权要求。

**修改指南**

1. 调整为两步交互：先执行 fresh observation，把本次 scope 摘要、header clue/不可靠说明显示给用户；用户在看到该结果后再确认并提交相同 observation version。
2. 如果 observation 导致 generation 变化或 unbound，必须停止流程、刷新状态，不能继续发放 one-shot receipt。
3. 增加前端行为测试（不要只做源码字符串匹配）：断言调用顺序为 observation → 展示结果 → 用户确认 → one-shot command；用户取消时不得调用 one-shot command。

## 2. 可读性与可维护性

### [P2] candidate display metadata 的进程内表没有完成态清理

**证据**

- `desktop/src-tauri/src/knowledge/store.rs:552` 新增 `pending_display_metadata: Mutex<HashMap<String, String>>`。
- `store.rs:1051-1056` 每次 staging 插入 generation metadata；激活路径在 `store.rs:2045-2052`、`2403-2404`、`2452-2453` 只调用 `get(...).cloned()`。
- 对该字段的全仓检索只有初始化、`insert` 和 `get`，没有在 activation、discard、失败清理或 rebuild 完成后 `remove`。

**风险**

每次导入生成新的 UUID generation key；长期运行中成功、失败或丢弃的候选元数据都会永久留在 Store 内存，形成无界增长，也使“候选数据只存到完成/清理边界”的生命周期不完整。

**修改指南**

在数据库事务成功提交后移除已发布 generation 的 metadata；所有 discard/失败清理路径也移除对应 key。注意事务失败前不能提前丢弃，以便重试仍能发布一致 metadata。补充成功激活、批量激活、discard 和事务回滚四类生命周期测试。

### [P2] header clue 标记为不可靠但仍原样跨 Tauri 返回，未真正实施长度上限

**证据**

- 方案第 109 行要求 header clue 最多 256 bytes / 128 scalar。
- `desktop/src-tauri/src/wechat/ocr.rs:26-46` 把第一行完整复制到 `text`；超限只令 `reliable=false`，没有截断或拒绝。`record_observation` 随后把 `header.text()` 原样写入 `HeaderObservationResponse.header_clue`。
- 现有 OCR/binding 测试没有覆盖超长 ASCII、多字节 Unicode 或多行 header response 的实际上限。

**风险**

异常 OCR backend 可以把超长字符串保存在 binding 内并跨 Tauri 发送到 UI，违反有界 DTO 约束，并增加内存、序列化和 UI 渲染风险。

**修改指南**

在构造 `HeaderIdentityClue` 时就执行 byte/scalar 双上限：超限时返回固定空/截短的 unreliable clue，不保留完整原文。新增 257-byte、129-scalar、多字节边界和多行输入测试，并断言 response 本身满足上限。

### 测试覆盖评价

- 新静态门禁主要检查源码中是否出现指定字符串，例如只确认存在 `capture_header_identity_observation`、`invalidate_current_capture` 和三个 UI action；它不能证明这些函数在正确调用链或正确顺序中执行。
- 新增前端测试同样主要是源码正则，未执行 Svelte 交互，因此没有发现一次性确认顺序问题。
