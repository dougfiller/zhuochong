## 2. 发现的问题

### P1：方案要求的既有回归门禁实际失败

- 证据：本次实际运行 `verify_wechat_json_archive.py --project-root .` 退出失败；本次实际运行 `verify_knowledge_lineage_generations.py --project-root .` 也退出失败。方案文件第 6 节“回归”明确要求三份既有 verifier 一并通过。
- 影响：当前实现没有通过既有 archive 与 lineage 契约。无论其中一部分断言是否已被 v3 设计取代，测试契约尚未以受审查的方式同步，因此不能证明没有回归，也不能将 phase 2 的“测试通过”扩大为本功能验收通过。
- 修改指南：仅更新这两个 verifier 中被 v3 设计有意替代的精确断言，保留并补强原有只读、脱敏、candidate 不可见、source audit 与 lineage 安全约束；新增正反例 fixture。完成后同时运行三份既有 verifier 与本 run verifier，报告四项原始输出。

### P1：带 retained parent member 的 selected/filtered 导入不会转为 ready candidate

- 证据：`store.rs:266-274` 对非 `Full` 导入复制 parent generation 的 membership；`store.rs:369-372` 随后把 `message_count` 更新为复制后的总 member 数。`finalize_source_candidates` 在 `store.rs:711-714` 却要求该总数等于本次 `knowledge_import_generation_input_keys` 数量，后者只由本次流式消息在 `store.rs:299-309` 写入。只要 parent 存在一个范围外 retained member，这两个数就不相等，状态保留为 `staging`。
- 影响：有已激活 parent 的会话再导入 selected/filtered 包时，importer 可返回成功汇总，但 generation 不能成为 `ready_candidate`。随后 source 被写为已验证状态，后续同 fingerprint 导入可能走 fast-verify，而残留 staging 仍无法走后续候选流程。
- 现有测试缺口：`store.rs:1226-1283` 仅以旧的 `mark_ready_candidate(... expected_message_count: 1)` 直接测试 retained member；它没有走本 run 新增的 `finalize_source_candidates`，因此未覆盖上述不等式。
- 修改指南：将“本次解析/accepted count”和“generation 总 membership count”分开持久化或在 ready SQL 中按 source/本次输入键验证，不要以总 membership 与本次输入键等同。新增端到端回归：先激活 full parent，再通过 archive importer 导入 selected/filtered archive，断言 retained member 存在、generation 变为 `ready_candidate`、本次 accepted count 正确且没有误激活。

### P1：大型流式、故障恢复与 no-op 验收没有可复现的实现或测试证据

- 证据：方案第 5、6 节要求 `ImportMemoryProbe`、百万级 synthetic `messages[]`、256 边界/尾批、`SQLITE_FULL` 或第 N 批 fault hook、重开重放，以及 no-op 的写入计数和耗时阈值。对 `desktop/src-tauri/src/knowledge` 和 `kaifa/kaifa_test` 检索 `ImportMemoryProbe`、`peak_batch_len`、`peak_message_dto`、`SQLITE_FULL`、`fault hook`、`messages_accepted`、`duplicates_rejected`、`conversation_ready`、`conversation_failed`、`manifest_declared_messages` 均无匹配。当前测试只证明普通 fixture repeat fast-verify（`archive_importer.rs:1387-1408`）和单条媒体行（`store.rs:1182-1224`）。
- 影响：虽然源码存在 `Vec::with_capacity(256)`（`archive_importer.rs:704-729`），尚无行为证据证明大输入不会积累 DTO、故障批次会完全回滚、重放不会重复 version/media/membership，或 fast-verify 不产生任何派生写入。方案把这些作为通过条件，缺失时不能宣称本功能满足大型导入与恢复要求。
- 修改指南：以脱敏 synthetic reader 添加独立测试 probe，至少断言峰值 batch 不超过 256、累计 ordinal/计数正确；在 Store 加仅测试可用的第 N 批与 `SQLITE_FULL` fault hook，验证失败清理、重开从会话开头重放和旧 active/其他 ready candidate 不变；为 exact repeat 记录写入前后 version、membership、media、chunk/index 计数，并验证审计改变时不走 no-op。不要使用真实 archive、媒体或人为耗尽磁盘。
