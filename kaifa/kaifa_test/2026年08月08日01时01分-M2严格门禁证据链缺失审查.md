## 2. 审查发现

### [P1] 故障矩阵和 AC 矩阵只校验“引用了任意 evidence id”，没有校验该证据证明对应场景

**位置：** `kaifa/kaifa_test/verify_m2_observability_gate.py:339-382`

`check_matrix()` 对 `pass` 行只要求 `evidence_ids` 非空且属于全局 evidence id 集合；它没有建立 `M2-RET-*`、`M2-MOD-*`、`AC-RAG-*` 等矩阵项与必须出现的场景、故障注入、终态、错误码、计数或 candidate batch 的对应关系。因此一条普通成功请求可以被 45 个故障行和 44 个 AC 行共同引用。

**动态复现：** 正向 fixture 的 89 个矩阵行本来就全部只引用 `E1`。审查时通过管道构造只保留 `request_evidence[0]` 的输入，删除唯一失败请求证据 `E2` 后运行 gate，结果仍为：

```text
M2_OBSERVABILITY_GATE status=pass failures=0 blockers=0
single_success_only_exit=0
```

这证明当前 gate 可以在没有任何检索失败、模型失败、并发/崩溃/隐私/桌宠故障执行证据的情况下，把完整故障矩阵判为 pass。现有 `fail-capability`、`fail-default-pass` 等负向 fixture 没有覆盖“错误证据引用到错误矩阵项”的路径。

**修改指南：**

1. 为每个 fault/AC id 定义机器可校验的 evidence contract，例如必需 `scenario_id`、触发故障、预期 stage/terminal/error code、模型/embedding/upload/capability 计数及 candidate batch。
2. `check_matrix()` 必须校验被引用证据满足当前行的 contract；不能只检查 id 存在。允许多个矩阵项复用同一批证据时，也必须逐项验证对应断言。
3. 增加负向 fixture：删除全部失败请求证据、把所有 fault 行改引成功请求、错配 error code/terminal/counter，均必须返回 fail 或 blocked。
4. 修复后复跑本报告第 4 节全部 gate fixture，并保留上述“single-success-only”回归，预期不再 exit 0。

### [P1] candidate、环境和 evidence SHA-256 只做字符串格式校验，未绑定真实文件或同一批产物

**位置：** `kaifa/kaifa_test/verify_m2_observability_gate.py:117-166, 169-199, 385-426`

当前 verifier 只确认 commit 看起来像 40 位十六进制、hash 看起来像 64 位十六进制、环境字段被声明为 `real/true`。它不读取或重新计算 trace/audit/privacy/sentinel/授权证据文件，不校验 `git_commit` 是否为当前 candidate，不校验 source tree、NSIS、batch id 与 request evidence 是否来自同一冻结批次。正向 fixture 使用重复数字组成的占位 hash、fixture host/profile，并把环境自报为 `real`，仍然 exit 0。

这不是单纯的 fixture 问题：生产 gate 接受同一 JSON schema，所以任何自报的 64 位十六进制字符串都可被当作“已附证据”。当前正式 JSON 保持 blocked 是诚实的，但 verifier 本身无法阻止后续仅改 JSON 字段形成假 pass。

**修改指南：**

1. gate 输入应包含受控 evidence manifest 和相对证据文件引用；逐个打开文件、计算 SHA-256，并拒绝缺文件、路径越界、symlink、hash 不一致和重复/跨 batch 引用。
2. 从实际 Git/candidate/package 产物计算或读取受信任 identity，校验 `git_commit + source_tree_sha256 + nsis_sha256 + batch_id` 一致；不要信任 JSON 自报身份。
3. 环境真实性需要由采集器生成且与 batch/candidate 绑定的证明，不能仅用 `evidence_type="real"` 和两个 boolean。
4. 增加“格式正确但无文件”“hash 指向其他 batch”“candidate commit 与当前冻结产物不符”“fixture 冒充 real”负向测试。

### [P1] 生产能力计数/终态/上传/哨兵采集链没有接通，strict gate 校验的是手填摘要而不是实现产生的证据

**位置：**

- `desktop/src-tauri/src/wechat/observability.rs:231-253, 356-439`
- `desktop/src-tauri/src/wechat/reply_flow.rs:505-508`
- `kaifa/kaifa_test/verify_m2_observability_gate.py:429-471`

生产路径目前能落盘 retrieval、embedding 和 model-attempt 事件，但 `capability_observed()`、`CapabilitySnapshot::from_events()`、`forbidden_are_zero()` 都受 `#[cfg(test)]` 限制。`TerminalObserved`、`UploadQueueObserved`、`OcrLocalProcessStarted`、pet/resource observer 等枚举没有对应生产构造/接线；Windows M2 OCR 仍把审计交给 `DiscardOcrAudit`。源码全局引用检查也显示 `CapabilitySnapshot` 只在同文件测试和 Python 的字符串 marker 检查中出现。

同时 `check_source_boundaries()` 只搜索符号/字符串是否存在，不证明这些能力在生产路径实际运行。这样正式证据 JSON 中的禁止能力零值、upload 零值、terminal、sentinel 和 OCR 计数无法从当前生产审计链可信生成，只能由外部手工填入；与方案要求的“同 requestId 汇聚真实 spy/counter”不一致。

**修改指南：**

1. 在受信任的生产/候选测试采集器中接入 terminal、OCR、upload queue、禁止能力和 pet/resource observer；同一 request/batch 生成不可手填的固定 schema 事件。
2. 明确区分“观察到显式 0”与“没有采集器/没有事件”。采集器缺失必须 blocked，不能把 `CapabilityCounts::default()` 当零调用证明。
3. 让 collector 从 trace/audit/observer 原始脱敏文件生成 gate manifest；verifier 重新校验 join、顺序、计数和 hash，而不是直接信任摘要 JSON。
4. 补生产路径/候选测试，证明 M2 OCR、成功/失败/cancel terminal、上传队列开启时零入队、桌宠哨兵五类计数均由实际 observer 产生；再保留 schema 不可表达正文/凭据的隐私测试。

## 3. 设计、安全与兼容性评价

- retrieval evidence 在 model transport 前持久化、模型重试冻结 request bytes/context/model id、audit 写失败时零 provider 调用，这些定向行为有 Rust 测试支撑。
- 固定字段 schema、`deny_unknown_fields`、16 KiB 单行上限以及不提供正文/路径/provider body 字段，降低了审计内容泄漏风险。
- 本 run 没有引入新第三方依赖；M1/M2 feature 编译均通过。
- 但上述局部正确性不能替代完整故障/AC 证据链。正式 after-gate 当前返回 blocked 是正确状态；在三个 P1 修复并获得真实 Windows/candidate/模型/授权证据前，不得把其改成 pass。

## 5. 最小修复顺序与复审门槛

1. 先修复矩阵项与场景证据的语义绑定，并加入 single-success-only 负向回归。

## 6. 最终结论

本次实现的局部 Rust 审计与 fail-closed 行为通过定向测试，但 strict gate 仍可把单条成功 fixture 复用为全部故障/AC 证据，且 hash、candidate 与生产能力计数没有可信证据绑定。相关测试并非全部通过（Node 全量有一项本 run 外既有失败），正式发布 gate 明确 blocked。必须先完成上述最小修复并重新审查，当前不能越过风险进入发布或合并结论。
