## 2. 阻断问题

### [P1-1] 最终代际重验不包含 denial/source 授权状态，撤销后仍可能返回已读出的正文

**证据**

- `desktop/src-tauri/src/knowledge/retrieve.rs:333-347` 先调用 `read_authorized_hit_payloads()` 取得正文和来源，再调用 `ensure_retrieval_still_active()`，随后直接构造 hash/reply。
- `desktop/src-tauri/src/knowledge/store.rs:1581-1654` 的 payload 读取确实使用授权 SQL，但它在一个独立 reader 中完成；末尾仅再次调用 `ensure_retrieval_active()`。
- `desktop/src-tauri/src/knowledge/store.rs:2687-2702` 的 `ensure_retrieval_active()` 只比较 catalog generation、index id、snapshot、embedding config 和 token budget/version，完全不重验 conversation/message/source denial，也不重验 `source_state='active'` 或每条 message 的 active provenance。
- 与此同时，`retire_source()` 可只更新 `knowledge_sources.source_state`（`store.rs:603-610`），`deny_or_delete()` 可只插入 `knowledge_denials`（`store.rs:2260-2275`）；这两条路径都不递增 catalog generation，也不改变 active index/snapshot。

**可复核失败路径**

1. 检索在 payload reader 中通过授权 SQL并把正文读入内存。
2. 在该 reader 返回后、`ensure_retrieval_still_active()` 之前，另一操作执行 `retire_source()` 或写入 source/conversation/message denial。
3. catalog/index/snapshot/config 未变化，所以最终重验仍返回 `Ok(())`。
4. 已被撤销授权的正文仍可进入 `RetrievedReply`。当前测试只在检索开始前把来源改为 retired（`retrieve.rs:1063-1077`），没有覆盖这个时序窗口。

**影响**

这不是普通一致性偏差，而是权限撤销后的内容泄漏窗口，违反“重取时再次授权”“每个 Store 调用前后重验”和 fail-closed 边界。

**修改指南（最小范围）**

1. 为 source/denial 变化建立可冻结、单调递增的 authorization epoch/digest，并放入 `AuthorizedScopeToken`；所有 retire/deny/delete 路径在同一事务中推进它。
2. 最终重验同时比较 catalog token 和 authorization token；不一致统一返回 `KB_RETRIEVAL_FAILED`，不得返回部分 reply。
3. payload 读取应在同一 SQLite read transaction/snapshot 内完成正文、message range、source path 和末次授权检查，避免同一 payload 内的多语句漂移。
4. 增加确定性并发 hook：分别在最后一条 payload 读取后、最终重验前注入 source retire、source denial、conversation denial、message denial；每项断言整次失败、reply 不存在、正文不进入 trace/model。

### [P1-2] `frozen_result_hash` 只绑定 chunk ID 和量化 score，没有绑定完整命中内容与关键请求策略

**证据**

- `desktop/src-tauri/src/knowledge/retrieve.rs:557-589` 的 hash 输入包含 request id、query、binding/catalog/index/snapshot、scope、预算、topK 和 mode；每个 hit 只加入 `knowledge_chunk_id` 与量化 score。
- hash 没有加入 `bound_conversation_id`、`same_conversation_boost`、显式 status，也没有加入 hit 的 `conversation_id`、message/time range、source paths、excerpt、token count。
- `desktop/src-tauri/src/knowledge/retrieve.rs:961-981` 所谓“完整响应/hash”测试只断言 hash 非空，没有改变任一字段后比较 hash，也没有验证 canonical 顺序。
- 指定开发日志 `:117-120` 宣称“完整响应、冻结 hash”已实现并通过回归，这一结论超出当前实现和测试证据。

**可复核失败路径**

对同一个 chunk id 和相同量化 score，只要正文、来源路径、message/time range、conversation id 或 token count 发生变化，当前 hash 仍完全相同。对 global scope，改变 bound conversation 或关闭 boost 但最终 id/score 未变化时，hash 也可能相同。因此该值不能证明实际交给后续受信任适配器的完整本地 hit 与请求策略被冻结。

**影响**

步骤 25 若用该 hash 关联重试、trace 或上下文，将可能把不同正文/来源契约视为同一检索结果，破坏结果绑定与审计可复核性。

**修改指南（最小范围）**

1. 定义版本化 canonical result schema，显式加入 `bound_conversation_id`、boost policy/开关、status、mode，以及每个 hit 的全部确定性字段；字符串继续使用长度前缀，列表保持已验证的稳定顺序。
2. `elapsed_ms` 若刻意不参与“冻结结果”以保持可重试稳定性，应在契约和字段名中明确；不得继续用“完整响应 hash”描述一个只覆盖 ranking identity 的摘要。
3. 增加表驱动测试，逐一改变 request policy、hit conversation/ranges/paths/excerpt/token count/score/order/status，断言预期字段变化会改变 hash；selected scope ID 顺序 canonical 化后应保持相同 hash。

### [P2-1] 非法 `bound_conversation_id` 的 `KB_SCOPE_UNRESOLVED` 被无条件压成 `KB_RETRIEVAL_FAILED`

**证据**

1. 在进入 reader 前完成 bound id 语法校验并保留 `KbScopeUnresolved`；只把实际 reader/catalog/SQL 错误映射为 `KbRetrievalFailed`。

## 5. 设计与架构

- 正向项：唯一异步门面位于 `retrieve.rs`，Store 层候选 SQL使用参数绑定并在候选阶段应用 active mapping、denial 和逐 message provenance；本地 embedding 不可连接时的显式 FTS fallback 与 fingerprint/维度错误不降级方向正确。
- 阻断项：catalog token 与授权 token 被混为一体，source/denial 变更不进入最终冻结检查；result hash 又没有绑定实际返回的完整 hit，两个问题都破坏单一可审计结果边界。
