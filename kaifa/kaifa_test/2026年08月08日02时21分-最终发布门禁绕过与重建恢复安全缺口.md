## 2. 审查发现

### [P1] final gate 可在没有任何有效 M2 request join 时返回 pass

位置：kaifa/kaifa_test/verify_final_m2_release_gate.py:253-306

m2RequestJoins 的校验用 if isinstance(row, dict) 过滤非对象元素。只要列表非空但元素全是字符串或数字，any(...) 即为 false，不会产生 failure 或 blocker。

动态复现：审查在系统临时目录复制 pass fixture，仅把 m2RequestJoins 替换为一个非对象字符串，重算 evidence SHA-256 后运行正式 CLI，实际结果为：

~~~text
exit=0
{"blockers": [], "failures": [], "schemaVersion": 1, "verdict": "pass"}
~~~

同一函数中，业务 UAT 只检查 8 个类别名，candidate contract 只检查非空字符串，rebuild/recovery/signature/asset/runtime/rollback/approval 大多只信任自报布尔值或计数。--project-root 虽必填却未使用；m2-contract-freeze-v1.json、candidate/package 文件、question-set 和签名输出均未被打开或重算。因此 verifier 不能满足方案要求的同批 candidate/hash/audit/UAT/signature/LKG join，也不能阻止 synthetic JSON 冒充正式证据。

修改指南：

1. 为 final evidence 建立 additionalProperties=false 的严格 schema；m2RequestJoins 每行必须是对象且含完整 request/batch/candidate/stage/terminal/count 字段，任何非对象行直接 fail。
2. 逐文件 resolve/re-hash，从 raw question rows、audit events、signature outputs、rebuild snapshots、recovery receipt 重算结果，不接受 categories/signatures=true/rebuildDeterministic=true 之类手填摘要。
3. 强制 join candidate commit/tree/feature marker/NSIS/updater hash、freeze hash、M2 contract freeze hash、releaseBatchId 和 approvals；任一证据变化必须使 approval 失效。
4. 增加非对象 join、缺 terminal/physical attempt、只列 UAT 类别、自报签名/恢复/重建、fixture 冒充 formal 等负向测试；保留本报告 probe，修复后必须非 0。

### [P1] rebuild 仍接受 frontend 路径字符串，且在 maintenance lease 前读源并替换 manifest

位置：

- desktop/src-tauri/src/knowledge/commands.rs:193-209
- desktop/src-tauri/src/knowledge/store.rs:859-973

Tauri command 仍把 SelectedRoots.selected_roots 字符串直接转成 PathBuf，没有 native picker 生成的一次性 opaque receipt。可调用该 command 的 frontend 代码仍可构造任意路径，与方案“禁止调用者传路径字符串绕过 picker”相违。

prepare_and_start_rebuild() 先读 roots、读 active embedding、替换私有 manifest，之后才由 start_rebuild() 调用 begin_maintenance()。这留下未受 maintenance 保护的 TOCTOU 窗口，不能证明 manifest 与最终重建使用同一冻结状态。

修改指南：

1. 由现有 native directory picker 的受信任 owner 生成进程内一次性 receipt；Tauri command 只接受 receipt id，Store 从受信任内存解析 roots。
2. 先取得单一 maintenance lease、阻断新 import/rebuild/retrieve/M2 并等待 reader drain，再冻结 source facts、写/fsync manifest、启动 worker。
3. 增加伪造/过期/重放 receipt、并发 maintenance/import/retrieve、manifest 写失败后 lease 终态等行为测试。

### [P1] rebuild manifest 没有保存或重放真实 priority、deny、retire 策略

位置：desktop/src-tauri/src/knowledge/store.rs:889-1022

prepare_rebuild_manifest() 把传入顺序直接当 priority，对每项固定写 state=active，policy receipt 只是 hash("<priority>|active")；它没有从 Store 冻结真实 source priority、retired/deny receipt。start_rebuild_from_manifest() 又强制每项 active，最终只把 roots 传回旧 start_rebuild()，从未重放策略。

此外 root_identity、coverage_sha256、policy_receipt_sha256 和整个 index_spec 在 start 阶段没有与当前 source/index 事实重算比较；实际只校验私有 manifest 文件 hash 和各 root 的 manifest.json hash。日志中的“policy/index facts 可恢复”和“确定性 rebuild”没有对应实现或行为证据。

修改指南：

1. 在 maintenance 写事务中从 KnowledgeStore 冻结 source facts、显式 priority、deny/retire policy receipt，不得用 enumerate + active 伪造。
2. 在 candidate 内重放并验证 active/retired/deny set、source lineage、priority、schema/embedding/index/catalog snapshot。
3. 增加同一只读源两次重建的逻辑摘要比较，覆盖 selected/full/incremental、priority、deny/retire 和 policy/spec 漂移。

### [P1] 隔离恢复忽略 rename 失败后仍删除 quarantine，可能删除旧集合唯一副本

位置：desktop/src-tauri/src/knowledge/store.rs:4323-4404

restore_old 对每个 fs::rename(moved, original) 都用 let _ = 丢弃结果，三个失败分支随后立即 remove_dir_all(quarantine)。尤其在 candidate DB 已放到 primary、candidate manifest rename/校验失败时，“把新 primary 移回 candidate”也忽略失败；若 primary 仍占位，旧 DB 从 quarantine 恢复会失败，随后 remove_dir_all 会删除旧 DB/manifest/WAL/SHM/audit 的唯一副本。

当前新增测试只覆盖 candidate manifest 无效且所有恢复 rename 成功，没有覆盖方案要求的每个 checkpoint 失败。日志所述“失败时完整恢复并保留 quarantine”与代码删除行为矛盾。

修改指南：

1. 把发布/恢复改成显式状态机；每个 rename、fsync、validate、reopen 结果必须检查。
2. rollback/restore 不完整时绝不删除 quarantine；保留旧副本并返回 KB_NOT_READY。只有 primary 完整恢复且 reopen 后才可处理空目录；成功发布的 quarantine 也按未获批保留策略继续保留。
3. 为 DB/manifest/WAL/SHM/audit 的移入、inventory 写入、candidate 移入、pair validate、新集合移出、旧集合逐项恢复和 reopen 增加 fault-injection 测试，断言旧数据至少保留一份且原始导出不变。

### [P1] Windows collector 的 batch 路径和 metadata 隐私校验可绕过

位置：desktop/scripts/release/collect-final-evidence.ps1:20-77

ReleaseBatchId 未限制为安全 opaque id，直接用于 Join-Path，且没有验证最终路径严格位于 EvidenceRoot 下。EvidenceRoot 只拒绝“恰好等于”用户 profile root，没有拒绝磁盘根、应用 data root、原始导出 root 或其父子目录，与 runbook 自身要求不一致。

metadata 禁止字段检查只查顶层属性。嵌套 body/messageText、数组内敏感字段或不同大小写 Authorization 都可进入 collector JSON。脚本还在解析和隐私验证 metadata 前创建 batch 目录，后续拒绝会留下无法用相同 batch 重试的半成品。

修改指南：

1. 对 ReleaseBatchId 使用固定正则和长度，拒绝路径分隔符、点路径、drive/UNC 和空白；canonical batch path 必须严格位于授权 EvidenceRoot 内。
2. EvidenceRoot 由 native picker receipt 授权，拒绝磁盘根、home/data/source 根及父子目录、reparse/junction。
3. 在内存中递归验证全部对象/数组节点的字段名、深度、数量和大小，再写临时目录；全部验证与 fsync 成功后原子提交。
4. 在 Windows PowerShell 实机增加路径逃逸、junction、嵌套正文/凭据和中途失败不留半成品测试。

## 5. 设计与架构

- KnowledgeStore 作为唯一 SQLite/migration owner 的边界仍保持，recovery 复用现有 Database::backup_to()，方向正确。
- rebuild 的路径授权、maintenance 时序、policy replay 和恢复状态机没有闭合；final gate 也没有复用 task 26 raw audit schema做可证明 join，而引入了一层可手填的大摘要 JSON。

## 6. 安全性

- formal blocked、release/updater disabled 必须继续保持。
- gate 绕过意味着未来只改 JSON 就可能把无真实 UAT/audit/signature/recovery 的候选伪装成 pass。
- frontend 原始路径 rebuild 和 collector 路径/嵌套 metadata 边界不足会扩大未授权读取、越界写入和敏感内容进入证据的风险。
- 恢复失败后删除 quarantine 违反“不自动删除派生旧集”的破坏性操作边界，必须先修复。

## 7. 性能、并发与事务

- verifier 能从 raw performance samples 重算 nearest-rank p50/p95 与 max；但未校验最小样本数、环境/candidate hash 和同批事实，不足以构成正式性能证据。
- manifest 准备位于 maintenance lease 外，有明确并发窗口；授权、冻结、持久化和 worker 启动应进入一个可证明的 maintenance 流程。
- 跨多文件 rename 的 publish/rollback 必须用 fault injection 验证每个局部失败，一个正常恢复测试不能替代。

## 8. 兼容性、日志与可观测性

- KB_REBUILD_SELECTION_REQUIRED 的脱敏错误映射可控，其他 rebuild 错误不回显 source path/body。
- quarantine inventory 只记录相对名与 bytes，未记录每个文件 hash，不能在恢复前复验旧集合完整性；修复状态机时应补 hash/size/type 和 generation receipt，仍不得写源路径/正文。
- collector 输出 Authenticode 公有状态，但 final gate 不读 collector schema，也不把 thumbprint/timestamp/candidate SHA-256 与 freeze 比较，两端尚未形成闭环。

## 10. 最终结论

task 27 的部分局部机制已有可运行合成测试：formal 状态诚实 blocked，performance 摘要能从 raw sample 重算，私有 manifest 有严格反序列化和 hash drift 检查，core DB backup 有 integrity 校验。
