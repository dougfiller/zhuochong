## 2. 阻断问题

### P1-1：设置页使用 snake_case，但后端 DTO 已强制 camelCase，用户的配置选择无法持久化

**证据**

- `desktop/crates/core/src/config.rs:866`、`:889`、`:932`、`:941`、`:961` 为 `WechatConfig`、`LocalEmbeddingConfig`、来源 DTO 与 `KnowledgeConfig` 标注了 `#[serde(rename_all = "camelCase")]`。
- `desktop/src-tauri/src/commands/config.rs:29-48` 直接把 `AppConfig` 序列化给前端、再把前端 JSON 反序列化为同一 `AppConfig`，中间没有字段名映射。
- 但 `desktop/src/routes/settings/Settings.svelte:83-92` 创建的是 `compatibility_profile_id`、`scope_mode`、`local_embedding` 等 snake_case 键；`SettingsWechat.svelte:29-55` 和 `SettingsKnowledge.svelte:25-47` 也持续读写这些 snake_case 键。

**影响与复现条件**

后端返回的 `wechat` 实际字段为 `compatibilityProfileId`、`textModelProfileId` 等，`knowledge` 实际字段为 `scopeMode`、`topK`、`localEmbedding`、`knowledgeSources` 等。对象存在时，`Settings.svelte` 的“对象缺失才初始化”分支不会执行字段迁移。用户在新页面选择 profile、scope 或 endpoint 后，前端会新增 snake_case 未知字段；Rust serde 不会把这些未知键写入对应 camelCase 字段。因此保存后配置仍为默认/旧值，页面与 `get_*_settings_status` 的实际状态不一致。

这违背方案中“设置仍用既有 `get_config`/`save_config`”及“配置只保存受信任 profile ID、scope 默认未选”的验收目标；当前 Rust 定向测试和 Vite 构建都无法发现这一跨端契约错误。

**修改指南（供 phase 4 执行）**

1. 选定单一 wire 约定：保留 Rust DTO 的 camelCase 时，把两个 Svelte 页面与 `Settings.svelte` 的新字段全部改为 camelCase；或移除这些新 DTO 的 `rename_all = "camelCase"` 并保持 snake_case。不得同时接受两套不受控字段而让未知键静默丢失。
2. 对已经由错误 UI 保存过的 snake_case 新字段，明确决定是否需要一次兼容迁移；若不迁移，应在发布说明中说明这些预发布配置不会生效，不能悄然保留假状态。
3. 增加端到端序列化回归：序列化 `AppConfig::default()` 后断言前端使用的键名，模拟一次 `get_config -> 设置修改 -> save_config`，再断言 profile、scope、topK、local embedding 与留存值真正变化。再为两个 Svelte 组件增加 save payload 断言。

### P1-2：loopback endpoint 校验可被 URL userinfo 绕过，不能实现“精确 loopback”安全承诺

**证据**

- `desktop/src-tauri/src/knowledge/config.rs:16-25` 通过 `strip_prefix("http://")` 和 `rest.split('/').next()` 取得整段 authority，再以 `host.starts_with("localhost:")`（以及同类 IPv4/IPv6 前缀）放行。
- 因此 `http://localhost:80@evil.example` 的 authority 会以 `localhost:` 开头而被函数接受；按 URL authority 语义，`localhost:80` 是 userinfo，真实 host 是 `evil.example`，并非 loopback。
- 现有测试 `knowledge/config.rs:34-45` 只覆盖 `0.0.0.0`、局域网 IP、https 和普通 DNS，未覆盖 userinfo、非法端口或带凭据的 authority；静态脚本也只检索错误码文本，不能验证语义。

**影响与复现条件**

步骤 5 目前不会发网络请求，所以不存在本步骤即时外连；但该函数已作为 `validate_knowledge_local_embedding` command 的唯一 endpoint 校验，并被设计为后续 embedding 的安全门。若后续实现信任该 `valid=true` 结果再连接 endpoint，恶意或误配配置可绕过“仅 `localhost` / `127.0.0.1` / `[::1]` 的 HTTP loopback”约束并连接远端服务。这是未来网络边界的 fail-open 缺陷，不能带入下一阶段。

**修改指南（供 phase 4 执行）**

1. 不要继续手写字符串前缀解析。使用已验证的 URL 解析器，强制 `http` scheme、无 username/password、hostname 精确等于 `localhost`、`127.0.0.1` 或 `::1`，端口为空或为有效数字端口；若产品只支持固定 base URL，应进一步限制 path、query 和 fragment。
2. 验证时保留“不解析 DNS、不请求网络、不云端 fallback”的行为；provider 仍须精确为 `ollama_loopback`。
3. 增加拒绝测试：`http://localhost:80@evil.example`、`http://127.0.0.1:80@evil.example`、带密码、畸形端口、IPv6 userinfo、query/fragment（若不允许）以及大小写/尾斜杠的明确策略。测试应在 command 层断言返回 `KB_EMBEDDING_ENDPOINT_NOT_LOOPBACK`，而不仅测试 helper。
