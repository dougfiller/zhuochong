## 2. 发现的问题

### P1：partial/selected 导入复制 parent 后，候选永远无法通过 message_count 就绪校验

- 证据：`store.rs:214-220` 对非 `Full` candidate 复制 parent 的所有 membership；`store.rs:291-294` 把 generation 的 `message_count` 更新为**复制后总数**。但 `archive_importer.rs:331-343` 仅累计本次文本数，并在 `archive_importer.rs:383-390` 将该数作为 `CandidateChecks.expected_message_count`。`store.rs:299-310` 要求两者严格相等。
- 影响：已有 active generation 的会话再导入 selected/filtered 包时，只要 parent 有任何成员，`mark_ready_candidate` 返回 `KB_NOT_READY`。这条路径 fail-closed，但功能上不能完成需求所述的“范围外 retained member + 覆盖内更新”。
- 缺失验证：没有“先激活 full，再导入 selected/filtered，并断言 candidate ready/active 且 retained_outside_coverage 存在”的集成测试。

### P1：实现没有确定性多 source 合并，结果仍受导入到达顺序和随机 conversation ID 影响

- 证据：`store.rs:208` 的 `source_set_hash` 仅接收当前 `NewSource`；`store.rs:213` 每个 generation 只插入当前触发 source。`store.rs:609-621` 又将随机生成的 `conversation_id` 纳入 hash。非 full 导入仅在 `store.rs:214-220` 从 parent 复制成员，随后 `store.rs:287-289` 以本次导入覆盖同一 message 的 member，`store.rs:463-476` 无条件激活当前 candidate。
- 影响：先导入较新的 source、再导入较旧 source 时，较旧正文会成为 active；相同 archive 在不同的新数据库会因随机 ID 得到不同 source-set hash。这不满足方案的固定 source-fact 排序、相同输入同一结果及“多个导出确定性合并”要求。
- 缺失验证：没有以相反到达顺序导入两个交叠 source，并比较 selected version、source-set hash、lineage 与 active snapshot 的测试。

### P1：失败包不能可靠清理已写入的 staging 正文，且多会话失败只尝试清理当前会话

- 证据：流式失败时 `archive_importer.rs:350-354` 只对当前 `staging` 调用 `discard_staging`；此前已完成的会话位于 `staged` 列表，未参与清理。`store.rs:337-355` 又先删除 `knowledge_message_versions`，但 `0001_initial.sql:53-59` 的 `knowledge_import_generation_members` 对版本的复合外键没有 `ON DELETE CASCADE`，已写 member 时该删除会被外键拒绝，generation/source 不会被继续清理。
- 影响：一个多会话包在后续会话解析/约束失败后，可在派生库留下 staging generation、source/lineage 和正文版本。它们目前不会被 `read_active_snapshot` 读出，但这不符合失败导入的完整回滚与最小留存边界，并会污染后续重试状态。
- 缺失验证：没有“第一个会话写入文本、第二个会话非法”的测试，也没有断言失败后 `knowledge_import_generations`、`knowledge_message_versions`、`knowledge_sources` 与 lineage 均不残留。

### P2：消息 ID 在整个 archive 内全局去重，与按会话建模不一致

- 证据：`archive_importer.rs:313-315` 在会话循环外创建 `message_ids`，并在 `stream_messages` 的 `archive_importer.rs:503-525` 全局拒绝重复 ID；而 `knowledge_messages` 的唯一性是 `(conversation_id, message_stable_id)`（`0001_initial.sql:41-45`）。
- 影响：两个不同会话复用同一导出内消息 ID 时会被拒绝，尽管 Store 的消息 identity 明确以会话为作用域。当前 v1 schema 未声明 message ID 全局唯一，因此不能把该假设当作输入契约。
- 缺失验证：没有双会话、相同 message ID 的合成 fixture。

## 3. 修改指南（供 phase 4 最小修复）

1. 让 readiness 校验比较一致的语义：要么将 expected count 定义为 retained + 本次有效文本，要么将“本次写入数”和“generation 总 member 数”分列保存；新增 full → selected/filtered 的回归测试。
2. 在 candidate 构建时依据持久化 source facts 收集完整 source set，并按 `exported_at`、coverage strength、manifest hash、coverage signature、export ID 的固定键决定胜出版本；hash 只包含稳定 source/conversation facts，不得包含 `opaque_id` 或导入时间。用相反导入顺序测试证明结果相同。
3. 将整包的 staging、source audit、lineage 和 candidate 激活纳入可回滚的导入事务/会话，或显式维护全部已创建 staging 的清理清单；删除时先移除 generation membership（以及其依赖），再移除版本和 source。只有候选和索引均 ready 且 activation 成功后写入可见 lineage。
4. 将 `message_ids` 的去重集合移动到单会话范围，或在 schema 中显式规定并验证全局唯一；在当前 Store identity 设计下应采用前者，并增加双会话回归测试。

## 4. 审查决定

本次验证确认现有定向命令可通过，但上述 P1 问题会使核心 partial lineage 路径失败、使多 source 结果不确定，并在失败导入时保留不应留存的 staging 数据。因此本审查**不通过**；在完成上述最小修复并补齐对应回归测试前，不建议合并或发布。
