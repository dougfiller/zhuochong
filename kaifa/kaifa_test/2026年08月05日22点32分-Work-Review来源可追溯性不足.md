## 4. 安全性与供应链

### [P1] 上游提交身份只是写入常量，未与本地快照建立内容证明

**证据：**

- `require_source()` 仅拒绝本地 `.git`、读取两个本地版本号并检查少量必需路径（`kaifa/kaifa_test/verify_work_review_baseline.py:83-94`）。同样写有 `1.1.0` 的任意本地目录都可满足这些条件。
- `write_metadata()` 把调用参数中的 tag 和 commit 直接写入 manifest（同文件 `118-167`）；`verify()` 只将 manifest 中的值与脚本默认/传入的常量比较（`209-235`），随后仅与同一本地 `--source` 逐文件比对。
- 脚本没有拉取、`git archive`、校验上游 tree hash，或将本地文件清单与官方固定提交的文件清单比较。因而本地快照即使已被篡改，只要保持两个版本字符串为 `1.1.0`，仍可生成和验证为当前宣称的 commit。

**影响：**

`desktop/` 可证明为当前本地参考目录的副本，但不能证明其内容来自所写的上游提交。这会使后续补丁差异、许可证台账、漏洞响应和升级比较失去可信基线；在该前提未补齐前，不应将此副本作为“正式产品源码基线”合并或继续开发。

**修改指南：**

1. 固定提交后，以可信远端执行 `git archive --format=tar 500f9d2cb3027392cfcc32ad18395dfe348fb4a1`（或临时浅克隆并检出该提交）取得官方文件集合；不要只使用 `git ls-remote` 的 tag 指针。
2. 对官方集合与 `参考/Work-Review-main/` 使用相同、显式的排除规则生成逐文件路径/字节/SHA-256 清单；集合或任一散列不一致即失败，且不得创建 `desktop/`。
3. 将可复核的来源证据（commit、tree hash、获取命令、文件清单或其 SHA-256）写入 manifest，并让 `verify` 在可联网时重新验证；离线时应明确报告“仅验证本地快照”，不可把它标记为上游身份已验证。
4. 修复后重新创建副本并执行：`python3 -B ... verify`、`npm ci && node --test`、`npm run build`、`cargo check --workspace --all-targets`、`cargo clippy --workspace --all-targets -- -D warnings`、`cargo test --workspace`。只有各项真实通过，才更新测试记录与解除合并阻断。
