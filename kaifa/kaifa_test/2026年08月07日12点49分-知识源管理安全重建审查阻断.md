## 1. 设计与架构

### P1：导入和重建没有异步 worker 或可轮询 operation receipt

- 证据：`desktop/src-tauri/src/knowledge/commands.rs:110-120` 和 `:152-164` 在 Tauri command 内直接调用 Store；`desktop/src-tauri/src/knowledge/store.rs:269-277` 与 `:313-324` 在同一调用栈中执行完整导入/重建后才返回 `maintenance_status()`。
- 证据：`finish_maintenance` 在 `store.rs:403-411` 将 operation 复位为 `idle/open`，因此 command 成功返回时既没有仍可查询的 operation ID，也没有保留的完成/失败结果；UI 的 `SettingsKnowledge.svelte:25-28,39-45,54-60` 只能在 invoke 未返回期间轮询，不能获得方案要求的“立即 receipt + 后台任务”的语义。
- 风险：大导出会占据 command 调用至完成；UI 在第一次状态刷新前不会立即禁用按钮，二次点击只能依赖后端失败，而不是方案要求的前后端共同防重复提交。失败后的受控错误码也无法按 operation ID 查询。
- 修改指南：将维护 lease 和状态放入 `KnowledgeStore` 的可共享 operation registry；command 仅校验 DTO、取得 lease、生成 opaque `operationId`，再启动 blocking worker 并立即返回 receipt。worker 按阶段和进度更新状态，使用 finally/guard 保证 lease 释放；`get_knowledge_maintenance_status` 必须以 operation ID 返回稳定的 running/succeeded/failed 状态。UI 收到 receipt 后先本地置 busy，再按该 ID 轮询到终态；取消、重复提交、worker 失败均应有行为测试。

### P1：候选库交换未实现成对 manifest 备份、交换后验证或失败回滚

- 证据：`desktop/src-tauri/src/knowledge/store.rs:327-380` 只将旧 `knowledge.sqlite` 重命名为 `knowledge.sqlite.backup-*`（`:362-369`）；旧 `knowledge.sqlite.manifest.json` 没有备份。随后独立重命名候选 SQLite 与 manifest（`:367-376`），并仅重新打开 SQLite（`:378-379`）。
- 证据：这段代码未执行方案所列的 `foreign_key_check`、`integrity_check`、schema/catalog/source-set/manifest 匹配复核，也没有在 `open_writer` 或任一交换后验证失败时恢复旧 SQLite 与旧 manifest 对。`write_redacted_manifest`（`:1155-1174`）只写 JSON，当前没有对应读取和一致性验证函数。
- 风险：出现交换后打开失败、manifest 与 SQLite 不匹配或进程异常时，旧 manifest 无法作为备份对恢复；实现不能证明“失败保留旧库”或“新 SQLite 与 manifest 成对匹配”。这是派生数据安全边界，不能以编译成功替代。
- 修改指南：在同一受控根目录先生成候选 SQLite/manifest，并在关闭连接后对候选执行完整完整性、外键、schema head、catalog/source-set 和 manifest 对照校验。为旧 SQLite **和旧 manifest** 创建同一代次的备份对；只在候选对复核通过后发布。发布后重新打开并再次核验，任一失败都恢复旧对、保持 `KB_NOT_READY`，且不得 copy-overwrite。为 rename 第二步失败、reopen 失败、manifest 不匹配、foreign key/integrity 失败、reader busy 与进程中断遗留候选添加临时目录行为测试。
