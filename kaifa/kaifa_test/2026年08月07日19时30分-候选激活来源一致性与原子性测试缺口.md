## 2. 阻断问题

### [P1-1] Source precedence 可被置换，候选验证也没有重放 winner/conflict 规则

**证据**

- 技术方案 `3.3` 与测试方案 `7.2.7` 要求：`precedence` 必须与固定 `SourceFact` 排序一致，并为每个 member 重放确定性 winner；同优先级不同 `content_hash` 的未决冲突必须拒绝。
- `desktop/src-tauri/src/knowledge/store.rs:2130-2178` 只按数据库中的 `precedence, source.id` 读取来源，检查 `source.1 == enumerate index`、source active/import verdict 及至少一条 provenance。
- 随后 `desktop/src-tauri/src/knowledge/store.rs:2164-2169` 把 `SourceFact` 重新排序后计算 `source_set_hash`，但没有把重新排序结果与数据库 precedence 顺序逐项比较。
- `validate_candidate_connection()` 没有调用 `incoming_source_wins()`，也没有等价的逐消息 winner/conflict 重放逻辑；新增测试 `embedding_store_is_frozen_resumable_and_exact_blob_fail_closed` 也没有 precedence 置换或错误 winner fixture。

**可复核失败路径**

假设两个来源的正确固定顺序是 A、B。把 mapping 改为 `B.precedence=0`、`A.precedence=1` 后，SQL 返回 B、A，连续性检查仍得到 0、1；代码随后再次排序为 A、B，`source_set_hash` 仍与原冻结值相同。因此被置换的 precedence 可以通过当前验证。类似地，member 只要仍有 generation source set 内的一条 active provenance，当前校验不会证明所选 version 是最高优先级 winner。

**影响**

候选可能在来源优先级或所选版本与冻结合并规则不一致时被标为 ready 并激活，破坏来源可追溯性与确定性合并契约。

**修改指南（最小范围）**

1. 在 `validate_candidate_connection()` 中保留 source id 与完整 `SourceFact`，按既有 `SourceFact::Ord` 得出 expected 顺序，并逐项断言数据库 precedence 恰为 expected index；不要先按被校验的 precedence 排序后再自证连续。
2. 对 generation 的每个 message/member 复用或抽取 `incoming_source_wins()` 的同一比较 primitive，重算获胜 source/version；若最高优先级候选留下不同 `content_hash`，返回稳定的 fail-closed 错误。
3. 增加行为测试：交换两个 precedence、选中低优先级 version、最高优先级冲突、source retired/missing/incomplete/denied；每项都断言激活失败且旧 catalog、import status 与 pointers 完全不变。

### [P1-2] 不完整 active 组合会先发起 embedding 请求，最终还会被转换成错误的 `KB_RETRIEVAL_FAILED`

**证据**

- `desktop/src-tauri/src/knowledge/store.rs:1309-1337` 的 `read_active_embedding_config()` 只要求 generation `status='ready'`；没有检查 `completed_at_ms`、catalog snapshot 一致、`activated_at_ms`、mapping/pointer 或 import active 状态。
- `desktop/src-tauri/src/knowledge/embedding.rs:447-476` 在调用该宽松读取后，立即完成 endpoint pin、模型 fingerprint 与 query embedding HTTP 调用。
- 更严格的 `load_active_embedding_read()` 位于 `desktop/src-tauri/src/knowledge/store.rs:2354-2374`，但直到后续 vector/FTS store 查询才使用；而 `desktop/src-tauri/src/knowledge/store.rs:1577-1583` 在已有 expected token 时会把这个起始不完整状态转换为 `KB_RETRIEVAL_FAILED`。
- 技术方案 `7.4.1` 明确要求 catalog snapshot 不等、ready 缺 completed、mapping/pointer/import 不完整均返回 `KB_NOT_READY`。

**可复核失败路径**

把 catalog 指向一个 `status='ready'` 但 `active_snapshot_hash != generation.snapshot_hash` 或 `activated_at_ms IS NULL` 的 generation。`read_active_embedding_config()` 仍会成功，用户 query 会先发送到本地 embedding transport；后续严格加载失败，并因 `expected.is_some()` 返回 `KB_RETRIEVAL_FAILED`，而不是要求的 `KB_NOT_READY`。

**影响**

不完整 catalog 未在请求入口 fail-closed；错误码破坏上层“未就绪不得降级”的状态语义，并在明确无可用 active 组合时产生不必要的 query transport 调用。

**修改指南（最小范围）**

1. 让 `read_active_embedding_config()` 复用 `load_active_embedding_read()` 的完整 catalog 条件，或删除宽松 SQL，避免两套 active 判定。
2. 在任何 fingerprint/query embedding 调用前完成 active catalog 与显式 scope 的只读预检；初始不完整统一保留 `KB_NOT_READY`，只有已开始的同一请求遭遇 catalog token 切换才转换为 `KB_RETRIEVAL_FAILED`。
3. 增加表驱动测试覆盖 catalog NULL、building/failed、snapshot 不等、ready 缺 completed、activated_at 为空、mapping 缺失、pointer 不等、import 非 active；断言均为 `KB_NOT_READY` 且 audit transport 调用数为 0。

### [P1-3] 新正式激活路径缺少方案要求的 DML 中途失败、busy 与进程崩溃行为测试

**证据**

- 新路径在 `desktop/src-tauri/src/knowledge/store.rs:1427-1553` 依次修改 generation ready、旧 import superseded、新 import active、conversation pointers 与 catalog。
- 本 run 新增的主测试 `desktop/src-tauri/src/knowledge/store.rs:4181-4541` 只在任何激活 DML 之前篡改 `chunk_count`，验证预检拒绝；随后从“无旧 active catalog”状态做一次成功激活。它没有在上述任一 DML 之后注入失败，也没有断言旧 active 查询持续服务。
- 现有 `writer_busy_lock_fails_closed_within_timeout`（`desktop/src-tauri/src/knowledge/store.rs:3939-3951`）锁住的是 `begin_staging_source()`，不是 `activate_validated_candidate()`。
- 仓库没有针对正式激活事务的子进程中止测试、`i64::MAX` sequence 测试或每一步 fault hook。技术方案 `7.3.1-7.3.6` 明确把这些列为验收项。

**影响**

当前 `62 passed` 能证明已有用例通过，但不能证明最危险的多表切换在中途错误、真实 writer busy 或进程终止时仍保持旧完整组合。开发日志中“原子激活、旧索引持续服务已验证”的范围因此超过现有测试证据。

**修改指南（最小范围）**

1. 仅在 `#[cfg(test)]` 下为 generation ready、每个 supersede/activate、每个 pointer、catalog CAS、final reread 增加可确定触发的 fault hook；逐点断言 rollback 后旧 catalog sequence/index/snapshot、旧 import status/pointers 和旧 FTS/vector hits 完全不变。
2. 用正式 `validate_candidate_index()` + `activate_validated_candidate()` 建立旧 active，再构造第二候选，覆盖正常切换的 `+1`、旧 superseded、新 active、全部 pointers 与 receipt。
3. 第二连接持有 `BEGIN IMMEDIATE` 超过 busy timeout，直接调用正式激活并验证旧 reader 仍可查询。
4. 增加 `catalog_generation_seq=i64::MAX` checked-add 回滚测试，以及最小子进程“commit 前终止/commit 返回后终止并重开”恢复测试；fixture 必须保持完全虚构和脱敏。
