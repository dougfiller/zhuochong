## 2. 审查结论

存在 1 个 P1 阻断问题。当前 production catalog 为空，因此 fallback 尚不能在生产路径启用；但一旦未来加入 enabled profile 和 fallback audit，该缺口会允许用**不同**冻结 probe 的 SHA-256 审计记录来启用 fallback，违背方案和实施日志所要求的“精确绑定冻结 probe”。在修复并补充反例测试前，不应宣称 fallback 审计门禁完成，也不能越过该风险建议合并或发布。

## 3. 发现

### [P1] fallback audit 未与 profile 的冻结 probe evidence SHA-256 精确相等

- 位置：`desktop/src-tauri/src/wechat/profiles.rs:44-61`、`desktop/src-tauri/src/wechat/profiles.rs:245-305`。
- 证据：`RawProfile.probe_evidence.evidence_sha256` 只被格式校验，随后没有保存到 `CompatibilityProfile`。`OcrFallbackAudit::is_approved_for` 仅调用 `is_sha256(&self.probe_evidence_sha256)`，没有将它与该 profile 的 `probe_evidence.evidence_sha256` 比较。
- 可复现性：同文件的 `fallback_audit_must_bind_to_one_exact_failed_or_unavailable_probe` 测试将 profile probe SHA 设置为 `bbbb...`，audit probe SHA 设置为 `cccc...`，却断言 `CompatibilityCatalog::parse(&profile).is_ok()`；本次执行的 38 个微信测试包含并通过该测试，说明现有测试把不匹配 SHA 当作合法配置。
- 影响：未来人工新增 audit 时，任意格式合法但不属于当前 profile 的失败/不可用 probe SHA 都会通过 parser，`WechatOcrDispatcher` 会在 primary `Unavailable`/`Failed` 后把它视为已批准并调用 fallback。这破坏了 profile 与真实 Windows probe 的可追溯性和 fail-closed 约束。

## 4. 修改指南（不在本审查中实施）

1. 在 `CompatibilityProfile` 保存已验证的 `probe_evidence_sha256`，并从 `RawProfile.probe_evidence.evidence_sha256` 赋值。
2. 在 `OcrFallbackAudit::is_approved_for` 中增加严格相等判断：`self.probe_evidence_sha256 == profile.probe_evidence_sha256`；保留现有格式校验。
3. 将现有成功 fixture 的 audit SHA 改为与 profile probe SHA 相同；增加一个仅替换 audit SHA 的反例，并断言解析返回 `Err(CatalogError::InvalidCatalog)`。
4. 将 `verify_wechat_windows_ocr.py` 从仅检查标识符存在升级为运行/检查该“相等/不等”契约，避免静态字符串检查再次漏掉语义回归。
5. 修复后重新运行本报告第 5 节全部命令；Windows target 编译和 Windows 11 x64 真机 probe 仍应作为独立发布门禁保留为 blocked，直至取得真实证据。
