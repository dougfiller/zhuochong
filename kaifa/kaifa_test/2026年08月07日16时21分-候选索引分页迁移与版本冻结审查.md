## 1. 阻断问题与修改指南

### [P1] 分页读取与无状态分块接口无法处理超过一页的会话

**证据**

- `desktop/src-tauri/src/knowledge/store.rs:1000-1058` 将每页上限限制为 256，并返回 `BuildMessagePage`/`next_cursor`。
- `desktop/src-tauri/src/knowledge/chunk.rs:77-163` 的 `chunk_messages()` 接收一个完整 slice，每次都从空 `groups/current` 开始；`desktop/src-tauri/src/knowledge/chunk.rs:151-160` 每次调用都通过 `enumerate()` 从 `chunk_index=0` 重新编号。
- `desktop/src-tauri/src/knowledge/migrations/knowledge/0004_candidate_index_chunks_fts.sql:17-18` 对 `(index_generation_id, conversation_id, chunk_index)` 建立唯一索引。
- 唯一新增 Store 行为测试 `desktop/src-tauri/src/knowledge/store.rs:2171-2189` 只读取一次第一页且 fixture 只有 2 条消息；没有继续使用 `next_cursor`。
- `cargo check` 的实际告警显示步骤 20 的 `begin_or_resume_index_build`、`read_build_message_page`、`write_chunk_batch`、`search_active_fts` 及整个 chunk 模块在生产构建中均未使用，当前没有另一个生产编排层补偿这一缺口。

**影响**

- 若调用方按设计逐页调用 `chunk_messages()`，第二页首个 chunk 又是 `chunk_index=0`，写入同一会话时触发唯一约束并返回 `KB_NOT_READY`。
- 即使调用方在内存中聚合所有页面后只调用一次，也会违反方案中“每页最多 256、chunker 只保留当前 chunk + overlap”的内存上界，并使超大单会话重新回到 O(会话消息数) 内存。
- 分页边界也无法保持前一页尾部的 token/40 条/30 分钟/最多 2 条 overlap 状态，生成结果会依赖分页方式，不能满足确定性恢复契约。

**修改指南**

1. 将 `chunk_messages()` 改为显式的有状态流式 chunker，例如由 `ChunkerState` 保存当前块、最多 2 条 overlap、下一个 `chunk_index` 和最后时间；每页输入后返回已封块 draft，最后显式 `finish()`。
2. 或提供一个 Store 内部编排器循环消费 `next_cursor`，但不得把全会话收集到 `Vec`；必须把跨页状态作为显式参数保存。
3. 增加至少 257 条、跨页恰遇 token/40 条/30 分钟三类边界的行为测试；断言无唯一键冲突、chunk index 连续、结果与不同 page size 无关、overlap 不超过 2。

### [P1] v3 中只要已有合法历史 chunk，v4 migration 提交后就会被自身 schema 校验拒绝

**证据**

- migration 在 `desktop/src-tauri/src/knowledge/migrations/knowledge/0004_candidate_index_chunks_fts.sql:10-15` 只新增可空的 `chunk_index`、`chunk_schema_version`、起止时间、token/message count，没有为已有 `knowledge_chunks` 回填这些字段，也没有明确拒绝/清空不可转换的旧 chunk。
- `desktop/src-tauri/src/knowledge/migrations.rs:112-120` 先提交 migration 和 `user_version=4`，随后才调用 `validate_schema()`。
- `desktop/src-tauri/src/knowledge/migrations.rs:253-260` 又要求每个已有 chunk 的上述字段均非空且合法。因此包含历史 chunk 的库会在 migration 已提交后打开失败。
- 临时 SQLite 探针实际执行 0001→0003、插入一个外键完整且有对应 FTS 行的虚构 v3 chunk、再执行 0004；结果显示该行全部新增字段为 `NULL`，同一 `invalid_chunk` 谓词返回 `1`，`PRAGMA foreign_key_check` 无报错。
- 当前 41 个测试没有 v3 历史 chunk 的可恢复/不可恢复迁移用例；只覆盖空库升级和 future schema 拒绝。

**影响**

- 只要已发布 v3 数据库内存在旧 chunk，即使旧 member 映射 preflight 能恢复，首次启动仍会把 schema 升到 4 后变成不可用；旧二进制又会因 future schema fail-closed，形成难以恢复的升级陷阱。
- 方案明确要求“旧 member mapping 可恢复/不可恢复”和 v3→v4 行为测试，当前实现与验收条件不一致。

**修改指南**

1. 在同一 migration 事务内定义旧 chunk 的确定性转换：回填 chunk index、schema、时间、token/message count，并验证 FTS/member/version 映射；不能可靠转换时应在提交前 fail-closed。
2. 若产品策略是不保留旧预留 chunk，应在方案和 migration 中显式、安全地清理仅非活动旧索引派生行，并证明不会影响 catalog active 数据；不能依赖校验失败代替迁移策略。
3. 将最终 `validate_schema()` 的关键迁移后检查纳入提交前事务，避免“升级已提交但打开失败”。
4. 增加 v3 空 chunk、可恢复 member、不可恢复 member、含 active catalog 的历史 chunk、重复打开和失败后 user_version/原数据不变测试。

### [P1] `fts-pretoken-v1` 只是未使用常量，没有被冻结到 index generation

**证据**

- `desktop/src-tauri/src/knowledge/chunk.rs:7` 声明 `FTS_PRETOKEN_VERSION = "fts-pretoken-v1"`，全仓作用域搜索除静态脚本和该声明外没有生产引用；`cargo test` 也实际报告该常量 `never used`。
- `desktop/src-tauri/src/knowledge/store.rs:189-195` 的 `FrozenIndexBuildSpec` 只有 chunk schema、token counter、budget 和 embedding identity，没有 FTS pretoken 版本。
- `desktop/src-tauri/src/knowledge/store.rs:1502-1517` 的冻结校验、`0004_candidate_index_chunks_fts.sql` 的持久化字段以及 `load_frozen_build()` 都不记录/比较该版本。
- 静态门禁只检查字符串存在，并固定打印 `pretoken=fts-pretoken-v1 counter=token-counter-v1`；实际 `TOKEN_COUNTER_VERSION` 是 `"v1"`。该输出不是数据库冻结证据。

**影响**

- 进程重启后恢复同一个 building generation 时，若以后修改 `fts_pretoken_v1()` 的实现或版本常量，spec 比较仍会通过；清空重建可在同一 generation/snapshot 下产生不同 FTS 文档。
- 步骤 22 无法从数据库审计或验证“索引时用了哪个 pretoken 版本”，不满足冻结配置和确定性恢复目标。

**修改指南**

1. 将 FTS pretoken 版本作为冻结字段持久化到 `knowledge_index_generations`（或明确纳入可审计、不可变的复合 schema identity），并在创建、恢复、schema 校验和步骤 22 激活前检查中一致比较。
2. 让索引侧和 query 侧都通过同一个带版本分派的入口；未知版本必须 fail-closed，不能默认调用当前实现。
3. 修正静态门禁输出，使其打印实际持久化值，不要仅凭常量名宣称版本已冻结；增加“改变 pretoken 版本不能 resume”的重开测试。

### [P1] 未知 stable scope 被当成 0 hit，而不是 `KB_SCOPE_UNRESOLVED`

**证据**

- `desktop/src-tauri/src/knowledge/store.rs:1152-1168` 只检查 scope 非空、数量、重复和 topK；没有验证请求中的每个 `(account_stable_id, conversation_stable_id)` 都能解析到唯一会话。
- `desktop/src-tauri/src/knowledge/store.rs:1179-1200` 直接把 scope 作为 `VALUES` CTE 与 `knowledge_conversations` 内连接。未知 tuple 只会令查询返回空集合，随后 `Ok(hits)`，与“已解析 scope 但确实无命中”无法区分。
- 现有测试只覆盖空 scope 和单个已存在 scope，没有覆盖未知 tuple、部分已知/部分未知或跨账户同 conversation stable ID。

**影响**

- 未来可信绑定适配器若传入过期、拼写错误或跨账户 scope，Store 会把绑定失败伪装成正常 `no_hit`，破坏 fail-closed 语义；M2 可能在错误会话范围下继续走无知识回复，而不是暴露 `KB_SCOPE_UNRESOLVED`。

**修改指南**

1. 在执行 MATCH 前，以同一个参数化 CTE 统计 requested tuple 数和唯一解析数；必须严格相等，否则返回 `KB_SCOPE_UNRESOLVED`。
2. 验证每个 tuple 唯一且 account/conversation 成对匹配；不得用仅 conversation key 的回退。
3. 增加单个未知、混合已知/未知、跨账户同 stable ID、重复 tuple 和 32/33 上限测试，并区分 `KB_SCOPE_UNRESOLVED` 与合法 0 hit。

### [P2] `write_chunk_batch()` 没有验证 draft 内容、顺序与 FTS 文档的一致性，测试也没有故障注入

**证据**

- `desktop/src-tauri/src/knowledge/store.rs:1109-1112` 写入前只检查成员非空、message index 不重复、`token_count == content.len()`。
- 它没有验证 message index 从 0 连续、首尾 version 与首尾成员一致、起止时间与成员一致、`chunk_key/content_hash/fts_terms` 由冻结版本和正文重新计算，也没有验证 draft chunk index 连续。
- `desktop/src-tauri/src/knowledge/migrations.rs:253-276` 的 reopen 校验只检查部分非空/count/mapping/FTS 一一对应，不能发现错误 content hash 或 FTS terms。
- 方案要求在 chunk/member/FTS 每一步故障注入并验证全回滚；当前测试只执行成功写入→reset→成功写入，没有注入任一步失败，也没有构造篡改 draft。

**影响**

- 后续步骤 21 的 crate 内调用方一旦传错或复用陈旧 draft，事务仍可能原子提交“结构完整但内容不一致”的 chunk/FTS，步骤 22 仅靠 count 无法可靠激活。

**修改指南**

1. 收窄 `ChunkDraft` 构造边界，或在 Store 写入前依据 frozen spec 和 member 顺序重新验证稳定 key、content hash、FTS terms、首尾 version、时间与连续 index。
2. 检查 `UPDATE ... status='building'` 和空 batch 的受影响行数；不存在/非 building generation 不能返回成功。
3. 增加 chunk insert、member insert、FTS insert 三处 fault injection、篡改 hash/terms/first-last/index、空 batch/错误 generation 的事务回滚测试。
