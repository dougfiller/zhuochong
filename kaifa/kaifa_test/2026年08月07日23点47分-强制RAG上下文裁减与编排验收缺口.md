## 2. 审查发现

### [P1] 模型实际消费完整 `context_lines`，绕过检索层每 hit 512 上限和冻结 excerpt

**证据**

- `desktop/src-tauri/src/knowledge/retrieve.rs:667-675` 只对 `payload.content` 执行 `MAX_HIT_TOKENS=512` 截断，形成 `excerpt`。
- 同一函数在 `desktop/src-tauri/src/knowledge/retrieve.rs:694-705` 却把未裁减的全部 `payload.context_lines` 原样放入 `LocalKnowledgeHit`。
- `desktop/src-tauri/src/knowledge/retrieve.rs:314-337` 将这些完整 lines 交给 `RetrievedContextParts`；`desktop/src-tauri/src/wechat/model_contract.rs:224-240` 再把全部 lines 序列化为真正的模型历史 items。
- `desktop/src-tauri/src/knowledge/retrieve.rs:774-796` 的 `frozen_result_hash` 绑定的是被截断的 `excerpt`，没有绑定模型实际消费的 `context_lines`。
- 测试夹具 `desktop/src-tauri/src/knowledge/retrieve.rs:852-871` 恰好令 `excerpt` 与单条 `context_lines.text` 相同，掩盖了生产 Store 路径的分叉。

**影响**

- 一个大于 512 的 chunk 仍可能把 512 之后的历史正文送入模型，违反“最小上下文”“步骤 23 单 hit 上限”和“模型只见入选 excerpt”的数据边界。
- `frozen_result_hash` 所声明的授权结果与实际模型上下文不是同一字节事实，无法用该 hash 复核本次实际入模内容。
- 当完整 lines 使规范 payload 超限时，步骤 25 只能删除整个 hit；这会把本可保留的受限 excerpt 整体丢弃，造成不必要的 `no_hit`/低质量上下文。

**修改指南**

1. 在 Store 同一授权读事务中生成一个唯一的“实际入模安全 item”表示；该表示必须同时用于 per-hit 上限、`frozen_result_hash`、`ModelKnowledgeContext` 和来源重取 hash。
2. 不要同时保留“截断后的字符串 excerpt”和“未截断的结构化 lines”两套可分叉事实。若不能安全地按完整 turn 裁减，则应 fail-closed，而不是把完整 lines 继续下传。
3. 新增真实 Store 行为测试：构造单 chunk 超过 512，并在 512 之后放置唯一 canary；断言 provider user prompt、context hash 对应 payload和来源详情均不含 canary，同时 frozen result 所绑定的内容与实际入模 item 完全一致。

### [P1] 两次 binding revalidate 的普通窗口/header 错误会留下活动 lease，后续请求持续 `WX_BUSY`

**证据**

- `desktop/src-tauri/src/wechat/commands.rs:134-143` 的 `validate_foreground_wechat` 和 `capture_header_identity_observation` 可直接返回窗口、截图、超时等错误；这些分支不会调用 `apply_binding_failure`，也不会终止 runtime lease。
- 第一次和第二次 revalidate 的调用方分别位于 `desktop/src-tauri/src/wechat/reply_flow.rs:340-353`、`:390-402`。错误分支调用 `finish_terminal(runtime, lease)`。
- `finish_terminal` 在 `desktop/src-tauri/src/wechat/reply_flow.rs:63-65` 仅调用 `finish_reply` 并忽略结果。
- `desktop/src-tauri/src/wechat/runtime.rs:423-428` 明确规定 `finish_reply` 只接受 `ReplyReady/Failed/Cancelled`；而上述失败发生时状态仍是 `Retrieving` 或 `Generating`，因此清理被拒绝，`inner.active` 不会释放。
- 现有 M2 测试没有覆盖生产 `generate_m2_wechat_reply` 的这两个错误分支。

**影响**

- 一次前台窗口变化、header 采集失败或 revalidate 超时即可把 single-flight 槽永久留在活动状态；之后用户再次显式触发会收到 `WX_BUSY`，直到进程重启或其他外部路径恰好失效该 binding。
- 第二次 revalidate 发生在 generating trace 已写入之后，残留 lease 还会使 trace 无终态，与阶段方案要求的 fail-closed 可审计终止不一致。

**修改指南**

1. revalidate 失败必须从当前精确状态写入 `Failed` 或 `Cancelled` 终态，再释放 lease；不能把 `finish_reply` 当作状态转换。
2. 保留原始白名单错误码，不要把窗口/header 错误无条件改写为模型或检索错误。
3. 新增两个编排行为测试：`BeforeRetrieval` 和 `BeforeModelTransport` 分别注入 `validate_foreground_wechat`/header capture 失败，断言 transport 次数为 0、trace 有唯一终态、下一次 `begin_reply` 成功。

### [P2] 现有 75 个 `wechat::` 测试没有编译或执行 Windows 生产 M2 编排函数

**证据**

- 生产函数 `desktop/src-tauri/src/wechat/reply_flow.rs:252-411` 受 `cfg(all(feature="wechat-m2", target_os="windows"))` 限制。
- 同文件测试模块 `desktop/src-tauri/src/wechat/reply_flow.rs:425` 仅在 `all(test, feature="wechat-m1")` 下启用，没有 M2 编排 seam。
- 本次在 macOS 运行日志中的 75/75 虽通过，但编译器同时报告 `generate_m2_wechat_reply` 的相关 helper/方法未使用，证明正向 M2 host 构建采用的是非 Windows stub。
- 已尝试 `cargo check --target x86_64-pc-windows-msvc ... wechat-m2`；构建在到达本项目源码前被 `libsqlite3-sys` 的交叉 C 编译环境阻塞（`stdlib.h file not found`），因此不能把它记为 Windows 产品代码通过或失败。

**影响**

- 指定日志把 75/75 描述成“M2 编排回归”，范围表述过宽；P1 的 lease 泄漏正因为生产编排未进入测试而未被发现。
- 当前没有可复核证据证明 Windows 专用函数能编译，更没有证据证明其正常/异常顺序、transport=0 和 lease 释放行为正确。

**修改指南**

1. 参考现有 M1 `finish_captured_m1_reply` seam，把 OCR 后的 M2 tail 抽成平台无关私有函数；用 fake binding revalidator、fake Store/retriever、fake transport 在所有 host 执行完整顺序与失败矩阵。
2. 在原生 Windows CI/受控 Windows 环境执行 `wechat-m2` 目标编译和 M2 tail 测试；交叉构建工具链失败只能记录为环境阻塞。
3. 更正测试记录：75/75 只能声称组件/运行时测试通过，不能声称 Windows 生产编排已经被执行。

### [P2] permit/trace 的 `model_request_id`、`requestId/stageSeq/contextHash` 未进入实际 transport spy

**证据**

- `desktop/src-tauri/src/wechat/model_contract.rs:70-119` 在 permit 中保存 `model_request_id`，但本次编译明确警告字段与 getter均未使用。
- `desktop/src-tauri/src/wechat/model_client.rs:56-76` 只用 permit 做 `validates(context)`，随后把仅含 system/user prompt 的 `SingleTurnTextRequest` 交给 transport；没有把 requestId、bindingGeneration、stageSeq、contextHash、modelRequestId 作为私有 out-of-band 审计 envelope 交给 spy。
- `desktop/src-tauri/src/wechat/reply_flow.rs:386-404` 先把独立生成的 `model_request_id` 写 trace，再用同一字符串构造 permit，但 transport 没有可观察该值的边界。
- `desktop/src-tauri/src/wechat/model_client.rs:444-470` 的 retry 测试只证明两次 prompt 相同，无法证明两个物理 attempt 与同一 request/stage/context/trace 关联。

**影响**

- 当前无法满足方案要求的“transport spy 验证实际序列化字段与 stageSeq”；trace 中的 ID 只是本地声明，不能和真实 attempt 建立可测试关联。
- `model_transport_calls` 仍记录一个逻辑调用，即使 client 内部发生两次物理 attempt，审计语义容易被误读。

**修改指南**

1. 新增仅后端可见、不会序列化给 provider 的冻结审计 envelope，携带 requestId、bindingGeneration、stageSeq、contextHash、modelRequestId、attempt 和精确 request bytes。
2. retry 只能复制同一个 envelope 并递增 attempt；fake transport/spy 必须断言两次 provider bytes 完全一致、关联字段完全一致，且与 generating trace receipt 相同。
3. 明确区分 logical model request 与 physical transport attempts 的计数/字段名称，避免 trace 把一次逻辑调用误写成一次网络 attempt。

### [P2] 只实现了历史 trace 来源入口，没有“当前建议”的本次来源入口

**证据**

- `desktop/src/routes/settings/components/SettingsKnowledge.svelte:88-106` 只能先调用 `list_wechat_reply_traces`，再从历史记录调用 `get_wechat_reply_sources`。

**影响**

- 用户生成当前建议后不能直接审查这次建议的来源，必须进入设置、手工加载历史并定位记录；“本次来源”交互没有闭环。

**修改指南**

1. 复用现有 `AvatarBubblePayload` 已有的 requestId，只增加用户显式点击入口；不要向桌宠 payload 添加 hit ID、正文、路径、score 或来源 DTO。
2. 点击后再调用 `get_wechat_reply_sources({requestId})`，保持不自动预取正文；来源消失仍逐项显示 unavailable。
3. 增加前端行为测试，证明未点击时调用次数为 0、点击时只传 requestId、失效/替换建议不能查看旧 request 的正文。
