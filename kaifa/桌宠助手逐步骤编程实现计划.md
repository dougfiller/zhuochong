## 1. 已确认的实施原则

### 1.1 以 Work Review 为正式产品继承基线，不从零开发

`desktop/` 必须由完整 Work Review 快照派生。新增代码只解决 Work Review 当前没有的微信业务边界、聊天知识库和强制 RAG 门控，不重建已有桌面能力。

路径约定：本节“优先复用的现有位置”全部是相对于只读 `参考/Work-Review-main/` 的真实工程根路径；同一路径复制后对应 `desktop/`。后文单写 `src-tauri/...`、`src/...` 或 `crates/...` 时均相对于 `desktop/`；引用既有 Work Review 文件时不使用 `commands/...`、`routes/...`、`lib/...` 或裸文件名缩写，任何步骤都不得在 `参考/` 下直接修改。

| 能力 | 优先复用的现有位置 | 本产品允许的最小修改 |
| --- | --- | --- |
| Tauri 生命周期、主窗口、托盘、单实例、自启动、更新 | `src-tauri/src/main.rs`、`src-tauri/tauri.conf.json` | 品牌、更新源、命令注册和微信显式触发入口；不新增第二套进程生命周期 |
| 前台窗口 | `src-tauri/src/monitor.rs` 的 `ActiveWindow`、`WindowBounds`、`get_active_window_fast()` / `get_active_window()` | 保留现有公开字段，最小扩展 Windows 内部窗口令牌与实际 DPI，再增加微信版本和 ROI compatibility profile 校验 |
| Windows 截图 | `src-tauri/src/screenshot.rs` 的 `ScreenshotService::capture_for_window()`、GDI BitBlt 主路径和 WGC 降级 | 抽出可复用的窗口像素采集 primitive，增加微信临时采集与窗口相对 ROI；保持普通工作截图行为不变 |

### 1.2 M1 与 M2 使用不同类型链和发布门禁

M1 临时链路：

~~~text
OcrReadyReply
→ M1ReplyInput
→ generate_m1_reply(M1ReplyInput)
→ GeneratedReply
~~~

M2 正式链路：

~~~text
CapturedWechat
→ OcrReadyReply
→ knowledge_retrieve()
→ RetrievedReply
→ build_model_context(RetrievedReply)
→ ModelKnowledgeContext
→ generate_rag_reply(ModelKnowledgeContext)
→ GeneratedReply
~~~

实施规则：

1. M1 可以独立交付，但不能把截图、OCR、模型、追踪和未来检索塞进一个文件。
2. `generate_m1_reply()` 只接受 `M1ReplyInput`，不能接收任何知识库错误对象。
3. M2 的 `RetrievedReply` 只能由 `knowledge_retrieve()` 创建，`ModelKnowledgeContext` 只能由受信任私有适配器创建。
4. `generate_rag_reply()` 只接受 `ModelKnowledgeContext`；裸 OCR、字符串、原始 hits 和 M1 类型在编译期不可调用它。
5. M2 发布构建必须删除或用 Cargo feature/编译条件硬禁用 M1 模型入口。
6. `KB_NOT_READY`、`KB_SCOPE_UNRESOLVED`、`KB_RETRIEVAL_FAILED` 都必须结束请求，不能回退到 M1。
7. `success` 和 `no_hit` 是仅有的两种可进入 M2 模型阶段的检索状态。
8. M2 最终发布不仅验收 AC-KB/AC-RAG，还要重新执行 AC-BASE、AC-WX 和 AC-PET 当前适用项，防止知识库改造破坏已交付 M1。

方案阶段与本计划步骤的固定映射：

| 开发方案阶段 | 本计划步骤 |
| --- | --- |
| 阶段 0：继承与契约 | 1—5 |
| 阶段 1：M1 手动回复 | 6—14 |
| 阶段 2：知识导入 | 15—19 |
| 阶段 3：索引与性能 | 20—22 |
| 阶段 4：M2 强制 RAG | 23—25 |
| 阶段 5：综合验证与发布 | 26—27 |

### 1.3 微信链路是封闭能力域

`wechat/reply_flow.rs` 的生产依赖只允许为：

~~~text
WechatCapture
OcrBackend
KnowledgeRetriever        # 仅 M2
WechatReplyModelClient
AvatarPresenter
ClipboardCopyGate
ReplyTraceStore
~~~

明确禁止：

1. 微信模块不得导入 `generate_text_with_model` Tauri 命令、`chat_with_tools`、通用 Agent、MCP、Bot、联网搜索、Localhost API、远程上传器或 ActionToolRegistry。
2. 微信请求不读取微信数据库、协议、内存或未选中的聊天，不注入微信，不调用 UI Automation 执行输入，不模拟鼠标键盘，不自动粘贴或发送。
3. 微信专用截图、OCR、知识命中和建议正文不得进入 Work Review 的 S3/WebDAV/远程上传队列。
4. Work Review 原有网络能力仍作为继承基线保留；“保留原功能”不等于微信请求可以调用它们。
5. 一次手动生成只冻结一个明确配置的回复 provider/model；有界重试必须保持 provider、model、请求语义和冻结知识上下文不变。
6. M2 除回复模型外只允许活动索引绑定的本机/loopback embedding；Work Review 通用 Localhost API 与 embedding loopback 是两种不同 capability，分别计数。
7. 桌宠渲染层只接收建议正文和不透明代际/显示元数据，不能取得截图、OCR、知识命中、数据库句柄、检索器或模型客户端。

### 1.4 原始聊天数据与知识库的三层格式

~~~text
只读原始 JSON/媒体
    ├──→ knowledge.sqlite + FTS5 + 本地向量
    │    （正式运行时派生层）
    └──→ 可选规范化 JSONL
         （仅调试、迁移或脱敏夹具，不是必经层）
~~~

实现约束：

- 当前开发种子为 `/Users/sky/aich8-zhuochong/微信聊天记录知识库/liaotian`；Windows 运行时必须由用户选择目录，不硬编码该 macOS 路径。
- 当前 manifest 的 `scope` 为 `selected`，所以第一个源包不得擅自当成具有删除推导权的完整全量快照。
- 原始目录始终只读；产品不写状态文件、不修复、不重命名、不移动、不覆盖、不删除源文件。
- 首期只消费 JSON 中的文本和媒体引用，不遍历、不 `stat`、不哈希、不复制约 37GB 媒体正文。
- `knowledge.sqlite` 可以删除并从原始 JSON 重建；它与 Work Review 核心数据库分离。
- importer 是唯一可直接读源 JSON 的模块；store 是唯一可打开 `knowledge.sqlite` 的模块。

### 1.5 对需求交叉项采用的实施口径

为避免编程阶段反复解释，下列口径在不修改需求基线的前提下冻结：

1. AC-WX 中明确只适用于 M2 的 embedding、`binding_generation`、`knowledge.sqlite` 条款，在 M1 矩阵标为“条件不适用”，不能删除；M2 时重新验收。
2. 实时微信回复的 M1/M2 首次发布只承诺受支持布局下的单聊。群聊仍可导入、检索并被用户显式选作知识范围，但不宣称支持群聊实时回复。
3. 默认审计只持久化 chunk ID、分数、代际和状态等非正文；用户查看来源时由 store 从当前本地知识库受控读取。只有开启内容留存后才持久化 excerpt；源已删除时显示“来源不可用”，不保留隐藏副本。
4. 首版实现一个默认关闭的“微信回复内容留存”总开关、可配置期限和一键删除。默认期限数值由第 27 步发布参数冻结，不从旧文档擅自恢复。
5. `sameConversationBoost` 只能在请求已授权的 scope 内重排，不能扩大 scope。
6. 普通 Work Review 工作截图与微信专用截图是两个数据域。本计划保证专用截图隔离；是否默认把微信加入普通工作截图隐私规则，作为发布前显式产品参数，不通过微信模块暗改原功能。
7. PNG 序列帧增强默认不实施，AC-PET 对应条件项标为不适用；这不阻断 M1/M2。

### 1.6 技术基线

| 项目 | 基线 | 说明 |
| --- | --- | --- |
| 桌面框架 | Work Review 现有 Tauri 2.9 / Rust 2021 / Tokio | 不新建 Electron、WPF 或 Python GUI |
| 前端 | Work Review 现有 Svelte 4、Vite 5、Tailwind 3 | 延续现有路由、设置、i18n 和 `*.test.js` |

| 测试 | Rust 单元/集成测试、Node test、Tauri/Windows 手工与自动探针 | 真实聊天内容不得进入源码夹具或测试日志 |

## 步骤 4：冻结微信、知识库、状态机和验收契约

**本步骤实现的功能**

先用 Rust 类型、状态迁移和脱敏夹具冻结 M1/M2 的共同语言，避免实现过程中出现可绕过 RAG 的弱类型捷径。

**具体开发任务清单**

1. 在 `wechat/types.rs` 定义 `RequestId`、`CaptureVersion`、`SuggestionGeneration`、`BindingGeneration`、`CapturedWechat`、`OcrReadyReply`、`M1ReplyInput`、`GeneratedReply` 和错误类型。
2. 在 `knowledge/types.rs` 定义 Rust 内部 `KnowledgeScope::{Conversation { id }, SelectedConversations { ids }, GlobalUserSelected}`、`KnowledgeRetrieveRequest`、私有查询组装类型 `KnowledgeRetrieveResult`、`KnowledgeHit`、`RetrievedReply` 和 catalog/index generation 类型；用逐变体 `#[serde(rename = "conversation")]`、`#[serde(rename = "selected_conversations")]`、`#[serde(rename = "global_user_selected")]` 加对应 id/ids payload，把 wire 规范形状固定为 `conversation(id)`、`selected_conversations(ids)`、`global_user_selected`，不得让 Rust/前端驼峰命名改变协议值。
3. 将 `RetrievedReply` 字段与构造器设为知识库模块私有；只有 `knowledge_retrieve()` 能把已验证的私有 `KnowledgeRetrieveResult` 封装成 `RetrievedReply`。将 `ModelKnowledgeContext` 构造器设为受信任适配器私有。
4. 定义 M1/M2 状态迁移表和严格单调 `stage_seq`，至少覆盖 idle、validating、capturing、ocr、retrieving、generating、reply_ready、copied、dismissed、cancelled、failed。
5. 定义稳定错误码 `WX_BUSY`、`WX_NOT_FOREGROUND`、`WX_PROFILE_UNSUPPORTED`、`WX_WINDOW_UNSUPPORTED`、`WX_CAPTURE_FAILED`、`WX_CAPTURE_TIMEOUT`、`WX_OCR_EMPTY`、`WX_OCR_UNAVAILABLE`、`WX_OCR_FAILED`、`WX_REQUEST_CANCELLED`、`WX_REQUEST_STALE`、`KB_NOT_READY`、`KB_SOURCE_UNSUPPORTED`、`KB_SCOPE_UNRESOLVED`、`KB_RETRIEVAL_FAILED`、`LLM_FAILED`；`OcrBackend` 的类型化结果必须区分 `Text`、`Empty`、`Unavailable` 和 `Failed`，所有错误仍进入合法 `stage_seq` 终态。
6. 明确 `no_hit` 是检索成功状态，不是错误码。
7. 分别冻结四类版本，禁止共用递增事件：`suggestion_generation` 在接受新请求时递增，并在被新建议替换、取消、主动关闭、成功复制后关闭、超时或晚到结果时失效；`binding_generation` 只在前台微信窗口实例、聊天标题/身份线索、用户选择范围、布局/profile、窗口矩形或知识会话绑定变化时递增；主 `capture_version` 只标识产生本次聊天 OCR 的采集并贯穿整个请求；`binding_observation_version` 只标识检索前/模型前的 header 复核观察。header-only 复核不得替换主 `capture_version`。新请求、复制、关闭、超时本身不得改变 `binding_generation`，晚到结果通过请求状态和既有代际校验丢弃。
8. 定义互斥的 M1 与 M2 Cargo release feature/发布配置；M2 feature 下不得编译或注册 `generate_m1_reply()`，两个 release feature 同时启用或同时未启用时用 `compile_error!` 阻止误发布。
9. 创建 `ac-applicability-matrix.md`，把 AC-WX/AC-PET 各子句标为 M1、M2 或条件适用。
10. 制作不含真实聊天的最小正常、空 OCR、重复消息、损坏 schema、重名会话、无命中和检索失败夹具。
11. 将当前只承诺单聊实时回复、群聊只作可选知识范围写入 compatibility contract。

Rust newtype/enum、serde、状态机、Cargo feature、脱敏 fixture。

**应参考的参考代码**

- **微信/知识库领域类型、M1/M2 状态机、错误码与 Cargo feature 门控：参考目录无对应实现，需原创。**
- 可借鉴的邻近模式（勿直接当微信类型用）：`参考/Work-Review-main/src-tauri/src/error.rs` 的错误分层；`crates/core/src/config.rs` 中 `TextModelProfile` / serde 兼容字段写法；`src-tauri/src/avatar_engine.rs` 的 `AvatarBubblePayload` 作为有界 payload 形状参考。

## 步骤 6：实现前台微信识别和版本化布局 compatibility profile

**本步骤实现的功能**

只在目标 Windows 微信窗口、版本和已验证布局满足条件时启动采集，其他窗口明确失败。

**具体开发任务清单**

1. 直接复用 `src-tauri/src/monitor.rs` 的 `get_active_window_fast()` / `get_active_window()` 返回的 `app_name`、`window_title`、`executable_path`、`window_bounds` 和 `is_minimized`，不把字段名改写为不存在的驼峰 API。
2. 最小修改 `src-tauri/src/monitor.rs` 的 Windows 分支：复用其当前 `GetForegroundWindow` 和 PID，通过 `GetDpiForWindow` 取得实际 DPI，并在后端伴随类型中生成含进程内不透明 `WindowInstanceToken`、PID、可取得时的进程启动时间和身份置信度。原始 `HWND` 不持久化、不写日志，也不通过 serde、Tauri event、UI 或模型 payload 暴露；后续复核必须再次读取前台 HWND/PID 并在 Rust 内部比较同一实例。
3. 微信路径要求 profile 固定的 executable/process allowlist 和可执行文件证据；现有 `src-tauri/src/monitor.rs` 在进程读取失败时按窗口标题猜出的 `app_name=WeChat` 只能用于普通 Work Review 展示，不能通过微信门禁。
4. 定义 `WechatWindowIdentity`：不透明窗口令牌、PID/进程证据、规范应用名、标题/身份线索、矩形、实际 DPI/profile 和捕获版本。
5. 在目标 Windows 探针并冻结微信小版本、可执行文件 allowlist、主题、DPI、窗口尺寸、主显示器布局、聊天 `chatRoi` 和标题 `headerIdentityRoi`，写入 `windows-wechat-v1.json`。
6. ROI 使用窗口相对比例并校验 `0 <= left < right <= 1`、`0 <= top < bottom <= 1`；profile 不匹配时返回明确错误。
7. 拒绝最小化、零尺寸、越界、非前台、正在切换或非支持 profile 的窗口。

## 步骤 7：复用 Work Review 截图 primitive 实现临时微信裁剪与隐藏恢复

**本步骤实现的功能**

获得不含本产品覆盖层的微信聊天区临时图，并确保成功、失败、超时和取消都恢复截图前状态。

**具体开发任务清单**

1. 审计 `ScreenshotService::capture_for_window()`：保留普通工作截图的归档 JPEG、OCR 临时 PNG 和现有调用行为。
2. 从 `src-tauri/src/screenshot.rs` 现有 GDI BitBlt/WGC 路径抽取共用的窗口像素采集 primitive，新增仅供微信使用的 ephemeral 模式；不得为此复制一套 Windows 截图库。结果使用 `EphemeralCapturedFrame { pixels, width, height, origin_x, origin_y, coordinate_space }`，因为现有代码实际可能捕获窗口所在显示器，不能只凭宽高推断窗口在帧内的位置。
3. 内容留存关闭时，ephemeral 模式只返回内存图，截图在任何阶段都不得落盘，也不得创建 `ocr_source_path` 或其他临时截图文件；若现有 Windows OCR 入口只接受路径，必须先补充字节/内存输入适配，不能用临时文件绕过 AC-WX。
4. 增加共享 `CaptureCoordinator`，短时暂停/串行化 Work Review 普通后台截图与微信 ephemeral 截图；等待前端隐藏确认和 capture worker 时不得持有整个 `AppState` mutex。
5. 实现 `WechatCaptureGuard`：快照桌宠/气泡/卡片/主应用可见性、展开状态、位置和鼠标穿透，隐藏全部产品覆盖层，等待前端/窗口隐藏确认后再截图。
6. guard 的所有权必须跟随实际 GDI/WGC capture worker；只有 worker 已确认完成或实现真正取消后才能恢复。不得用 `tokio::timeout(spawn_blocking(...))` 提前丢弃 handle，再让不可取消的 WGC worker 在恢复桌宠后继续取帧。
7. 截图前、worker 完成后都重新核对 HWND token、PID、bounds、DPI、前台状态和 profile；任一变化立即销毁图像。正常、错误、超时、取消和 panic-safe 路径恢复原状态且不得激活主窗口或夺走微信焦点。
8. 先用 `window_global - capture_origin` 换算帧内坐标，并验证逻辑坐标/物理像素/DPI 一致，再裁微信窗口、`chatRoi` 与 `headerIdentityRoi`；不能把“所在显示器截图”直接当聊天图。
9. 每次主聊天裁剪生成新的 captureVersion，并绑定 requestId、window identity 和 profile version；窗口矩形变化生成新版本并使旧图失效。后续只为 binding 复核采集 header 时生成独立 bindingObservationVersion，不能覆盖本请求的主 captureVersion。
10. 只有用户明确开启内容留存时，才允许把截图写入独立微信内容目录并登记期限；OCR 中间对象在请求终止后释放。关闭留存后立即停止新的截图/OCR/excerpt/建议正文写盘。
11. 为嵌套隐藏、重复恢复、窗口关闭、迟到 WGC worker、后台截图竞争、捕获原点、DPI、负坐标和副屏建立 fake/window 单元测试。
12. 在真实 Windows 分别注入成功、截图失败、超时和取消，证明截图中没有桌宠/气泡，结束后微信仍前台。

**涉及的关键技术/框架/库**

Work Review GDI/WGC、`image` 裁剪、Tauri WebviewWindow、RAII 清理守卫、取消/超时。

**应参考的参考代码**

- 窗口截图像素主路径：`参考/Work-Review-main/src-tauri/src/screenshot.rs` 的 `ScreenshotService::capture_for_window()`、`capture_with_gdi()`（BitBlt）、`capture_with_wgc()` 降级。

## 步骤 8：建立 Windows OCR 专用后端和条件本地 OCR fallback

**本步骤实现的功能**

只在本机把聊天区图片转成规范化文本，并在 OCR 不可用或无文字时停止后续流程。

**具体开发任务清单**

1. 定义最小 `OcrBackend` trait 和 `OcrBackendResult::{Text, Empty, Unavailable, Failed}`，只有 `Text` 能构造 `OcrReadyReply`；不让 reply flow 依赖具体进程或脚本。
2. 从 `src-tauri/src/ocr.rs` 的 `OcrService` 暴露可测试的 Windows OCR 调用，复用现有 PowerShell/Windows OCR、文本清理、超时和错误映射，并补充内存图输入。
3. 微信首选后端固定为现有 `OcrEngine::WindowsOCR`。为避免 `OcrService::new()` 初始化时“确保 `paddle_ocr.py` 存在”的无关写盘副作用，抽出或暴露仅构造 Windows OCR 的专用路径；现有 Windows 实现没有 cloud OCR 分支，不得以不存在的 Paddle/cloud 优先级作为新适配器理由。
4. 在目标 Windows 用冻结聊天 ROI 样本做中文、英文、混排、空白和低对比度探针，记录可用性与错误。
5. 只有 Windows OCR 探针失败时才审计路线 A：`参考/Umi-OCR-main` 已能证明的是 Umi-OCR.exe 及本地 HTTP/CLI 调用方式；适配前必须冻结版本、哈希、许可证、命令参数、串行限制、隐藏界面行为、服务线程和正常/异常退出清理，不得把它直接描述为现成无 GUI 引擎。
6. 若路线 A 的 GUI/服务生命周期不满足单进程产品边界，再审计路线 B：另行取得独立 RapidOCR-json/engine，验证来源、许可证、模型文件、哈希、真正无界面启动、并发/串行语义和退出清理后，才可实现为后端；当前参考目录不能替代这项证据。
7. 任一 fallback 只实现图片到文字，不持有桌宠、知识库、模型、托盘、自启动或更新职责，也不能产生第二个用户可见应用壳。
8. OCR 请求只接受内存图；禁止远程 OCR、媒体下载或任意用户命令拼接。若候选 fallback 只能读文件且无法满足内容留存关闭时截图不落盘，则该候选验收失败。
9. 规范化换行、空白和不可见字符，设置最大输入/输出边界；真实正文不写普通日志。
10. `Empty` 写 `WX_OCR_EMPTY`，`Unavailable` / `Failed` 分别写 `WX_OCR_UNAVAILABLE` / `WX_OCR_FAILED`，并全部终止，模型 transport spy 计数保持 0。
11. 探针和边界审计完成后固定单一生产后端；fallback 的启用依据是冻结实机探针中的 `Unavailable/Failed`，不能因某次空白截图返回 `Empty` 就在运行时切换后端。

**涉及的关键技术/框架/库**

## 步骤 11：实现 M1 手动微信回复后端编排闭环

**本步骤实现的功能**

后端在一次显式请求中完成前台校验、隐藏截图、本地 OCR 和单模型建议，并把有效结果交给第 12 步实现的 `AvatarPresenter` 边界；本步骤尚不宣称用户可操作的 M1 纵向闭环完成。

**具体开发任务清单**

1. 在 `wechat/reply_flow.rs` 实现 `generate_wechat_reply` 门面，按状态机创建 requestId 并取得 single-flight。
2. 触发后如需倒计时，等待用户切回微信；随后重新校验 `WechatWindowIdentity`。
3. 调用 `WechatCaptureGuard` 获取聊天 ROI，保证 guard 恢复后再进入耗时 OCR/模型阶段。

## 步骤 21：复用嵌入/向量/RRF primitive 并强制本地 loopback

**本步骤实现的功能**

## 步骤 23：实现唯一 knowledge_retrieve() 混合检索门面

**本步骤实现的功能**

为 M2 提供唯一、范围受限、可审计的本地检索入口，并对无命中与故障作出不同处理。

**具体开发任务清单**

1. 在 `knowledge/retrieve.rs` 实现唯一公开业务门面 `knowledge_retrieve(request) -> Result<RetrievedReply, KnowledgeError>`。私有 `run_retrieval()` 可以先组装 `KnowledgeRetrieveResult`，但只有同文件/模块的私有构造器能把 `success | no_hit` 封装为字段不可见的 `RetrievedReply`；微信编排层不能导入构造器，任何 `KnowledgeError` 都不能产生 `RetrievedReply`。
2. 请求 wire shape 必须包含 `request_id`、规范化 `query_text`、`binding_generation`、显式 `scope`、`top_k`、`token_budget` 和 `token_counter_version`；`RetrievedReply` 绑定 `request_id`、规范化 query、活动 `index_generation_id`、`binding_generation`、冻结结果 hash，并完整封装 `status`、`retrieval_mode`、`hits[]` 和 `elapsed_ms`。
3. 读取 `knowledge_catalog_state` 和活动 indexGeneration 冻结的 embedding 配置；无活动 ready 组合返回 `KB_NOT_READY`。
4. 生成本地查询向量并执行向量召回；本地 embedding 不可用时跳过向量并保留 FTS。
5. 执行 FTS 召回，用共享 RRF 融合、去重并排序。
6. 在 store/SQL 查询层同时应用活动 indexGeneration、`knowledge_denials`、source state/provenance 和 wire 值精确为 `conversation(id)`、`selected_conversations(ids)` 或 `global_user_selected` 的 scope；借助 `knowledge_chunk_messages` 验证 chunk 中每条消息至少有一个 `active` 来源，某个来源 retired/missing 但同一消息仍有其他 active provenance 时可保留，否则阻断整个 chunk。不得先全库召回再在展示层过滤，Rust/前端内部命名也不得改变三个 serde 判别值。
7. 按 topK、单 hit 上限和版本化 tokenBudget 生成有界 hits；完整本地 hit 至少保留 knowledgeChunkId、conversationId、sourceMessageRange、sourceTimeRange、sourcePath、excerpt 和 score。
8. 没有相关结果返回 `status=no_hit`；向量失败但 FTS 成功返回 `retrievalMode=fts_fallback`。
9. SQLite、索引、scope 或结果组装错误返回错误并停止，不调用回复模型。
10. `sameConversationBoost` 只在 SQL/Store 已产出的授权候选集合内重排；开关前后 conversation ID 集合必须完全相同，只允许顺序/分数变化。
11. retriever 只依赖 KnowledgeStore 类型化查询和 local embedding，不调用回复模型、UI、上传、MCP、Bot 或搜索。
12. 默认 trace 只持久化 hit IDs/scores；来源查看按权限从 store 受控重取正文。
13. 测试三种 scope 的精确 wire 序列化、越界会话、boost 集合不变、noHit、FTS fallback、索引损坏、数据库 busy、token 截断、响应完整字段和模型调用数为 0。

**涉及的关键技术/框架/库**

KnowledgeStore、FTS5、向量召回、RRF、token budget、显式 scope。

**应参考的参考代码**

- 混合检索门面算法源：`参考/Work-Review-main/src-tauri/src/commands/semantic_memory.rs` 的 `search_semantic_memory_inner()`（向量召回 + FTS + RRF）；FTS/BLOB Top-K 底层见 `crates/core/src/database.rs`。

## 4. 关键状态、事务与调用顺序速查

| 场景 | 必须采用的顺序/事务规则 |
| --- | --- |
| 新建微信请求 | 锁 reply runtime → 确认 idle → 生成 requestId/suggestionGeneration → 写 stageSeq=1 → 释放锁；不能持锁执行截图/OCR/网络 |
| 倒计时后采集 | 重新读取前台窗口 → 校验 WeChat/profile → 快照覆盖层状态 → 隐藏并等待确认 → 截图/裁剪 → guard 恢复 → 再进入 OCR |
| M1 模型 | OCR success → 私有构造 M1ReplyInput → 冻结一个 ModelConfig → 有界无工具调用 → 复核 request/capture/suggestion generation → 显示 |
| M2 模型 | 主聊天 OCR success → header-only observation 复核 binding（不替换主 captureVersion）→ await knowledge_retrieve → 冻结 RetrievedReply/context hash → 新 observation 再复核 binding → generate_rag_reply → 复核全部代际 → 显示 |
| 复制建议 | 前端传 requestId/suggestion/binding generation → 后端校验并返回当前正文 → navigator.clipboard 写入 → 成功确认后关闭；任一失配拒绝 |
| 导入小批写 | 只写 staging importGeneration/不可变 versions/membership → 会话计数通过后 readyCandidate；不改 active pointer |
| overlay 导入 | 锁 candidate conversation → 复制经验证 parent membership → 替换本次所见消息 → filtered/incremental/unknown 不删除缺席项 |
| full 删除推导 | 验证同账户、同 coverage、完整 manifest/filters/count 和 predecessor → fullReplace membership → 仅其他 active source 也不含时删除/tombstone identity |
| 索引构建 | 固定 readyCandidate snapshot/config → 写 building chunks/FTS/vectors → 校验计数/维度/外键 → 标 ready |
| catalog 激活 | `BEGIN IMMEDIATE` → 重验 candidate mapping/ready/deny/conflict → 新 import generations 标 active、旧 active 标 superseded → 按 mapping 更新各 conversation `active_import_generation_id` → 写 `active_import_snapshot_hash` / `active_index_generation_id` / `activated_at` → 递增 `catalog_generation_seq` → commit |
| 用户移除知识 | 先写 deny/tombstone 或将 scope 标 KB_NOT_READY → 后台构建新候选 → 原子切换；不能在等待期间返回旧已移除命中 |
| 删除并重建知识库 | maintenance barrier 拒绝新任务 → 取消并等待在途任务 → 写非正文 rebuild manifest → 关闭全部 Store 连接 → 隔离 DB/WAL/SHM → migration/重导入 → 新 session/catalog/binding 失效 |
| 来源查看 | trace hit ID → KnowledgeStore 在当前 active/允许范围内重取 → 本地 UI 显示；默认不从 trace 读取持久化 excerpt |
| 回复重试 | 只重试同 provider/model/endpoint、同 requestId、同 payload 语义；M2 复用同一 RetrievedReply/context hash |
| 任一失败 | 写合法终态/错误码 → 取消未开始的后续阶段 → 释放内存敏感对象并清理仅在留存开启时产生的受管文件 → 等实际 capture worker 结束后恢复覆盖层 → 禁止自动切 provider、scope、工具或 M1 |

## 6. 正式联调和发布前必须冻结的外部参数

以下参数不阻塞 fake/脱敏夹具开发，但会阻塞对应真机、性能或正式发布验收：

1. 目标 Windows 11 构建号、CPU、内存、磁盘类型/可用空间和显示器拓扑。

2. 被支持的 Windows 微信 4.0.x 精确小版本、主题、DPI、窗口尺寸、主/副屏布局和聊天 ROI。

3. 产品正式名称、bundle identifier、binary 名、图标/人物素材授权、签名证书、时间戳服务、更新域名、公钥和发布渠道。

4. 用户明确选择的单一回复模型 provider、model、base URL、API key，以及经探针冻结的超时、重试上限、temperature 和输出上限；密钥不得写入本计划或仓库。

5. Windows 正式导入目录选择方式和用于 UAT 的冻结聊天导出 exportId/manifest hash；当前 macOS `liaotian` 只作开发种子。

6. 本地 embedding 服务、模型、endpoint、模型文件/服务指纹、向量维度、批大小和中文检索基准；必须通过 loopback 与性能探针后冻结。

7. “微信回复内容留存”的默认期限数值，以及是否默认把微信加入普通 Work Review 工作截图隐私规则；未确认前保持专用内容留存关闭且不暗改原功能。

8. 如果 Windows OCR 探针为 `Unavailable/Failed`：路线 A 冻结 Umi-OCR HTTP/CLI 的确切版本、二进制/模型哈希、许可证、分发方式、隐藏界面、串行限制以及 GUI/服务退出生命周期；路线 B 需另行取得并审计 standalone RapidOCR-json/engine 的来源、版本、哈希、许可证、真正无界面启动与退出清理。两者都不能读取命名临时截图；探针成功则不引入。

9. 业务 UAT 问题集、期望回复风格、单会话/多会话/全库代表样本和人工验收人。

10. 首次全量索引、查询 p50/p95、峰值内存、派生库体积、Work Review 调度漂移和 UI 响应的最终数值上限。

11. 安装升级、知识库重建、配置/核心库备份、M2 同阶段回滚和故障响应负责人。

以上参数未冻结时，可以完成相应 fake、契约、单元和脱敏集成测试，但不得把真实连通性、目标机性能、素材合规或正式发布标为通过。
