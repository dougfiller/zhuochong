## 0. 已确认的产品决定

1. 正式产品直接从 Work Review 派生，不另做临时壳，不把整套产品重写为 Python。
2. Work Review 原有能力是正式产品的继承基线，不是待以后重新开发的需求池；新增微信功能不得破坏这些能力。
3. 首个阶段先完成可运行的微信回复闭环；知识库/RAG 是已经确认的后续阶段，不再作为未知可选项。
4. 从 M2 开始，每次微信文字进入回复生成流程后，必须先完成一次 `knowledge_retrieve()`，再允许调用大模型；M1 是知识库接入前的阶段性闭环，不得冒充已完成 RAG。
5. 当前聊天记录导出目录是知识库的主要原始来源，但现有 JSON 目录结构不是永久的内部存储格式。
6. 原始 JSON 只读保留；正式产品将其导入规范化 SQLite、FTS5 与向量索引。JSONL 只可作为可选的流式中间格式或调试导出格式。
7. Work Review 的网络、MCP、Bot、Localhost API、远程上传和行动工具可以继续存在，但微信回复链路不得自动调用它们。微信手动“生成建议”唯一允许的网络例外，是调用用户明确配置的一个回复模型。
8. 微信回复仍只提供建议和复制；最终粘贴、修改与发送始终由用户完成。
9. `参考/VPet-main` 仅作为桌宠交互、动画资源组织、缓存和多屏边界的只读设计参考；它不改变 Work Review 是唯一正式产品底座的决定。
10. 正式产品不得引入 VPet/.NET/WPF 桌宠运行时或 GUI sidecar，不得形成第二套桌宠窗口、托盘、自启动、更新器或生命周期。
11. 可以在现有 Rust/Svelte 桌宠内独立实现 VPet 中有价值的动画语义；VPet 的 Steam/Workshop、代码 MOD、遥测、任意程序/URL 启动、输入模拟、养成系统和内置素材均不进入 M1/M2。PNG 序列帧增强不是 M1/M2 阻断项，Live2D 仍等待用户另行确认。

## 1. 产品定义与阶段边界

本产品是在 Work Review 桌面应用上增加微信回复建议和个人聊天知识库能力的正式派生产品。

### 1.1 阶段 M1：继承基线与微信回复闭环

```text
当前前台微信单聊
→ 用户明确触发
→ 截图并裁剪聊天区
→ 本地 OCR
→ 形成待回复文字
→ 调用 M1 专用无工具模型入口生成一条建议
→ 桌宠气泡显示
→ 用户点击复制并自行发送
```

M1 必须同时满足两项结果：

- 新增微信回复闭环可运行。
- Work Review 核心原有功能通过回归验收，而不只是保留源码和入口。
- M1 使用临时且独立的 `M1ReplyInput -> generate_m1_reply()` 类型入口；M2 发布后该入口必须被移除或禁用，绝不能在检索失败时充当绕过 RAG 的后门。

### 1.2 阶段 M2：聊天记录知识库与强制 RAG

```text
微信待回复文字
→ knowledge_retrieve()
→ 混合检索聊天记录知识库
→ 组装命中文段、来源和检索状态
→ 调用模型生成建议
→ 保存检索追踪信息
→ 桌宠气泡显示建议
```

M2 是已确认交付阶段。M1 可以先于 M2 完成，但不得把 M2 从开发路线、数据设计或验收计划中删除。

### 1.3 “每次先检索”的准确含义

- 从 M2 开始，无论采用手动触发还是其他以后经过确认的触发方式，只要本次流程准备调用大模型生成微信回复，就必须先调用 `knowledge_retrieve()`。
- 当前 M1 可以先用可见聊天区的规范化 OCR 文本作为输入。
- M2 只允许 `RetrievedReply -> ModelKnowledgeContext -> generate_rag_reply()`；`ModelKnowledgeContext` 只能由私有适配器从检索结果构造，`OcrReadyReply`、裸字符串和 M1 输入类型都不能调用该模型入口。
- 若要严格做到“每一条新收到的对方消息”分别触发，必须在后续增加新消息提取、我方/对方方向判断、消息哈希去重和请求版本绑定；在这些能力完成前，不得宣称已经实现逐条新消息识别。

## 2. Work Review 正式产品继承基线

### 2.1 必须继承的能力

以下 Work Review 能力整体保留，并继续作为同一个正式产品的一部分：

- Tauri 2 桌面外壳、主窗口、托盘、单实例、自启动、暂停与恢复。
- 前台应用、窗口标题、浏览器 URL、使用时长、应用分类和空闲状态记录。
- 概览、时间线、活动详情、小时汇总、日报、周报和 Markdown 导出。
- 普通工作截图、现有 OCR、隐私过滤、存储管理和数据清理设置。
- 工作助手、模型配置、基础模板、AI 增强和现有语义记忆。
- 设置页、多语言界面、桌面化身、状态气泡和已有提醒能力。
- S3/WebDAV 远程存储、Localhost API、Bot、MCP、联网搜索及其他已有可选集成。

### 2.2 继承原则

- 以 Work Review 完整工程为底座开发，不拆出另一套重复应用。
- 能调用现有函数和模块时直接复用，不复制后再用另一种语言重写。
- 原功能允许因品牌、应用标识、更新源、签名和产品边界做必要适配。
- MIT 许可证、版权声明及第三方声明必须随正式发行物保留。
- 上游可选网络能力默认保持隔离；保留功能不等于允许微信回复流程自动使用。

### 2.3 微信链路能力白名单

微信回复流程只允许依赖以下能力：

- 前台窗口读取与截图。
- 聊天区裁剪与本地 OCR。
- 本地知识库导入、索引与 `knowledge_retrieve()`。
- 本地嵌入/FTS 检索和用户明确配置的回复模型。
- 桌宠状态、气泡和用户点击复制。
- 本地检索追踪与必要日志。

微信回复流程不得直接或间接调用：

- Work Review 远程上传、S3、WebDAV。
- MCP、Localhost API、Bot、联网搜索或通用行动工具。
- 自动控制微信的 UI Automation、鼠标键盘操作、输入、粘贴或发送。
- 与本次回复无关的工作记录外发能力。

知识库导入器是唯一可以读取原始聊天 JSON 的模块；`knowledge/store` 是唯一持有 `knowledge.sqlite` 连接的模块。导入器、chunker 和 retriever 只能通过 store 的类型化 API 写入/查询，不能各自打开数据库。模型客户端、微信编排器、桌宠、通用 Agent、MCP、Bot、Localhost API 和远程上传模块均不得直接读取原始聊天 JSON、数据库文件或任何 `knowledge_*` 表；微信编排器只能通过 `knowledge_retrieve()` 获取有界结果。

### 2.4 桌宠渲染与 VPet 参考边界

- Work Review 的 Tauri 桌宠窗口继续作为产品唯一的桌宠窗口和生命周期所有者；窗口位置、置顶、鼠标穿透、拖动、跨屏、状态和气泡都在现有产品进程内管理。
- 可借鉴 VPet 的 `Start/Loop/End` 动作阶段、动作变体与 fallback、数据驱动资源清单、序列帧缓存、归一化点击区域、拖动锚点及屏幕边缘/多显示器测试思路，但必须在现有 `avatar_engine.rs` 与 `routes/avatar/` 边界内用 Rust/Svelte 独立实现。
- 当前 M1/M2 继续使用 Work Review 已有桌宠渲染路径。只有在用户提供自有或已授权素材并单独确认增强后，才允许增加渲染器中立的 PNG 序列帧清单；该增强不得改造窗口壳，也不得阻塞微信回复与 RAG。
- 若启用 PNG 序列帧增强，资源清单必须版本化并至少描述逻辑画布、动作、`single/start/loop/end` 阶段、帧时长、状态映射、fallback、点击区域和拖动锚点。`idle`、`working`、`generating`、`reply_ready`、`error`、`dragging` 等产品状态必须有确定映射；缺失或损坏资源必须回退到可见的 `idle`，不能白屏或卡死。
- 资源清单只能声明受信任的数据文件，不能声明 DLL、脚本、命令、URL 或可执行入口。桌宠渲染层只消费最终建议正文与不透明显示/失效元数据，永远不得取得 `RetrievedReply`、任何知识命中、原始截图/OCR、聊天导出或知识库源路径、数据库句柄、检索入口或模型客户端。
- VPet 源代码与素材分别判断授权。默认采用“行为规格后独立实现”和本产品自有素材；如确需复制 Apache-2.0 代码，必须登记来源，随发行物提供许可证副本，保留源文件中适用的版权、专利、商标和归属通知，存在 NOTICE 时保留其适用内容，并在修改文件中显著标记修改。VPet 动画、图片、字体、图标、Logo、品牌和其他二进制素材不得推定为 Apache-2.0。本产品采用额外的严格门禁：只有逐文件取得可审计的书面商业授权并登记适用条件后才允许使用；这是一项内部发行政策，不是对 VPet README 素材条款的转述。
- M1/M2 不嵌入 `VPet-Simulator.Core`、VPet 程序集或 WPF 控件，不接入 Steam/Workshop、Talk API、MOD/DLL loader、原作者遥测/反馈、`SendKeys`、任意程序/URL 启动、游戏存档或养成系统。

## 3. 微信回复功能需求

### FR-WX-01 手动触发与前台窗口

- M1 只要求用户明确触发一次回复建议流程。
- 真正采集时，当前前台窗口必须是支持范围内的微信窗口。
- 点击入口使微信失去前台时，可以显示短暂倒计时让用户切回微信。
- 当前前台不是微信、已有请求执行中或窗口状态不支持时，显示明确错误并结束。
- 同一时刻只处理一个回复请求。

### FR-WX-02 截图与聊天区裁剪

- 复用 Work Review 的窗口信息和截图实现，但不得把“所在显示器截图”等同于“聊天区截图”。
- 截图前临时隐藏本产品桌宠和气泡，成功或失败后都必须恢复。
- 隐藏范围必须覆盖桌宠本体、气泡、卡片及其他可见覆盖层；编排器确认隐藏完成后才允许截图。
- 截图编排必须使用统一清理守卫，在成功、失败、超时和取消路径恢复截图前的可见性、展开状态、位置与鼠标穿透设置；恢复不得抢占微信前台焦点。
- 先根据前台窗口矩形取得微信窗口区域，再按经过实机验证的 ROI 裁出聊天区。
- 首期只承诺一个微信小版本、主题、DPI、窗口尺寸和主显示器布局。
- 只有聊天区裁剪图可以作为微信 OCR 输入；仅在用户开启 FR-WX-06 的内容留存后，才允许保存到独立微信记录目录。
- 截图过程不得点击、滚动、切换聊天对象或改变微信内容。

### FR-WX-03 本地 OCR 与待回复文字

- 聊天区图片必须在本机完成 OCR，不把图片发送给远程 OCR 服务。
- 首选 Work Review 的 Windows OCR；目标机器不可用时才固定切换到经过验证的本地 RapidOCR 路径。
- OCR 失败或无文字时不得进入检索和模型阶段。
- M1 可使用规范化后的可见聊天文本。
- M2 若启用逐条消息模式，必须先识别最新对方文字、排除我方消息并按稳定消息哈希去重。

### FR-WX-04 回复生成

- 复用 Work Review 现有模型配置和基础模型客户端，但微信回复使用无工具的一次性生成入口。
- 微信模块只能依赖封闭的 `WechatReplyModelClient`，不得直接导入 Work Review 的通用 `generate_text_with_model`、`chat_with_tools` 或 Agent 入口；`RetrievedReply` 字段和构造器对微信编排层私有，只能由检索边界返回。
- 微信回复不得进入带 MCP、网页搜索、远程上传或行动工具的通用 Agent 工具循环。
- 用户的一次手动“生成建议”动作，只授权调用当前明确配置的一个回复模型；允许同一提供商、同一模型、同一请求语义下有上限的传输重试，但不得自动切换提供商、模型或工具模式。
- M1 使用 `M1ReplyInput -> generate_m1_reply()` 和固定提示词生成一条简短、自然、可复制的中文建议；该入口不得接收知识检索错误作为输入。
- M2 使用 `RetrievedReply -> ModelKnowledgeContext -> generate_rag_reply()`；发送给模型的上下文只包含本次待回复文字、token 预算内的命中摘录、必要时间/角色信息和数据边界说明，不直接发送完整检索审计对象。
- M2 启用后，M1 模型入口必须移除或由发布配置硬禁用，不得成为 `KB_NOT_READY`、`KB_SCOPE_UNRESOLVED` 或 `KB_RETRIEVAL_FAILED` 的降级路径。
- M1/M2 除上述一个回复模型外，其他非 loopback 外部 egress、MCP、Bot、Localhost API、上传、搜索和行动工具调用计数都必须为零；M2 允许并单独计数 `knowledge.localEmbedding` 的本机/loopback 调用。
- 模型失败、超时或返回空内容时显示失败信息，不生成可复制的伪建议。

### FR-WX-05 桌宠气泡与复制

- 复用现有桌宠窗口和气泡，不改变普通工作提醒气泡的既有行为。
- 微信建议使用持续气泡，直到用户复制或主动关闭。
- 只有用户点击“复制”后才允许写入剪贴板。
- 产品不得自动聚焦微信、自动输入、自动粘贴或自动发送。
- 微信建议只通过现有 Work Review 桌宠事件和气泡路径显示，不创建第二个桌宠窗口或消息窗口。
- 微信持续气泡必须提供明确的“复制”和“关闭”动作。显示、悬停、拖动、普通状态变化和关闭均不得写入剪贴板；复制只能写入当前仍有效且可见的建议，`suggestion_generation` 失效或 M2 `binding_generation` 失效时不得复制。
- 微信持续气泡显示期间，普通状态气泡和已有提醒不得静默覆盖它；复制、主动关闭、`suggestion_generation` 失效或 M2 `binding_generation` 失效后，普通气泡行为恢复。
- 桌宠渲染层只接收建议正文、`request_id`、M1/M2 都有的 `suggestion_generation`、M2 适用的 `binding_generation` 和显示状态等有界 payload；不得接收 `RetrievedReply` 或任何知识命中，也不得直接调用 OCR、知识检索或回复模型。

### FR-WX-06 本地追踪与内容留存

- 每次 M1/M2 请求始终只写入最小、非正文的本地追踪：`request_id`、单调递增的 `stage_seq`、阶段状态、时间、错误码和模型传输计数。
- 聊天区裁剪图、OCR 正文、知识命中正文和建议正文默认不落盘；只有用户在独立的本地隐私设置中明确开启后才可保存。
- 内容留存使用独立的本地保留期限和“一键删除微信回复内容”入口；关闭后新请求立即停止保存正文，默认值为关闭。
- 微信回复追踪与内容不得自动导入聊天知识库，也不得进入 Work Review 远程上传扫描范围或任务队列。

### FR-WX-07 M2 检索范围绑定

- M2 首次使用或范围变化时，产品必须提供明确的范围选择 UI：绑定一个知识库会话、选择多个会话或用户确认全库；不得只靠 OCR 文本/同名标题自动猜测。
- 单会话绑定由用户从已导入会话中确认；重名联系人/群必须展示群标记、时间范围、消息数等本地元数据帮助区分，仍无法区分时不得建立绑定。
- 每个绑定保存 `binding_generation`。前台微信窗口、聊天标题/身份线索、用户选择范围、布局或会话发生变化时递增代际，并使旧 OCR、检索结果和待显示建议失效；请求在模型传输前必须再次核对代际。
- 不能可靠识别当前聊天且用户没有为本次请求确认其他范围时返回 `KB_SCOPE_UNRESOLVED`；允许用户每次重新确认，但不得自动退到全库。

## 4. 聊天记录知识库源数据

### 4.1 当前原始目录

当前开发和分析使用的只读源目录为：

```text
/Users/sky/aich8-zhuochong/微信聊天记录知识库/liaotian
```

截至 2026-08-04 的结构探查结果为：

- 根目录包含 `manifest.json`、`report.json`、`_integrity/`、`conversations/` 和 `media/`。
- `conversations/` 中约有 721 个会话目录，每个会话当前包含 `meta.json` 和 `messages.json`。
- 约有 402,673 条消息；单个会话最多超过 100,000 条消息。
- 整体约 37GB，主要体积来自图片、文件、视频和语音等媒体，而不是 JSON 文本。
- `messages.json` 当前为带 `schemaVersion`、会话信息和 `messages` 数组的对象；消息包含稳定 ID、时间、顺序、类型、收发方向、发送人、会话标识、正文、引用和媒体元数据等字段。

以上只是当前样本快照，不得把目录名、可选字段或单个导出版本写死为永久产品协议。

### 4.2 原始格式与内部格式决定

采用三层格式：

1. **原始档案层**：保留当前 JSON、完整目录层级、完整性文件和媒体文件，导入器只读，不原地修改。
2. **可选交换层**：需要流式调试、迁移或脱敏样本时，可以生成“一条规范化消息一行”的 JSONL；JSONL 不是运行时权威数据库。
3. **运行时索引层**：使用 SQLite 规范化表、FTS5 全文索引和向量索引，供增量导入、过滤、检索、删除和追踪。

不采用以下方案：

- 每次回复时遍历原始 JSON。
- 把 37GB 原始目录复制进安装包或 Git 仓库。
- 为追求“统一格式”而覆盖或删除原始导出。
- 把聊天知识文档直接混入 Work Review 现有 `memory_chunks` 屏幕记忆表。

### FR-KB-01 源包识别

- 导入器优先读取 `manifest.json`、`schemaVersion`、`exportId`、会话 `meta.json` 和完整性信息。
- 每个源包保存来源路径、账户稳定 ID、导出 ID、导出时间、schema 版本、内容哈希、filters/覆盖范围、快照类型 `full | filtered | incremental | unknown`、前驱/后继关系、`active | retired | missing` 状态、导入时间和错误摘要。
- 所有快照类型都可以声明经过验证的 merge base/前驱。`filtered`、`incremental` 或 `unknown` 必须以“前一活动视图 + 本次所见消息 overlay”形成候选视图，永远不能据此删除未出现的历史；只有 manifest/filters 和计数证明为同账户、同覆盖范围的完整快照，且明确继承前一快照时，才允许以“新快照缺失”推导删除。
- 同一稳定消息在互不构成前后继的活动来源中正文冲突时，不静默覆盖：按用户确认的 source priority 选择，未确认则阻止该会话激活并报告冲突。
- 未识别的 schema 版本必须停止导入并提示，不得猜测字段含义后继续。

### FR-KB-02 消息规范化

规范化消息至少保留：

```text
account_stable_id
conversation_stable_id
message_stable_id / source_message_id
create_time
sort_seq
message_type / render_type
is_sent
sender_id / sender_display_name
text_content
quoted_content
source_json_path
content_hash
extra_json
```

- 跨导出包的规范消息唯一键优先使用 `account_stable_id + conversation_stable_id + message_stable_id`；导出包 ID 只作为来源证明，不参与该唯一键。
- 同一规范消息可以关联多个导出包来源，来源关系单独保存；只有确实缺少稳定消息 ID 时，才使用版本化的内容/时间/方向回退键并标记低置信度。
- `extra_json` 只保存经过白名单允许、大小受限且不含媒体二进制/大段原对象的附加字段；不能为“避免丢字段”而复制完整原始消息对象。原始完整信息继续由只读 JSON 保存。
- 相同消息在同一导出包或后续新导出包中重复出现，都不得产生重复规范记录。
- 规范消息 ID 与消息版本分离；正文、方向、发送人、引用、附加字段和媒体关系按 `import_generation` 保存不可变版本。代际成员关系单独保存，使 overlay 候选可以复用前代未变化版本并只替换本次出现的消息；旧活动代际继续读取旧成员/版本，不被新候选污染。
- 同一源消息正文变化时，新版本必须使候选知识块和向量索引重建；只有完整 import/index 组合原子激活后才替换旧版本。

### FR-KB-03 文本与媒体范围

M2 首批索引：

- 普通文字。
- 链接标题、链接摘要和 URL。
- 引用文字。
- 文件名、可用的文本说明和其他明确的文本字段。

M2 首批不解析：

- 图片内容。
- 语音转写。
- 视频内容。
- PDF、Word、压缩包和其他附件正文。

一条消息可以保存多个媒体候选引用或文件 ID。媒体文件首期只保留导出 JSON 已提供的来源引用和元数据，`exists_state` 默认是 `unknown`；导入阶段不遍历、不 `stat`、不哈希、不复制媒体正文，也不因媒体缺失阻塞文字知识库。媒体 OCR、ASR 和文档解析是已知扩展点，但需要单独确认后实施。

### FR-KB-04 对话分块

- 分块不得简单按固定字符切断对话。
- 每个知识块必须限制在同一会话内，按时间顺序保留说话人、收发方向和必要时间信息。
- 分块可以综合使用时间间隔、消息数量和 token 预算，并保留少量相邻消息重叠。
- 每个块保存稳定 chunk key/序号、首尾消息 ID、会话 ID、时间范围、内容哈希、分块版本和索引代际。
- 用户本人历史回复与对方消息的方向信息必须保留，便于后续检索相似问题及用户既有回复风格。

### FR-KB-05 增量与恢复

- 导入必须用 Rust 自定义 `serde_json::DeserializeSeed/Visitor` 或经过验证的等价流式解析器逐项消费根对象内嵌的 `messages[]`；禁止用会构造完整 `Vec` 的 `from_reader::<Archive>` 一次性反序列化大型文件。
- 小批事务只写入不可见的 `import_generation` 暂存代际、不可变 message versions 和 generation-membership。`filtered/incremental/unknown` 先继承已验证 merge base 的成员集合再 overlay 本次消息；`full` 后继按完整覆盖规则重建成员集合。整段会话解析、规范化、计数核对成功后只能标记为 `ready_candidate`；在匹配索引完成前不切换活动视图，失败代际对分块和检索不可见。
- 进程重启后默认从当前会话文件开头重新流式解析，并按稳定键跳过/幂等 upsert；不得假设能安全按 `messages[]` 元素序号 seek。可选 JSONL 只有在被明确生成时才可提供可定位恢复点。
- 重复导入同一未变化源包应快速完成且不产生重复数据。
- 只有满足 FR-KB-01 完整后继规则的新快照，才把缺失旧消息从候选活动视图移除；仅当该消息也不再属于其他活动来源时才删除或 tombstone 规范身份。关联的 chunk、FTS 和向量按外键/代际规则失效，不能永久残留。
- 单个会话损坏时记录错误并继续处理其他会话；源包级协议不兼容时整体停止。

### FR-KB-06 独立数据库与索引代际

- 聊天知识库使用独立的 `knowledge.sqlite`，由 `knowledge/store` 独占连接与读写 API；不得向 Work Review 核心数据库添加聊天表，也不得让大批导入/建索引事务阻塞工作记录写入。
- chunk、FTS 和向量重建使用不可见的 `index_generation`，记录它绑定的 import-generation 集合/快照哈希、分块版本、本地嵌入模型指纹、向量维度、开始/完成时间与 `building | ready | failed` 状态。
- 普通重建期间继续服务上一份完整活动快照；新 import-generation 集合与 index-generation 全部完成并通过计数/维度校验后，在同一事务中原子切换。失败或半成品代际不能被检索。
- `knowledge_catalog_state`（或等价单行状态）必须保存唯一的活动 import snapshot 哈希与 `active_index_generation_id`。查询向量必须读取活动索引代际记录的 provider、模型指纹和维度，不能直接读取尚未完成重建的候选配置。
- 用户明确移除源/会话/消息时，受影响范围必须立即加入本地拒绝过滤或暂时返回 `KB_NOT_READY`，不得在等待重建期间继续从旧索引召回已移除内容。
- `knowledge_messages`、媒体引用、来源关系、chunks、FTS 和向量必须有明确的唯一约束、外键与级联/失效语义，删除活动消息后不得留下可检索孤儿。

## 5. `knowledge_retrieve()` 强制边界

### 5.1 唯一职责

`knowledge_retrieve()` 只负责：接收本次待回复文字和检索范围，完成知识召回与排序，返回可审计的命中结果。它不得直接调用回复模型、修改微信、上传数据或显示 UI。

概念接口：

```text
knowledge_retrieve(
  request_id,
  query_text,
  binding_generation,
  scope: conversation(id)
       | selected_conversations(ids)
       | global_user_selected,
  top_k,
  token_budget
) -> {
  status,
  retrieval_mode,
  index_generation_id,
  binding_generation,
  hits[],
  elapsed_ms
}
```

每个 `hit` 至少包含：

```text
knowledge_chunk_id
conversation_id
source_message_range
source_time_range
excerpt
score
source_path
```

这是微信回复读取聊天知识的唯一业务入口：只有 importer 直接读取原始 JSON，只有 store 直接打开 `knowledge.sqlite`；retriever 通过 store API 查询。回复模型、桌宠、通用 Agent、MCP、Bot、Localhost API、上传器和其他 Work Review 模块不得绕过该入口直接查询聊天数据。

完整 `hits[]`、内部 chunk/message ID、分数、绝对/相对源路径和导出 provenance 只留在本地审计层。受信任的上下文适配器从 `RetrievedReply` 生成最小 `ModelKnowledgeContext`，只包含有界摘录、必要的时间/角色/方向标签和无命中状态；回复模型客户端不能访问本地来源路径或内部数据库 ID。

### FR-RAG-01 强制调用顺序

- 微信回复编排器必须直接调用并等待 `knowledge_retrieve()`；不得把检索注册成“由模型自行决定是否调用”的可选工具。
- 只有检索返回 `success` 或 `no_hit` 后，才允许调用回复模型。
- 同一 `request_id` 的模型重试复用第一次检索结果，不重复改变上下文。
- 追踪必须以单调 `stage_seq` 和合法状态迁移证明检索成功先于模型传输；时间戳只作为辅助观测。

### FR-RAG-02 混合检索

- 只复用 Work Review 的 HTTP/本地调用、向量归一化、BLOB 编解码、FTS5 和 RRF 等底层 primitive；不得复用其“语义记忆是否启用”的功能开关、云端提供商选择或自动降级策略。
- 聊天知识库使用独立的 `knowledge.localEmbedding` 配置和本地提供商校验。M2 首批只允许本机进程或 loopback 地址；`127.0.0.1`/`localhost` Ollama 属于本地调用，不得自动回退云端嵌入。
- 本地嵌入 HTTP 客户端默认禁止重定向；如底层库必须跟随重定向，则逐跳重新解析并验证仍为 loopback，任何非本机目标立即失败。
- 聊天知识库使用独立的 `knowledge_*` 表和索引，不污染屏幕语义记忆。
- 检索优先支持向量召回与 FTS 关键词召回的混合排序。
- `conversation(id)` 只能检索该会话，`selected_conversations(ids)` 只能检索用户明确选择的集合，`global_user_selected` 才允许全库检索；不得静默混入范围外会话。
- 请求“当前会话”但无法可靠映射，且用户没有显式选择全库或会话集合时，返回 `KB_SCOPE_UNRESOLVED`，不得猜联系人或自动扩大范围。

### FR-RAG-03 无命中与故障

- `no_hit` 表示检索已经执行但没有相关结果，不属于系统故障；模型可以在明确的“无知识命中”上下文下继续回答。
- 向量嵌入服务不可用时允许降级到本地 FTS，并在结果中标记 `retrieval_mode=fts_fallback`。
- 没有完整、活动且 `ready` 的索引代际时返回 `KB_NOT_READY`；部分导入或部分重建不能伪装成 `no_hit`。
- SQLite、索引读取或结果组装失败时，不得绕过知识库直接调用模型；应显示检索失败并结束本次请求。
- 知识块作为不可信外部文本注入提示词，必须与系统指令分隔，禁止其中内容改变产品规则或触发工具。

### FR-RAG-04 来源与追踪

- 每次回复记录查询文本哈希、知识库/索引代际、检索模式、命中 chunk ID、分数、模型请求 ID、单调 `stage_seq`、阶段状态和最终结果。
- 正式产品应允许查看本次建议使用了哪些会话片段；首期至少保证追踪数据可查。
- 追踪数据不得包含未命中的整个知识库内容。
- 本地审计记录与 `ModelKnowledgeContext` 分开保存/序列化；发送模型前必须能检查 payload 中不存在源路径、内部 ID、导出包标识和未入选命中。

## 6. 数据存储与隐私边界

- 原始聊天导出和规范化知识库默认只存本机。
- 当前 macOS 源目录只用于开发导入；Windows 正式产品通过用户选择或配置导入目录，不依赖硬编码的 macOS 路径。
- 原始聊天目录、规范化数据库和向量索引不得进入 Git、安装包或更新包。
- 微信截图、OCR、知识命中和建议不得自动进入 Work Review 远程上传、MCP、Bot、Localhost API 或联网搜索。
- M2 的知识导入、建索引和 `knowledge_retrieve()` 默认且首批只使用本地 SQLite、FTS 和本地嵌入，不得在微信请求中静默调用云端嵌入。
- 若未来需要云端嵌入，必须作为独立、用户明确触发的索引能力另行确认，不能成为本地检索失败后的自动降级。
- 回复模型可以使用用户已明确配置的远程 LLM：M1 只能发生在用户本次手动触发之后，M2 还必须发生在本次检索成功完成之后；只允许同一请求的有界传输重试，不得自动切换提供商/模型，也不得携带 MCP 或行动工具。
- 模型只接收本次回复所需的待回复文字和经过 token 预算裁剪的命中文段，不发送整个知识库。
- 原始导出由用户在产品外管理，产品永远不删除、不覆盖、不“重建”它。用户取消导入、源目录在外部消失或选择移除某个会话时，只删除/停用对应派生记录、FTS 和向量；可选 JSONL 与 `knowledge.sqlite` 才允许从原始导出删除后重建。
- 桌宠渲染、动画资源和资源清单不得产生外部网络请求、启动子进程、加载外部插件/脚本或原生库，也不得访问微信/知识库内容；它们只能接收编排层提供的有界显示 payload。

## 8. 验收要求

### AC-BASE Work Review 核心回归

发布前必须维护一份版本化的“Work Review 继承基线矩阵”，逐项列出上游功能、入口、数据依赖、修改前证据、修改后结果、自动/手工/契约测试方式和发布阻断状态；任何原能力不得因为没有真实外部凭据而从矩阵消失。正式产品派生后至少验证：

1. 应用启动、单实例、托盘、自启动设置和退出。
2. 工作记录暂停/恢复，前台应用、窗口标题、浏览器 URL、使用时长、应用分类和空闲状态正常。
3. 普通截图、OCR、隐私忽略/脱敏规则不因微信模块失效。
4. 概览、时间线、活动详情、小时汇总和应用分类可读取新增前后的记录。
5. 日报、周报生成，历史查看和 Markdown 导出可用。
6. 工作助手与模型设置可用，现有屏幕语义记忆不被聊天知识库污染。
7. 设置保存、多语言切换、数据目录、存储统计和清理入口可用。
8. 桌宠显示、普通气泡、已有提醒和新增微信持续气泡互不破坏。
9. S3/WebDAV、远程上传、MCP、Bot、Localhost API、联网搜索及其他可选网络能力保持原入口和默认隔离。
10. 没有真实外部凭据时，网络能力仍须完成配置 schema、mock/契约、队列边界和错误路径验收；只有真实连通性结果可标为条件验收，不能把该功能整体标为“未测”。

### AC-WX 微信回复闭环

1. 用户在支持布局的微信单聊中明确触发。
2. 产品取得正确聊天区截图并在本机 OCR。
3. 非微信窗口、截图失败或 OCR 无文字时不调用模型。
4. 建议显示在桌宠持续气泡中，只有点击复制后剪贴板才改变。
5. 全流程没有自动输入、粘贴、发送、滚动或切换联系人。
6. 一次手动动作最多调用一个明确配置的回复模型；同请求重试有上限且不切换提供商。除 M2 明确允许且单独计数的本地 embedding loopback 外，其他非 loopback egress、MCP/Bot/上传/搜索/行动工具调用计数均为零；重定向不能逃逸到外网。
7. 默认只产生含 `stage_seq` 的非正文本地追踪；截图、OCR、命中和建议在内容留存关闭时均不落盘、不进知识库、不进上传队列，开启后的删除和期限设置有效。
8. 成功、失败、超时和取消四类截图路径都证明桌宠及全部可见覆盖层不出现在采集图中；流程结束后恢复截图前状态，微信仍保持前台且未收到自动输入。
9. 预置剪贴板后分别验证显示、悬停、拖动、普通提醒、关闭、复制、`suggestion_generation` 失效和 M2 `binding_generation` 失效；只有点击当前有效建议的“复制”才把剪贴板改为该建议，普通提醒不能覆盖持续建议，失效建议不能复制。
10. 依赖和权限审计证明桌宠渲染层不能读取原始聊天 JSON、打开 `knowledge.sqlite`、调用检索/模型或执行输入、粘贴与发送，只能消费有界显示 payload。

### AC-PET 桌宠参考复用与运行时隔离

1. 安装包、依赖图、运行进程、窗口和已加载模块证明桌宠仍由 Work Review Tauri 外壳唯一管理；不存在 VPet/.NET/WPF GUI sidecar、重复托盘/自启动/更新器、VPet 程序集、Steam/Workshop 或代码 MOD loader。
2. 以批准的 Work Review 发行基线为对照，对完整桌宠与微信流程进行网络、外部进程、外部插件/脚本加载和合成输入观测；不得出现由桌宠、动画或资源配置触发的新增调用。需求明确批准的回复模型、本地 loopback 服务和可选 `OcrBackend` sidecar 按各自白名单单独计数，且桌宠/资源层不得调用它们；放在受测资源目录旁的测试 DLL、脚本或命令不会被扫描、加载或执行。
3. 发布前有可复核的参考与素材台账：独立实现记录所参考的行为；复制代码记录原文件、修改和 Apache-2.0 发行义务；所有图片、字体、图标、动画和品牌资源均能证明为本产品自有或已明确授权。未经批准的 VPet 素材或标识为发布阻断项。
4. 若本次发行包含 PNG 序列帧增强，则额外验证 `single/start/loop/end`、状态切换与中断、动作变体、fallback、帧缓存、点击区域、拖动锚点、不同 DPI 和多显示器边界；资源缺失、损坏或动作中断时不得白屏、卡死或丢失气泡。
5. 第 4 项只对实际包含 PNG 序列帧增强的发行生效。未启用该增强时，继续使用现有 Work Review 渲染器即满足当前范围，不得因没有新动画引擎而判定 M1/M2 失败。

### AC-KB 知识库导入

1. 能从指定 `liaotian` 源目录识别 manifest、721 个当前会话目录和各自 schema；manifest/meta/实际解析计数可核对，当前样本总消息数应核对为 402,673，任何差异都有解释且不修改源文件。
2. 能用嵌套 `messages[]` 流式解析导入文字消息并保留稳定 ID、时间、方向、`render_type`、会话和来源追踪；对约 151MiB、108,447 条消息的最大当前会话记录峰值内存。
3. 同一消息跨多个导出包不重复写入；中断重启可从文件头安全重放；完整新导出缺失的旧消息能被删除/tombstone；单会话错误可定位且失败代际不可见。
4. 37GB 媒体不被复制进索引数据库，缺失媒体不阻塞文字消息导入。
5. 原始 JSON 始终只读且产品不能删除/重建；只有可选 JSONL 与 `knowledge.sqlite`/FTS/向量派生层可删除并从原始 JSON 重建。
6. 中文关键词查询和中文语义查询分别经过真实样本验证；分词器、嵌入模型和向量维度只能在该探针后冻结。
7. 导入和重建期间旧活动 import/index 组合仍可用，新 message versions 和索引不会部分暴露；切换后消息、chunk、FTS、向量计数与外键一致，Work Review 工作记录线程保持响应。
8. `full/filtered/incremental/unknown`、前驱/后继和 source priority 分别验收：overlay 代际保留 merge base 中未出现的消息，筛选/未知导出不会推导删除，冲突来源未确认时不会激活。

### AC-RAG 强制检索

1. 对已知聊天问题能返回带来源的相关历史片段。
2. 每一次 M2 微信回复模型调用都有同一 `request_id` 的在先检索记录；不把 Work Review 助手或 M1 调用误计入该约束。
3. 零命中时记录 `no_hit` 后可以继续生成。
4. 本地向量服务不可用时降级 FTS；索引未就绪返回 `KB_NOT_READY`，范围不明确返回 `KB_SCOPE_UNRESOLVED`，数据库检索失败时模型不被调用。
5. 模型重试不重复检索，也不改变已冻结的知识上下文。
6. 模型传输 spy 与单调 `stage_seq` 共同证明检索成功状态先于模型传输；任何检索错误路径的真实模型网络调用计数均为零。
7. 微信回复过程除用户明确配置的单一回复模型和 M2 本地/loopback embedding 外，没有其他非 loopback egress、远程上传、MCP、Bot、网页搜索、Localhost API、云端嵌入或通用行动工具调用；上传队列中没有微信/知识库数据。
8. 阶段 2/3 探针后、阶段 4 开始前，必须冻结版本化性能门槛文件，记录目标 Windows 硬件、数据规模以及首次索引时长、派生库/索引体积、构建峰值内存、查询 p50/p95、工作记录调度漂移/UI 响应的数值上限；M2 发布实测必须全部满足。若 SQLite BLOB 扫描不达标，须在不改变 `knowledge_retrieve()` 契约的前提下替换向量索引实现后重验，不能只记录超标结果仍判通过。
9. `conversation(id)`、`selected_conversations(ids)` 和 `global_user_selected` 三种范围分别验收，任何结果都不包含范围外会话。
10. 发送给远程回复模型的 `ModelKnowledgeContext` 只含入选摘录和必要标签；本地路径、内部 chunk/message ID、导出包信息及未入选内容均不在实际 payload 中。
11. 三种范围都有可操作的用户选择入口；单会话重名可区分，窗口/聊天/范围变化会递增 `binding_generation` 并使旧请求失效，无法绑定时不会自动全库检索。

## 9. 完成定义

- **M1 完成**：AC-BASE、AC-WX 与 AC-PET 当前适用项全部通过。
- **M2 完成**：AC-KB、AC-RAG 与 AC-PET 当前适用项全部通过，并在真实 Windows 回复链路中证明“先检索、后模型”。
- Work Review 原有能力不再以“非阻塞、以后再决定”的方式排除在产品外；它们是正式产品基础能力。
- 知识库/RAG 不再属于未知需求池；M1 完成后按本文件继续交付 M2。
- 对 VPet 的参考分析只形成设计输入；接入 VPet 运行时/GUI sidecar、Steam/Workshop、代码 MOD、内置素材或新建通用动画引擎均不是 M1/M2 交付内容。现有 Rust/Svelte 桌宠内的必要状态与气泡调整不受此条限制。
- Live2D、ASR、TTS、图片/语音/附件知识化、多模态 OCR、直播和通用电脑控制仍需用户另行确认，不因本次修订自动进入实施。
